多个训练任务共享同一张物理 RDMA 网卡，网卡凭什么不串包？

这是理解 RDMA 资源模型最好的入口。先把结论摆出来，四组概念各管一段，缺一层都不成立：

| 概念 | 解决什么问题 |
|---|---|
| **IP / GID / LID** | 数据发送到哪台机器、哪个网络端点 |
| **QP / QPN** | 数据属于哪个通信连接 |
| **CQ** | 通信操作完成后如何通知应用 |
| **PD / MR / lkey / rkey** | 哪些内存允许被访问、哪些不允许 |

RoCEv2 和 InfiniBand 在 QP、CQ、PD、MR 这些核心机制上基本一致，差别在底层网络寻址、报文封装、网络管理与隔离方式。

> 本文是 RDMA 系列的第五篇。前三篇讲承载 RDMA 的网络本身（[技术手册](/2026/04/20/2026-04-20-RDMA技术手册：面向AI场景的深度解析/)、[技术栈全解](/2026/07/17/2026-07-17-RDMA技术栈全解/)、[全链路拆解](/2026/09/11/2026-09-11-RDMA全链路拆解从verbs到硬件再到训练平台落点/)），第四篇讲 [RoCEv2 无损网络的三件套](/2026/11/10/2026-11-10-RoCEv2无损网络PFC-ECN-DCQCN与配置一致性/)。这一篇往上一层：**网卡内部有哪些资源、它们怎么隔离不同任务、NCCL 又是怎么用它们的。**

## 一、六个核心对象

| 对象 | 全称 | 作用 |
|---|---|---|
| QP | Queue Pair | 通信队列对 |
| SQ | Send Queue | 存放发送操作 |
| RQ | Receive Queue | 存放接收操作 |
| CQ | Completion Queue | 存放操作完成结果 |
| PD | Protection Domain | 内存访问保护域 |
| MR | Memory Region | 注册给 RDMA 网卡使用的内存区域 |

围绕它们还有几个名词：

- **WR**（Work Request）：应用提交给网卡的操作请求
- **WQE**（Work Queue Element）：网卡工作队列中的请求描述符
- **CQE**（Completion Queue Entry）：网卡产生的完成记录
- **CM**（Connection Manager）：辅助建立 RDMA 连接的组件

### 与传统 TCP 网络的类比

| 普通 TCP 网络 | RDMA 网络（以 RC 为例） |
|---|---|
| Socket | QP |
| Socket 连接标识 | 端点地址 + QPN |
| TCP Sequence Number | PSN |
| send / recv | RDMA Work Request |
| I/O 完成通知 | CQ / CQE |
| 操作系统进程内存保护 | PD + MR + 内存访问权限 |

两者不是完全一一对应，但这个类比有助于理解。

### QP 与 CQ 的关系

QP 负责提交通信工作，CQ 负责接收完成结果。队列通常位于网卡可访问的内存中，网卡维护对应的硬件上下文。

假设 NCCL 想发送一段 4 MB 的梯度数据，大致流程是：

1. NCCL 向 QP 的 SQ 提交一个 WR
2. 用户态驱动将请求转换为 WQE，并通知网卡
3. 网卡读取请求及对应数据，执行 RDMA 操作
4. 对于需要完成通知的操作，网卡向 CQ 写入 CQE
5. NCCL 轮询 CQ，判断操作是否成功

> **CQ 不是网络连接，也不是用来存放收到的梯度数据的**——它只记录工作完成状态。
>
> 而且 **QP 和 CQ 不是一对一**。多个 QP 可以共用一个 CQ，应用通过 CQE 中的 `qp_num` 和 `wr_id` 区分完成的是哪个请求。

## 二、QPN 如何区分连接

假设 Node 1 上的 RDMA 网卡已经有四个 QP：

| QPN | 所属任务 | 对端 QPN | 对端 IP | 本地保护域 |
|---|---|---|---|---|
| 101 | Job A | 201 | 10.0.0.2 | PD 10 |
| 102 | Job B | 202 | 10.0.0.2 | PD 20 |
| 103 | Job A | 203 | 10.0.0.3 | PD 10 |
| 104 | Job C | 301 | 10.0.0.4 | PD 30 |

这是一张用于理解的**逻辑表**，并非网卡真实的硬件数据结构。实际上网卡并不知道 Job A、Job B 这些 Kubernetes 概念，它知道的是 QP、PD、地址和传输状态。

每个普通 RC QP 都会维护自己的通信上下文：

```
// 示意结构，不是实际驱动定义
struct QPContext {
    uint32_t local_qpn;
    uint32_t remote_qpn;

    Address remote_address;

    uint32_t send_psn;
    uint32_t recv_psn;

    uint32_t pd_id;
    uint32_t send_cq_id;
    uint32_t recv_cq_id;

    Queue send_queue;
    Queue recv_queue;

    AccessFlags permissions;
    QPState state;
};
```

所以，**即使两个任务使用同一个源 IP、目的 IP 和物理网卡，QP 上下文仍然不同。**

### RoCEv2 报文中直接携带目的 QPN

一个简化的 RoCEv2 RDMA Write 报文结构：

```
Eth | IP | UDP | BTH | RETH | Data | CRC
                    │      └── 远端内存地址、R_Key、DMA Length
                    └── Opcode、Dest QP、PSN、P_Key 等
```

**BTH 包含 24 位目的 QPN 和 24 位 PSN**；RoCEv2 使用 UDP 目的端口 **4791**。RDMA Write 的首包或单包还会携带 RETH 等必要信息。

于是两条 RDMA 连接的报文可以长这样：

| 报文字段 | Job A | Job B |
|---|---|---|
| 源 IP | 10.0.0.1 | 10.0.0.1 |
| 目的 IP | 10.0.0.2 | 10.0.0.2 |
| UDP 目的端口 | 4791 | 4791 |
| **BTH Dest QP** | **201** | **202** |
| PSN | 10001 | 80001 |
| Payload | A 的梯度 | B 的梯度 |

数据到达 Node 2 的网卡后，**网卡根据目标 QPN 找到相应的 QP 上下文**。此外 RC QP 有自己的 PSN、ACK、重传及其他传输状态，不同 QP 的报文顺序状态也是独立的。

> **一个容易误解的地方**：RoCEv2 虽然使用 UDP 封装，但 **RC 模式的 RDMA 通信仍然是可靠传输**。可靠性由 RDMA 传输协议实现，而不是由外层 UDP 实现。

## 三、PD 与 MR 如何隔离内存

QPN 只解决了数据属于哪个连接，还不足以解决内存访问安全——还需要 PD 和 MR。

### PD：Protection Domain

PD 可以理解为 RDMA 网卡中的**本地内存访问权限分组**。创建 QP 时把 QP 绑定到 PD，注册内存时也把 MR 绑定到 PD——接收方处理 RDMA Read/Write 时，**必须检查目标内存区域与接收 QP 的 PD 是否匹配**。

> **PD 是本地的保护域**，两个通信节点上的 PD 编号不需要相同。它也不是 Kubernetes 给每个 Job 分配的全局租户 ID。

### MR：Memory Region

假设 Job B 有一块 1 MB 内存，需要允许其他 Worker 对它做 RDMA Write：

```c
struct ibv_mr *mr = ibv_reg_mr(
    pd,
    buffer,
    1024 * 1024,
    IBV_ACCESS_LOCAL_WRITE |
    IBV_ACCESS_REMOTE_WRITE
);
```

注册成功后应用得到两个 key：

| Key | 用途 |
|---|---|
| `lkey` | 本地 RDMA 操作访问注册内存时使用 |
| `rkey` | 远端 RDMA Read/Write 等操作访问该内存时使用 |

网卡会维护对应内存的地址映射、长度、权限以及所属 PD。**远端进程并不能随便提供一个物理地址就要求网卡写入对应内存。**

### 网卡到底检查什么

假设 Job A 发出一条 RDMA Write：

```
Destination QP: 201
Remote Address: 0x10000000
Remote Key:     0xA001
Length:         4096
```

接收方网卡的处理逻辑可以简化为：

```
// 原理伪代码，不是实际网卡固件源码

qp = lookup_qp(packet.dest_qpn);

if (!qp || !qp.can_receive)
    reject();

check_transport_state(qp, packet);

mr = lookup_mr(packet.rkey);

if (!mr || !mr.valid)
    reject();

if (mr.pd != qp.pd)
    reject();

if (!qp.allow_remote_write || !mr.allow_remote_write)
    reject();

if (!address_in_range(mr, packet.addr, packet.len))
    reject();

dma_write(mr, packet.addr, packet.payload);
```

### 真实实现长什么样：看 Soft-RoCE

Linux 内核的 Soft-RoCE（RXE）在软件中实现 RoCE 协议，因此可以看到很多在物理网卡中由硬件和固件完成的操作。

内核源码 [`drivers/infiniband/sw/rxe/rxe_mr.c`](https://github.com/torvalds/linux/blob/master/drivers/infiniband/sw/rxe/rxe_mr.c) 中的 `lookup_mr()` 函数会检查：

- 本地或远端 key 是否匹配
- MR 与请求所使用的 PD 是否匹配
- MR 的访问权限是否满足操作要求
- MR 是否处于有效状态

而 `rxe_resp.c` 中，接收方处理远端操作时会使用当前 QP 的 PD 和报文中的 rkey 查找 MR，再检查内存地址范围。**这就是真实的底层隔离逻辑。**

当然，ConnectX 等物理网卡并不是在 CPU 上执行这段代码，而是由自己的硬件和固件实现相应语义。

### 两条路径：Slow Path 与 Fast Path

你可能还有另一个疑问：Job A 和 Job B 都打开了 `/dev/infiniband/uverbs0`，为什么 Job A 不能直接操作 Job B 创建的 QP？

因为这里还有一层 Linux 内核资源管理。`ib_uverbs` 根据文件描述符和用户态上下文跟踪资源对象，通过内核维护的对象句柄限制进程能够操作的资源。这也解释了为什么进程退出时，即使没有主动调用所有资源销毁函数，**内核通常也能回收该上下文拥有的 RDMA 资源**。

| 路径 | 操作 | 执行方式 |
|---|---|---|
| **Slow Path** | 创建 QP、CQ、PD，注册 MR | 用户态与内核驱动交互 |
| **Fast Path** | 提交 WQE、收发数据、轮询 CQ | 通常直接操作映射的队列及网卡寄存器 |

这个设计既实现资源管理和权限检查，又避免每次收发数据都经过内核协议栈。

## 四、一条 RC 连接是怎么建起来的

下面的代码使用 libibverbs API。为了突出关键机制，**省略了错误处理、完整状态参数、资源释放等代码**——不是可以直接编译运行的完整程序。

### Step 1：打开 RDMA 设备

```c
struct ibv_device **devices = ibv_get_device_list(NULL);

struct ibv_context *ctx = ibv_open_device(devices[0]);
```

假设打开的设备是 `mlx5_0`。这一步相当于进程获得了访问 RDMA 网卡的上下文。**Job A 和 Job B 都可以打开 `mlx5_0`，但各自拥有自己的用户态设备上下文。**

### Step 2：创建 PD、CQ、MR

```c
struct ibv_pd *pd = ibv_alloc_pd(ctx);

struct ibv_cq *cq = ibv_create_cq(ctx, 128, NULL, NULL, 0);

char *buffer = malloc(4096);

struct ibv_mr *mr = ibv_reg_mr(
    pd, buffer, 4096,
    IBV_ACCESS_LOCAL_WRITE | IBV_ACCESS_REMOTE_WRITE
);
```

此时进程已经拥有自己的内存保护域、完成队列和注册内存。

### Step 3：创建 QP

```c
struct ibv_qp_init_attr attr = {
    .send_cq = cq,
    .recv_cq = cq,
    .qp_type  = IBV_QPT_RC,
    .cap = {
        .max_send_wr  = 128,
        .max_recv_wr  = 128,
        .max_send_sge = 1,
        .max_recv_sge = 1
    }
};

struct ibv_qp *qp = ibv_create_qp(pd, &attr);

printf("QPN: %u\n", qp->qp_num);
```

调用成功后，驱动和网卡为应用创建 QP 并返回分配好的 QPN。

> **QPN 不是由 AI 平台或 Job Controller 分配的**，而是底层 RDMA 实现分配的。在相关 RDMA 设备的 QP 编号空间内，同时有效的普通 QP 不会使用相同 QPN。**QPN 在不同设备之间可以重复，销毁后也可能被重新使用。**

### Step 4：交换连接信息

QP 创建完成时还不知道要和哪个远端 QP 通信，所以两端需要交换信息：

```c
struct ConnectionInfo {
    uint32_t qpn;
    uint32_t psn;

    uint16_t lid;
    union ibv_gid gid;

    uint64_t addr;
    uint32_t rkey;
};
```

例如：

| 字段 | Worker 0 | Worker 1 |
|---|---|---|
| QPN | 101 | 201 |
| 初始 PSN | 10000 | 20000 |
| IP 对应 GID | `::ffff:10.0.0.1` | `::ffff:10.0.0.2` |
| MR 地址 | 0x10000000 | 0x20000000 |
| rkey | 0xA001 | 0xB001 |

通常可以通过普通 TCP Socket 交换这些元数据。其中 QPN、PSN、地址信息用于配置连接；MR 地址和 rkey 用于后续的单边 RDMA 内存操作——**后两者不一定在连接建立时交换，也可以按需在后续交换。**

> 也就是说，**RDMA 的控制面完全可以走 TCP，真正的大规模训练数据走 RDMA。** 两者不冲突。

### Step 5：修改 QP 状态

创建后的 QP 不能立即通信，需要经过状态转换：

| 状态 | 含义 |
|---|---|
| **RESET** | QP 刚刚创建，尚未配置 |
| **INIT** | 设置端口、P_Key 索引和访问权限 |
| **RTR**（Ready To Receive） | 配置远端 QPN、路径地址、接收 PSN |
| **RTS**（Ready To Send） | 配置发送 PSN、重传、超时等参数 |

最核心的连接配置代码类似：

```c
struct ibv_qp_attr attr = {
    .qp_state    = IBV_QPS_RTR,
    .dest_qp_num = remote.qpn,
    .rq_psn      = remote.psn,
    .path_mtu    = IBV_MTU_1024
};

// 还需设置 ah_attr 等必需参数
ibv_modify_qp(qp, &attr, mask);
```

其中 `attr.dest_qp_num = remote.qpn;` 就是**将本地 QP 和远端 QP 关联起来**的重要步骤。两端分别完成各自的 QP 状态配置、进入 RTS 后，就能进行正常的 RC 通信。

### Step 6：真正发起 RDMA Write

```c
struct ibv_sge sge = {
    .addr   = (uintptr_t)buffer,
    .length = 4096,
    .lkey   = mr->lkey
};

struct ibv_send_wr wr = {
    .wr_id      = 1001,
    .sg_list    = &sge,
    .num_sge    = 1,
    .opcode     = IBV_WR_RDMA_WRITE,
    .send_flags = IBV_SEND_SIGNALED
};

wr.wr.rdma.remote_addr = remote.addr;
wr.wr.rdma.rkey        = remote.rkey;

struct ibv_send_wr *bad_wr;
ibv_post_send(qp, &wr, &bad_wr);
```

**注意这里没有传入目的 IP，也没有传入远端 QPN。** 因为这些信息在建立 RC QP 时就已经配置到 QP 上下文里了。现在应用只需要告诉网卡：

- 使用哪个本地 QP
- 读取本地哪块内存
- 写到远端哪块内存
- 远端内存访问 key 是什么

网卡就能根据 QP 上下文构造报文并执行传输。

### Step 7：轮询 CQ

```c
struct ibv_wc wc;
int n;

do {
    n = ibv_poll_cq(cq, 1, &wc);
} while (n == 0);

if (n > 0 && wc.status == IBV_WC_SUCCESS) {
    printf("QP %u, WR %lu completed\n",
           wc.qp_num, (unsigned long)wc.wr_id);
}
```

这样就完成了一次基本的 RDMA 操作。

> **一个容易忽略的点**：普通 RDMA Write **不需要接收端预先提交 Receive WR，也不会天然给接收端产生一条 CQE**。如果接收端应用需要得到数据到达通知，通信库还需要设计同步机制，例如 Write with Immediate 或额外的控制消息。

## 五、RoCEv2 与 InfiniBand：传输层同源，寻址分道

### 报文格式不同，核心机制相同

```
RoCEv2:      MAC | IP | UDP | BTH | 扩展头 | 数据 | CRC
InfiniBand:  LRH | GRH* | BTH | 扩展头 | 数据 | CRC
                              └── 共用的 RDMA 传输头及语义
```

（GRH 在适用的全局寻址场景下使用。）

从应用层看，两者都可以调用 `ibv_create_qp()`、`ibv_reg_mr()`、`ibv_post_send()` 等 Verbs API，**但不同网络需要提供不同的路径寻址信息**。

### 连接建立时的寻址方式不同

| 维度 | RoCEv2 | InfiniBand |
|---|---|---|
| 物理网络 | Ethernet | InfiniBand |
| 网络寻址 | IP 对应的 GID | LID / GID |
| 路由机制 | IP 路由、以太网转发 | IB Fabric 路由 |
| 子网管理器 SM | 不需要 IB SM | **需要** |
| UDP 4791 | 使用 | 不使用 |
| 目标 QPN | 有 | 有 |
| PSN、ACK | RC 支持 | RC 支持 |
| PD、MR、CQ | 支持 | 支持 |
| 网络分区 | VLAN、VRF 等 | **P_Key** |
| 拥塞控制 | 通常 ECN、CNP，可配合 PFC | IB 流控及拥塞管理 |

RoCEv2 的 GID 通常与网络接口配置的 IP 关联，IPv4 地址可以表示为 IPv4-mapped IPv6 GID，驱动会维护对应的 GID 表。

**RoCEv2 的路径配置**：

```c
attr.ah_attr.is_global        = 1;
attr.ah_attr.grh.dgid         = remote.gid;
attr.ah_attr.grh.sgid_index   = local_gid_index;
attr.ah_attr.grh.hop_limit    = 64;
```

**同一 IB 子网中的典型 LID 寻址**：

```c
attr.ah_attr.is_global = 0;
attr.ah_attr.dlid      = remote.lid;
attr.ah_attr.sl        = 0;
attr.ah_attr.port_num  = 1;
```

（均为简化示例，两种方案都需要其他必要的 QP 参数。IB 也可以使用全局 GID 寻址。）

除了路径配置不同，**QP 状态转换和基本 RDMA 操作非常相似**。

### IB 不需要 IP 就能通信吗

**可以。** InfiniBand 原生 RDMA 可以通过 LID、GID、QPN 等信息完成通信，不依赖 IP 协议栈。

但训练框架仍然经常需要 IP 网络，用于 rendezvous、连接信息交换、管理通信等。因此 IB 集群通常会使用普通以太网管理网络，或者 IPoIB。**IPoIB 和原生 IB RDMA 是不同的通信方式，不要混在一起。**

### 多租户隔离的四个层次

如果你要提供一个允许不互信租户使用的 AI 云平台，光靠 QP、PD、MR 还不够：

| 层次 | 解决的问题 | 实现机制 |
|---|---|---|
| **连接隔离** | 正常通信不会串包 | QP、QPN、PSN |
| **内存隔离** | 不能任意访问其他进程内存 | PD、MR、rkey |
| **租户网络隔离** | 未授权租户之间不能通信 | VF、VLAN、VRF、P_Key 等 |
| **性能隔离** | 不能抢光别人的资源 | QoS、带宽限制、RDMA cgroup |

- **RoCEv2 走以太网隔离**：通常需要结合 SR-IOV VF、VLAN、VRF、交换机 ACL、硬件防伪造策略等能力。
- **InfiniBand 走 P_Key 分区**：Subnet Manager 管理 P_Key 分区成员关系，报文携带对应的 P_Key，网络设备根据分区成员关系检查。

> ⚠️ **两个必须警惕的点**：
> 1. **RDMA 数据可能绕过宿主机普通网络协议栈**，因此不能默认 Kubernetes NetworkPolicy 或 iptables 就能拦截所有 RDMA 流量。必须确认实际的数据路径和策略执行位置。
> 2. **rkey 不是密码学意义上的身份认证密钥，QPN 和 PSN 也不是安全凭证。** 正常通信不串包，与抵御恶意租户攻击，是两个不同的问题。
>
> 另外，如果两个 Pod 共享一个允许访问多个 P_Key 的物理 HCA，仍需确保每个租户只能使用授权给它的分区——**不能简单地在 Job 中指定一个 P_Key 就认为实现了完整隔离。**

## 六、NCCL 是怎么用这套东西的

实际运行时，Worker 里不会有人自己写上面那些 C 代码。调用链大致是：

```
PyTorch                     torch.distributed / AllReduce
  ↓
NCCL                        通信拓扑、Channel、Rank、集合通信
  ↓
NCCL NET/IB Transport       创建 QP、CQ、PD、注册 MR
  ↓
libibverbs / mlx5 Provider  提交 Verbs 操作、构建 WQE
  ↓
Linux RDMA Driver           资源管理、设备上下文
  ↓
RDMA NIC                    DMA、数据收发、ACK、传输状态
```

> NCCL 的 `NET/IB` 通信后端**同样支持 RoCE**，并不是只有 InfiniBand 才用这个模块。

NCCL 源码 [`src/transport/net_ib/connect.cc`](https://github.com/NVIDIA/nccl/blob/master/src/transport/net_ib/connect.cc) 中包含这些函数：

| 函数 | 作用 |
|---|---|
| `ncclIbSenderQpsCreate` | 创建发送侧 QP |
| `ncclIbReceiverQpsCreateToRts` | 创建接收侧 QP 并配置连接状态 |
| `ncclIbQpCreate` | 封装底层 QP 创建操作 |
| `ncclIbQpInit` | 初始化 QP |

可以看到它确实在创建 RC QP、指定 PD 和 CQ，并将 QPN 放入连接元数据与远端交换。

### 一个 Worker 会创建多少 QP

**不一定是一个。** 假设一个 Job 有两个 Worker、每个 Worker 有 8 张 GPU、每个 Worker 启动 8 个训练进程、每个 GPU 对应一个 Rank——那么整个任务有 16 个 Rank。

NCCL 可能根据通信拓扑、Channel 数量、网卡数量、通信算法及每个连接的 QP 配置，创建**多个** RDMA QP。所以以下资源之间**没有固定的一对一关系**：

```
TrainingJob
    └── Worker Pod
          └── 训练进程 / Rank
                └── NCCL Communicator
                      └── 通信连接
                            └── 一个或多个 QP
```

**你不能简单地认为一个 Pod 申请了一个 RDMA 资源，就只能创建一个 QP。**

## 七、从训练启动到 QP 建立：四步走

### 7.1 成员发现（PyTorch / torchrun）

NCCL **不会主动扫描 Kubernetes 集群寻找 Worker**，也不会扫描 RDMA 网络判断哪些网卡属于同一个训练任务。**它是由上层训练框架告知参与者身份**，然后在这些参与者之间建立通信拓扑。

整个过程有三个层次：

| 层次 | 负责者 | 确定什么 |
|---|---|---|
| 训练任务成员发现 | PyTorch / torchrun | 哪些进程属于同一个 Job、Rank 是多少、总共有多少 Rank |
| 通信拓扑构建 | NCCL | 哪些 GPU 应该互相通信、用 Ring 还是 Tree、选哪些网卡和路径 |
| RDMA 连接建立 | Verbs | 创建 QP、CQ，交换 LID/GID/QPN，建立实际数据传输连接 |

用一个具体例子走一遍：**4 个 Worker、每个 Worker 2 张 GPU 和 2 张 RDMA 网卡**，即 4 个 Pod、8 张 GPU、8 个训练 Rank（`WORLD_SIZE = 8`）。

> 注意 **Worker Pod 和 Rank 不是同一个概念**。在常见的一进程一卡模式下，一个 Worker Pod 里可能有 8 个 Python 训练进程，每个进程有一个全局 Rank。**NCCL 主要在 Rank 粒度上组织集合通信，而不是 Kubernetes Pod 粒度。**

平台为每个 Pod 注入：

| 环境变量 | Worker 0 | Worker 1 | Worker 2 | Worker 3 |
|---|---|---|---|---|
| `NNODES` | 4 | 4 | 4 | 4 |
| `NODE_RANK` | 0 | 1 | 2 | 3 |
| `NPROC_PER_NODE` | 2 | 2 | 2 | 2 |
| `MASTER_ADDR` | worker-0 | worker-0 | worker-0 | worker-0 |
| `MASTER_PORT` | 29500 | 29500 | 29500 | 29500 |

然后每个 Pod 执行：

```bash
torchrun \
  --nnodes=4 \
  --nproc-per-node=2 \
  --node-rank=${NODE_RANK} \
  --master-addr=${MASTER_ADDR} \
  --master-port=29500 \
  train.py
```

torchrun 会为每个训练进程设置 `RANK`、`LOCAL_RANK`、`WORLD_SIZE` 等环境变量。此时上层框架就知道这是一个由 8 个 Rank 组成的训练任务了——**但还没有必然建立 RDMA 连接。**

### 7.2 Rendezvous 汇合

所有训练进程使用共同的初始化 Store 汇合，**但训练数据不需要经过 TCPStore**。

```python
import os
import torch
import torch.distributed as dist

local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)

dist.init_process_group(
    backend="nccl",
    init_method="env://"
)
```

这里就进入了 PyTorch 的分布式通信初始化流程。

> **`MASTER_ADDR` 是初始化集合点的地址，不是所有梯度数据的转发地址。**

### 7.3 Communicator 如何区分两个训练 Job

NCCL 有一个重要概念叫 **Communicator（通信域）**：

```c
ncclCommInitRank(&comm, world_size, unique_id, rank);
```

| 参数 | 含义 |
|---|---|
| `comm` | 当前进程的通信域对象 |
| `world_size` | 通信域包含多少 Rank |
| `unique_id` | 通信域初始化标识 |
| `rank` | 当前进程在通信域中的编号 |

典型情况下，Rank 0 调用 `ncclGetUniqueId(&id)` 生成 ID，然后 PyTorch 通过 Store 把这个 ID 分发给其他参与训练的 Rank。**所有 Rank 使用相同的 Unique ID 初始化 NCCL Communicator。**

**即使 Job A 和 Job B 都存在 Rank 0、Rank 1、Rank 2、Rank 3，它们也是不同通信域中的 Rank。** 它们不会因为共用一张网卡就自动加入彼此的训练任务。

> 当然，**这种通信域区分不是密码学意义上的租户安全隔离**，平台仍需要提供网络访问控制。

### 7.4 NCCL 怎么知道该和谁通信、该选哪张网卡

**和谁通信**由集合通信算法决定。以 AllReduce 为例，4 个 Rank 可以选择 Ring、Tree、Full Mesh 等不同算法。Ring 的通信顺序可以是：

```
Rank 0 → Rank 1 → Rank 2 → Rank 3 → Rank 0
```

NCCL 需要建立能够支持这些通信边的传输连接。实际 NCCL 可以建立多个 **Channel**，每个 Channel 有自己的通信拓扑，并行处理不同的数据块。

> **并不是 8 个 Rank 就一定需要让所有 8 个 Rank 两两建立 RDMA QP。** 更关键的是，**如果两个 Rank 位于同一台物理机器，它们可能根本不需要 RDMA。**

**选哪张网卡**由 NCCL 的 **Topology Detection 与 Graph Search** 模块负责。NCCL 初始化时会收集本地硬件信息（GPU、PCIe、NVLink、NUMA 节点、RDMA 设备及端口），在各 Rank 之间交换，再构造通信拓扑。

在物理机上执行 `nvidia-smi topo -m` 可能看到：

```
        GPU0  GPU1  NIC0  NIC1
GPU0     X    SYS   PIX   SYS
GPU1    SYS    X    SYS   PIX

NIC0    PIX   SYS    X    SYS
NIC1    SYS   PIX   SYS    X

NIC Legend:
NIC0: mlx5_0
NIC1: mlx5_1
```

其中 `PIX`、`PXB`、`PHB`、`SYS` 描述不同设备之间的硬件路径。NCCL 综合硬件拓扑、带宽、通信算法和网卡使用情况做选择，**不只是简单地按网卡编号分配**。

| 通信范围 | 可能采用的传输方式 |
|---|---|
| 同一台机器、支持 GPU P2P | NVLink / PCIe |
| 同一台机器、不支持直接 P2P | Shared Memory 等 |
| 不同机器、有 RDMA | NCCL NET/IB |
| 不同机器、使用普通网络 | NCCL NET/Socket |

所以 **NCCL 做的其实是一个从逻辑通信拓扑到物理硬件传输路径的映射**。

### 7.5 真正的 QP 连接

假设 NCCL 已决定 Rank 1 需要通过 Worker 0 的 NIC 1 向 Worker 1 的 Rank 2 发送数据：

| 信息 | Rank 1（发送端） | Rank 2（接收端） |
|---|---|---|
| 普通 Pod IP | 10.244.0.5 | 10.244.1.5 |
| RDMA Device | `mlx5_1` | `mlx5_0` |
| RDMA IP | 172.16.0.11 | 172.16.0.21 |
| GID | `::ffff:172.16.0.11` | `::ffff:172.16.0.21` |
| QPN | 101 | 201 |

NCCL 源码中的逻辑简化后大致如下：

```c
qpAttr.qp_state    = IBV_QPS_RTR;
qpAttr.dest_qp_num = remoteQpNum;

if (linkLayer == IBV_LINK_LAYER_ETHERNET) {
    // RoCE
    qpAttr.ah_attr.is_global      = 1;
    qpAttr.ah_attr.grh.dgid       = remoteGid;
    qpAttr.ah_attr.grh.sgid_index = localGidIndex;
} else {
    // InfiniBand 子网内寻址示例
    qpAttr.ah_attr.dlid = remoteLid;
}

ibv_modify_qp(qp, &qpAttr, attrMask);
```

> **一个容易忽略的细节**：`localGidIndex` 是本地 RDMA Port 的 GID 表索引，**不同机器上的 GID Index 不必相同。**

到这里就能理解为什么：

- NCCL 不需要平台告诉它远端 QPN
- NCCL 不需要平台提前建立网卡之间的连接
- NCCL 不需要平台维护 Worker RDMA IP 到 QPN 的映射关系

**这些信息都是通信库根据设备发现和连接协商自行获得的。** 而且 QP 通常可以被后续训练迭代反复使用，**并不是每执行一次 AllReduce 就重新建立一遍**；部分连接也可能在首次使用时按需创建。

## 八、平台需要干预 NCCL 选网卡吗

会遇到选错的情况，尤其是在有多张 RDMA 网卡、多网段、多租户、多个 Rail 的集群中。这时平台可以根据集群网络实际情况，给 NCCL 注入约束配置：

| 环境变量 | 平台控制的内容 |
|---|---|
| `NCCL_SOCKET_IFNAME` | Socket 通信用哪个网络接口 |
| `NCCL_IB_HCA` | 允许 NCCL 使用哪些 RDMA 设备及端口 |
| `NCCL_IB_GID_INDEX` | 特定场景下选择本地 GID |
| `NCCL_IB_ADDR_FAMILY` | RoCE 动态 GID 选择的地址族 |
| `NCCL_IB_ADDR_RANGE` | 限定动态 GID 选择的地址范围 |
| `NCCL_CROSS_NIC` | 是否尽量避免跨 Rail 通信 |
| `NCCL_IB_QPS_PER_CONNECTION` | 每个网络连接使用的 QP 数量配置 |

```bash
# 普通控制面通信
export NCCL_SOCKET_IFNAME='=eth0'

# 允许使用的 RDMA 设备
export NCCL_IB_HCA='=mlx5_0:1,mlx5_1:1'

# 允许 RDMA 传输
export NCCL_IB_DISABLE=0

# 适用于特定 Rail-optimized 网络
export NCCL_CROSS_NIC=0
```

> **注意**：`mlx5_0` 只是本地设备名称，**并不意味着两台机器上的 `mlx5_0` 一定连接同一个 Rail**。
>
> 这正是云平台的价值所在：**你比 NCCL 更清楚整个集群的网络建设方式**，能够给 NCCL 提供合理的设备范围和网络约束。

## 九、LID / GID 标识的到底是什么

准确来说，**LID 和 GID 标识的是 RDMA 网络端点，通常与 RDMA Port 相关联**——而不是简单地标识一张物理网卡，也不是标识一个 Pod。

物理网卡、物理端口、虚拟设备、网络地址、通信连接，其实是五个不同的层次：

| 概念 | 标识粒度 | 示例 |
|---|---|---|
| PCI Device | PCIe 设备或功能 | `0000:81:00.0` |
| RDMA Device / HCA | RDMA 设备实例 | `mlx5_0` |
| RDMA Port | RDMA 设备的端口 | `mlx5_0/1` |
| LID / GID | 网络端点地址 | `0x0011`、`::ffff:10.0.0.11` |
| QPN | RDMA 通信队列 | `101`、`102` |

**它们并不是一一对应的。** 一张物理网卡可以有多个物理 Port，可以虚拟出多个 VF，一个 RDMA Port 也可以有多个 GID。

### RoCEv2：GID 与 IP 的关系

假设物理机上有一张 ConnectX 网卡，通过 SR-IOV 创建两个 VF 分别交给两个训练 Pod：

| 设备 | IP | GID |
|---|---|---|
| PF / `mlx5_0` | 10.0.0.10 | `::ffff:10.0.0.10` |
| VF 0 / `mlx5_1` | 10.0.0.11 | `::ffff:10.0.0.11` |
| VF 1 / `mlx5_2` | 10.0.0.12 | `::ffff:10.0.0.12` |

在 RoCEv2 模式下，IPv4 地址通常以 IPv4-mapped IPv6 的形式表示为 GID。当 CNI 给 VF 对应的网络接口配置 IP 后，**支持该接口的 RDMA 驱动通常会自动维护相应的 GID Table**。

每条 GID Table 记录主要包含 GID Value、GID Type（RoCEv1 或 RoCEv2）、关联的 Network Device。**因此同一个 IP 甚至可能在 GID Table 中出现两次，分别对应 RoCEv1、RoCEv2。**

> ✅ **一个对平台设计的实用结论**：在典型 SR-IOV RoCE 方案中，**你的 AI 平台通常不需要额外实现 GID 分配器**——配置好 VF 和 IP，驱动就会处理相应的 GID。

### 如果不是 SR-IOV，而是 Shared RDMA

情况就不一样了。假设两个 Pod 使用 hostNetwork 共享同一个 RDMA 设备，此时两个 Pod 可以拥有：

- 相同的 HCA
- 相同的 Port
- 相同的 IP
- **相同的 GID**
- 不同的 QP、CQ 和内存保护上下文

所以 **GID 不一定能够区分训练任务，QPN 才是区分普通 RC 通信连接的关键标识之一。**

### InfiniBand 的 LID / GID

IB 与 RoCE 最大的不同是它有自己的网络寻址体系：

- **GUID**：通常是一个 64 位的设备或端口标识
- **LID**：由 Subnet Manager 分配，用于 IB 子网内的报文转发
- **GID**：128 位地址，通常由 64 位子网前缀和 64 位接口标识组成

对于没有虚拟化的 IB 网卡，两个 Port 有各自的 LID 和 GID。此外 **IB 的 LMC 机制允许一个 Port 拥有多个 LID**。

开启 SR-IOV 后要区分具体的 IB 虚拟化模式：

| IB 虚拟化方式 | LID | GID |
|---|---|---|
| 物理 HCA | 端口拥有 LID | 端口拥有 GID 表 |
| Shared Port | PF、VF 可以共享 LID | VF 有自己的虚拟 GID 表 |
| 支持独立 LID 的虚拟化模式 | VF / 虚拟端口可以拥有独立 LID | 可以拥有独立 GID |

传统 IB Shared Port 架构下，不同 VF 共享物理端口的 LID，但拥有自己的虚拟 GID 表、P_Key 表和设备上下文。

### 两种网络的资源管理差异

| 配置项 | RoCEv2 | InfiniBand |
|---|---|---|
| VF 创建 | SR-IOV | SR-IOV |
| 网络地址管理 | IPAM | SM、GUID 管理等 |
| GID 产生 | 驱动根据关联接口 IP 等维护 | IB 端口标识与子网配置 |
| LID 分配 | 不用于 RoCE 转发 | Subnet Manager |
| Pod 必须有 RDMA 网卡 IP | 常见部署需要 | 原生 IB 通信不依赖 IP |
| QP 创建 | 应用运行时 | 应用运行时 |

## 十、平台到底该管什么

### 设备分配数量 ≠ QP 数量

例如配置 Shared RDMA Device Plugin：

```json
{
  "resourceName": "shared_rdma",
  "rdmaHcaMax": 32
}
```

节点上报 `rdma/shared_rdma: 32`。**这里的 32 是插件暴露的逻辑资源额度，并不是网卡只能创建 32 个 QP。**

如果某个 Worker 申请了 1 个共享 RDMA 额度，其中的训练进程仍然可能创建大量 QP、CQ、MR。所以需要区分三个资源维度：

| 资源维度 | 示例 | 管理者 |
|---|---|---|
| 设备分配 | PF、VF、共享 HCA 额度 | Kubernetes / Device Plugin |
| **运行时对象** | QP、CQ、MR、PD | RDMA 驱动 / 通信库 |
| 网络容量 | 带宽、拥塞、QoS | 网卡和交换网络 |

### 一个训练任务会不会把网卡耗尽

**会。** RDMA 网卡的 QP、CQ、MR 等资源容量不是无限的。如果 Job A 持续创建大量 RDMA 对象，可能导致 Job B 无法创建新 QP，**即使 Kubernetes 显示它仍然有共享 RDMA 资源可以申请**。

Linux 提供了 **RDMA cgroup controller** 用于统计和限制 RDMA 资源使用，相关文件一般包括：

```
rdma.max
rdma.current
```

例如限制某个 cgroup 对 `mlx5_0` 的资源使用：

```
mlx5_0 hca_handle=64 hca_object=4096
```

> 这里的数值只是示例。**`hca_object` 是相关 RDMA 对象的聚合资源限制，并不等于精确的独立 QP 数量限制。** 生产环境需要结合内核、驱动、容器运行时和实际训练任务的资源消耗来设计限制策略。

### Job Controller 应不应该管理 QP

**不应该由 Job Controller 直接创建或分配 QP。** 平台应该管理的是**网络能力和资源使用权限**：

| 操作 | AI 平台是否负责 |
|---|---|
| 决定 Job 是否使用 RDMA | ✅ 是 |
| 分配 RDMA 设备资源 | 通过 Kubernetes |
| 分配租户网络 | ✅ 是，或对接网络平台 |
| 配置 RDMA IP / VF | 通过 CNI、IPAM 等 |
| **创建 QP** | ❌ 否，由 NCCL 等通信库负责 |
| **创建 CQ、PD、MR** | ❌ 否，由通信库负责 |
| **交换 QPN、PSN、rkey** | ❌ 否，由通信协议负责 |
| RDMA 资源配额及监控 | ✅ 是 |
| 租户安全隔离 | ✅ 是 |
| 回收运行时 QP | 由进程和驱动负责 |

### 平台 API 该描述什么

```yaml
spec:
  replicas: 4

  resources:
    gpuPerWorker: 8
    rdmaDevicesPerWorker: 8

  network:
    profile: roce-sriov
    fabric: fabric-01
    topology: rail-optimized

  distributed:
    launcher: torchrun
    backend: nccl
    rendezvous:
      backend: c10d
```

至于「Rank 1 到 Rank 9 应该使用哪个 QP、应该通过哪张网卡通信」，**这些不应该作为 Job API 中的静态配置**。

## 十一、Rail：把连线照着通信模式安排

### 为什么要设计 Rail

假设有两台 GPU 服务器，每台 2 张 GPU、2 张 400 Gbps RDMA 网卡，网络采用 Rail-Optimized 架构。

**同 Rail 通信**：

```
Server A / NIC 0
        ↓
Rail 0 Switch
        ↓
Server B / NIC 0
```

**跨 Rail 通信**：

```
Server A / NIC 0
        ↓
Rail 0 Switch
        ↓
Spine Switch
        ↓
Rail 1 Switch
        ↓
Server B / NIC 1
```

同 Rail 只经 1 台交换机、不占用 Spine 链路。**Rail-Optimized 的核心设计目的，就是尽可能减少不必要的跨 Rail 流量**，让不同 Rail 并行工作，降低流量之间的相互干扰。

### 跨 Rail 会发生什么

| 网络架构 | 跨 Rail 的结果 |
|---|---|
| **Rail-Only**，Rail 完全独立 | 无法直接通过网络通信 |
| **Rail-Optimized**，Rail 之间有限带宽互联 | 可以通信，但容易出现性能瓶颈 |
| **全互通、无阻塞网络** | 可以正常通信，性能影响可能较小 |

**情况一：Rail 完全不互通。** 两个 Rail 之间没有网络路径，NIC 0 无法直接向对端 NIC 1 发送 RDMA 数据。这时即使两个 Worker 的普通 Pod IP 能互通、NCCL 也可能通过 TCP 成功交换 QPN 和 GID，但**实际 RDMA 数据无法到达对端**。可能出现：

- 路由或邻居解析失败
- QP 初始化失败
- RDMA 数据发送后收不到 ACK
- RC QP 不断重试，最终超过重试次数
- NCCL AllReduce 卡住或训练任务超时退出

> **甚至可能出现 QP 已经进入 RTS 状态，但实际上无法完成数据传输。** 因为 **QP 进入 RTS 不代表底层网络一定可达。**

**情况二：Rail 之间互通但带宽有限。** 这是更典型的**性能**问题。例如 4 条各自需要 400 Gbps 的通信流同时经过一条 400 Gbps 的跨 Rail 链路：总需求 1600 Gbps，瓶颈容量 400 Gbps，**每条流量平均只能获得原先四分之一的带宽**。

更严重的是，**AI 训练通常是同步通信**——即使其他 Rank 的通信都很快，只要某条关键通信路径很慢，其他 Rank 就可能不得不等待。**局部网络拥塞会扩大为整个训练任务的同步等待**，这也是大模型训练对网络尾延迟特别敏感的原因。

### 跨 Rail 时 QP 会发生什么变化

你可能会认为跨 Rail 时交换机需要重新建立 QP。**实际上不需要。**

```
本地 QP:  QPN 101, HCA mlx5_0, Rail 0
远端 QP:  QPN 201, HCA mlx5_1, Rail 1
```

NCCL 在创建连接时就已确定发送端和接收端的 RDMA 端点。**只要底层网络可达，数据包可以经过多台交换机到达远端 QP。交换机只负责网络转发，不会为你的训练任务创建新的 QP。**

| 对象 | 跨 Rail 时是否改变 |
|---|---|
| 源 QPN / 目的 QPN | **不变** |
| 目标 GID / LID | **不变** |
| PD / MR / rkey | **不变** |
| 网络转发路径 | 可能更长 |
| 通信带宽和延迟 | 可能变差 |

所以**跨 Rail 本质上是网络路径与资源竞争问题，不是通信连接隔离问题**——它不会因为经过不同 Rail 就让两个训练任务的数据串在一起。

### PXN：用节点内带宽换外部跨 Rail

**PXN = PCI × NVLink**，✅ 已核实（来源：NVIDIA 官方技术博客 *Doubling all2all Performance with NCCL 2.12*）：**NCCL 2.12 引入**，用于优化包括 All-to-All 在内的通信场景。

思路是：先在本机通过 NVLink 把数据转移到**与目标端处于同一 Rail** 的 GPU/网卡上，再发出。这样就能利用节点内的 NVLink/NVSwitch 带宽，**减少外部网络的跨 Rail 流量**。

```
直接跨 Rail:   Server A / NIC 0 → Rail 0 SW → Spine → Rail 1 SW → Server B / NIC 1
PXN 优化:      Server A / GPU 0 --NVLink--> GPU 1 --NIC 1--> Rail 1 SW --> Server B / NIC 1
```

官方博客另外提到，PXN 还能让网络层把多个消息聚合（`multireceive`），减少穿过二级 Spine 交换机的流量。

> 所以 **GPU 0 的数据并不一定必须通过 NIC 0 发送**。实际能否使用取决于硬件拓扑和通信库配置。

### NCCL_CROSS_NIC 控制什么

| 参数 | 含义 | 适用场景 |
|---|---|---|
| `NCCL_CROSS_NIC=0` | 尽量要求同一 Ring/Tree 使用对应 NIC | Rail-Optimized，跨 Rail 带宽有限 |
| `NCCL_CROSS_NIC=1` | 允许同一 Ring/Tree 使用不同 NIC | 网络充分互通 |
| `NCCL_CROSS_NIC=2` | 优先对应 NIC，但允许性能更好的其他选择 | **默认值**，通用场景 |

✅ 已核实（来源：NVIDIA 官方 *Performance and Tuning* 文档）：默认值确为 **2**，原文 *"The default value is 2"*。

官方文档特别指出，**即使设置为 `0`，当不同节点上的 Communicator 使用了不同位置的 GPU 时，也仍然可能需要跨 NIC 通信**。因此：

```bash
export NCCL_CROSS_NIC=0
```

**不是一个强制网络隔离开关，也不能保证任意 GPU 分配组合都能正常通信。**

### 这对调度设计的影响

假设有两台 8 卡 GPU 服务器，每张 GPU 附近都有一张 RDMA 网卡，分别连接 Rail 0～7。现在用户申请两个 Worker、每个 Worker 使用 4 张 GPU：

- **Rail 对齐分配**：Node 0 和 Node 1 都各分配 GPU 0～3（Rail 0～3）→ 两个 Worker 共同获得 **4 个对齐的 Rail**，具有良好的同 Rail 直接通信条件
- **随机分配**：可能一方拿 GPU 0～3、另一方拿 GPU 4～7（Rail 4～7）→ 跨 Rail 流量激增

从 Kubernetes 原生资源调度角度看，**两种方案都满足**：

```yaml
resources:
  limits:
    nvidia.com/gpu: 4
    example.com/rdma: 4
```

但从 AI 训练网络角度看，**两种分配方式可能存在巨大的性能差异**。这意味着**你的平台不能永远只把 RDMA 当作一个数字资源**。

### 增加 RDMA 拓扑资源模型

Node Agent 可以上报：

```yaml
node: gpu-node-01

devices:
  - gpu: GPU-UUID-0
    pciAddress: "0000:17:00.0"
    numaNode: 0
    preferredRDMA:
      - device: mlx5_0
        port: 1
        rail: rail-0
        fabric: fabric-01
        bandwidthGbps: 400

  - gpu: GPU-UUID-1
    pciAddress: "0000:31:00.0"
    numaNode: 0
    preferredRDMA:
      - device: mlx5_1
        port: 1
        rail: rail-1
        fabric: fabric-01
        bandwidthGbps: 400
```

（这是自定义的平台资源模型，不是 Kubernetes 原生 API。）

| 字段 | 数据来源 |
|---|---|
| GPU UUID | NVML |
| PCI Address | sysfs / NVML |
| NUMA Node | sysfs |
| GPU-NIC 亲和关系 | PCIe 拓扑 / NVML |
| RDMA Device | RDMA Netlink |
| **Rail ID** | **网络控制器 / 基础设施资产配置** |
| Fabric ID | 网络平台 |
| 网卡速率 | RDMA 驱动 / 网卡信息 |

> ⚠️ **特别注意：Rail ID 一般不能仅凭 GID、LID 或 mlx5 设备名称可靠推断出来。** 你需要从网络基础设施获得实际的拓扑信息。

### 调度策略的三个层次

| 层次 | 解决什么 |
|---|---|
| **第一层：资源数量调度** | GPU 和 RDMA 数量是否满足要求 |
| **第二层：节点内拓扑调度** | GPU 和 RDMA NIC 是否处于较近的 PCIe / NUMA 路径 |
| **第三层：跨节点 Rail 感知调度** | 同一 TrainingJob 的不同 Worker 是否获得**兼容的 Rail 资源** |

第三层就是 **Rail-Aware Scheduling**。

对于整机 8 卡独占训练，这个问题通常比较简单，因为 Worker 可以获得整组训练网卡。**但对于多租户、1 卡、2 卡、4 卡等非整机训练，这个问题就会变得非常重要。**

### RoCEv2 与 IB 跨 Rail 的差别

| 维度 | RoCEv2 | InfiniBand |
|---|---|---|
| 跨 Rail 转发 | 以太网转发或 IP 路由 | IB Fabric 转发 |
| 互通条件 | 路由、VLAN、VRF、ACL 等 | IB 路径、LID/GID、P_Key 等 |
| 拥塞管理 | ECN、CNP、PFC 等 | Credit 流控及拥塞控制 |
| 路径不可达 | QP 初始化或通信失败 | QP 初始化或通信失败 |
| QP 是否重新创建 | 正常跨 Rail 转发**不需要** | 正常跨 Rail 转发**不需要** |

> **RoCEv2 支持 IP 路由并不意味着所有 Rail 天然互通；IB 有 Subnet Manager 也不意味着不同物理 Fabric 天然互通。**

## 十二、动手：观察、验证、读源码

### 观察 RDMA 运行时资源

不需要自己开发 RDMA 程序，也可以观察一个实际训练任务从创建到退出的过程：

```bash
# 查看 RDMA 设备
ibv_devices

# 查看设备属性及硬件支持的资源上限
ibv_devinfo -v

# 查看 RDMA 资源使用汇总
rdma resource show

# 查看所有 QP / 指定网卡的 QP
rdma resource show qp
rdma resource show qp link mlx5_0/1

# 查看 CQ / PD / MR / 设备上下文
rdma resource show cq
rdma resource show pd
rdma resource show mr
rdma resource show ctx
```

这些都是 Linux 提供的 RDMA 资源追踪接口，**具体可见字段与权限、内核和驱动版本有关**。

QP 查询可能看到类似输出：

```
link mlx5_0/1 lqpn 101 rqpn 201
    type RC state RTS pid 18452 comm python
```

其中 `lqpn` 是本地 QPN、`rqpn` 是远端 QPN、`RTS` 表示 QP 处于 Ready To Send 状态，`pid` 是关联进程 ID。

**建议做一次这样的实验**：

| 实验步骤 | 观察内容 |
|---|---|
| 不启动训练任务 | 查看 RDMA 资源基线 |
| 启动 Job A | 观察 QP、CQ、MR 数量增长 |
| 启动 Job B | 观察同一网卡上出现更多 QP |
| 停止 Job A | 观察 A 的运行时资源释放 |
| 保持 Job B 运行 | 验证 B 的通信不受正常资源回收影响 |
| 停止 Job B | 确认资源恢复到基线附近 |

甚至可以进一步开发 RDMA Exporter，通过 RDMA Netlink、sysfs 等接口采集数据，结合宿主机 PID、cgroup、Pod UID，**把运行时资源归属关联到 TrainingJob**。这样平台就不仅能看到某个 Job 分配了几张网卡，还能知道它**实际消耗了多少 RDMA 运行时资源**。

### 观察 NCCL 如何完成这一切

同时在宿主机上观察：

ibdev2netdev

（`show_gids`、`ibdev2netdev` 是否存在取决于安装的驱动及工具包。）

**把 NCCL 日志中的 Rank、网卡名称和宿主机上查询到的 QP 关联起来**，就能完整观察从训练任务初始化到 RDMA 连接创建的过程。

## 收尾

四句话把所有知识串起来：

> **Rank 决定我是谁、和谁一起训练。**
> **NCCL 通信拓扑决定我应该和谁交换数据。**
> **LID / GID 决定数据应该到达哪个 RDMA 网络端点。**
> **QPN 决定到达该端点后，由哪个通信队列处理数据。**

而你的云平台要做的是**保证这些训练进程能够发现彼此，并给它们提供正确、可达、隔离且性能合适的 RDMA 网络资源**。剩下的连接创建工作，由 NCCL 在运行时完成。

**网卡分配给 Pod，只是让 Pod 获得了使用 RDMA 的能力；真正的 RDMA 通信连接，是训练进程启动后，根据训练任务的通信拓扑动态创建出来的。**

最后记住四个不同的调度维度：

| 感知能力 | 解决的问题 |
|---|---|
| **RDMA-Aware** | 节点有没有 RDMA 资源 |
| **NUMA-Aware** | GPU 和网卡距离是否足够近 |
| **Rail-Aware** | 不同 Worker 的网卡能否高效地相互通信 |
| **Fabric-Aware** | 整个训练任务是否处于合适的高速网络域 |

**第一版可以先实现 RDMA-Aware。如果后续要支持 GPU 服务器上的多租户共享和非整机分配，Rail-Aware 很可能就是下一步的重点。**
