技术债整理

一、P0：训练系统的“底层因果链”——这是你最大的债

你现在大概是：

Kubernetes → Job/Pod → GPU → Megatron/FSDP → Timer → Metrics → Straggler

这些东西你都接触过。

但面试官如果继续往下追：

为什么 FSDP 会产生 All-Gather？
为什么某个 rank 会变慢？
NCCL 到底在什么时候阻塞？
GPU utilization 下降到底是计算问题还是通信问题？
一个 iteration 为什么突然从 10s 变成 15s？
是 GPU、CPU、PCIe、NVLink、IB、NCCL 还是数据加载？

你现在的知识链条还没有完全打通。

这就是你最大的技术债。

你需要建立这一条完整链路

你现在的问题不是其中某个点完全不会。

而是：

每一层之间的连接关系还不够深。

这应该是你未来 2～3 个月最重要的补课方向。

PyTorch 当前的分布式训练体系本身就把 DDP、FSDP2、TP、Device Mesh 等放在同一个分布式训练体系里；FSDP 的核心则涉及参数、梯度、optimizer state 的 sharding，以及 forward/backward 前后的 all-gather / reduce-scatter。

二、P0：NCCL + GPU 通信

这是我认为你最值得狠狠补的一块。

因为你现在已经开始往训练 Infra 走了。

你不能停留在：

“NCCL 是 GPU 通信库，AllReduce 用得比较多。”

而应该达到：

“我看到训练卡顿，能够判断它是不是 NCCL communication bound，并进一步定位到 topology / NVLink / PCIe / NIC / IB / RoCE / rank imbalance。”

NCCL 本身就是 topology-aware 的 GPU collective communication library，核心 primitive 包括 AllReduce、AllGather、ReduceScatter 等。

你至少要吃透：

Collective

  • AllReduce
  • AllGather
  • ReduceScatter
  • Broadcast
  • AllToAll

通信算法

  • Ring
  • Tree
  • Hierarchical communication

GPU topology

为什么 PCIe topology 不合理，会让 NCCL 性能掉下来？

NVIDIA 文档明确指出 NCCL 会依赖 /sys 发现 GPU/NIC 的 PCI topology，容器/虚拟机中的 topology 暴露异常可能直接造成次优性能；GPU Direct、/dev/shm、网络接口选择等也都可能成为通信问题来源。

这一块你学深了，面试深度会明显上一个台阶。

这就是 Infra 工程师真正应该掌握的 trade-off。

PyTorch 文档对 FSDP 的定义就是参数分片，并明确描述了 FULL_SHARD 下 forward/backward 周围的 all-gather、reduce-scatter 以及 optimizer state sharding。
