Kubernetes 控制器与调度器源码解剖：从控制循环到自研调度框架

Kubernetes 有两个"看起来不难、写起来全是坑"的地方：控制器的调谐循环，和调度器的插件框架。

前者难在并发——你面对的是一个最终一致的分布式缓存，写操作和缓存可见性之间有延迟，稍不留神就会重复创建 Pod；后者难在契约——十几个扩展点、几十个插件、三种队列状态，要理解"为什么这个 Pod 现在不能被调度"得同时看懂队列、缓存和抢占。

本文的读法是从基础设施往上层走：先看 client-go 那套事件流水线（Reflector → DeltaFIFO → Indexer → Workqueue），再用 Deployment 和 ReplicaSet 两个内置控制器把控制循环串起来；然后拆 kube-scheduler 的调度周期与框架契约；最后落到自研调度器 Sky-Scheduler——看它在 kube-scheduler 的框架之外，为什么选择了另一套 Session / Action / Statement 模型。

代码基线：Kubernetes v1.32.0-alpha.0（commit 1bbe775d5ff，master，2024-09-29）；自研调度器 Sky-Scheduler（约 3 万行 Go，下文源码路径均相对其仓库根）。

前置阅读：Kubernetes Informer 机制详解 讲的是概念层，本文补的是源码层；自研调度器的设计细节（Quota 两级调度、RDMA 拓扑、Spot GPU）见 Sky-Scheduler：面向 AI 训练的拓扑感知与 Quota 两级调度器，本文不重复，只做与 kube-scheduler 的架构对照。

一、控制循环：一个反直觉的起点

先纠正一个常见的理解偏差：控制器并不"监听事件"。

事件确实会来（informer 的 AddFunc/UpdateFunc），但回调里做的事情通常只有一件——把对象的 key 塞进一个队列：

真正的业务逻辑在 worker 里，它拿到的是一个 key，然后回缓存里重新读当前状态，再决定做什么：

这个设计有三层含义：

  1. 事件只是"提示"，状态才是真相。事件可能丢失、可能重复、可能乱序，但 syncHandler 每次都从缓存读最新状态，所以幂等。
  2. 队列做了合并去重。同一个 Deployment 在 1 秒内被改了 100 次，队列里只有 1 个 key，控制循环只跑一次——这是 K8s 能扛住大规模抖动的关键。
  3. “调谐”（reconcile）意味着双向。不是"收到创建事件就创建"，而是"把实际状态推向期望状态"，所以它既能处理"该有 Pod 但没有"，也能处理"不该有 Pod 却有了"。

标准控制器的骨架是一条带反馈的闭环——写回 API Server 的操作会产生新的 watch 事件，重新流回 Reflector：

下面把这条流水线逐段拆开。

二、事件是怎么进来的

2.1 Reflector：Run 是退避外壳，ListAndWatch 是内核

Reflector 只干两件事：List 拿全量，Watch 拿增量。

Run 本身不含业务逻辑，它是个退避重试外壳：ListAndWatch 出错返回，就按 backoffManager 睡一会儿再来一遍。注意 v1.32 里已经没有 ListAndWatchWithContext 了（老版本有，后来被移除）。

2.2 DeltaFIFO：队列里存的是"变化"而不是"对象"

这是 client-go 里最容易被误解的一个数据结构。它不存对象，存的是同一对象上的一串变化：

为什么要存"变化序列"而不是"最新对象"？因为下游的 processDeltas 需要按顺序重放才能得到正确的回调语义。如果只存最新对象，Added 后面紧跟 Deleted 的场景就会被压缩成"一个不存在的对象"，回调就发不出来了。

队列本身还做了两层优化：

  • 同 key 合并（delta_fifo.go:400 dedupDeltas / :439 queueActionLocked）：连续的同类型 delta 会被合并，避免队列膨胀。
  • Delete 的短路（delta_fifo.go:337-356）：如果被删对象既不在 items 也不在 knownObjects 里，直接忽略——这个对象控制器从来没见过，删了也没人在意。

Replace 是另一个关键路径（delta_fifo.go:636-715），对应"List 拿回全量"的场景。它做三件事：对 list 中每项发 Sync/Replaced；对本地有、新 list 没有的 key 发 Deleted（用 DeletedFinalStateUnknown 包一层，因为对象已经拿不到了，只能给个 key）；如果配了 knownObjects，对缓存里有但 list 里没有的也发 Deleted。

processorListener 内部还有一个环形缓冲区（shared_informer.go:869-905 的 pendingNotifications buffer.RingGrowing）：如果 handler 处理太慢，事件会先落进 ring buffer 而不是阻塞分发。这是个典型的用内存换吞吐的取舍——代价是慢消费者会吃掉内存，所以 initialBufferSize = 1024 起，能涨但不会无限涨。

HasSynced 有两级语义，这点经常被搞混：

  • sharedIndexInformer.HasSynced（:517-525）：委托给 DeltaFIFO，表示至少完成过一次全量同步。
  • processorListener.HasSynced（:909-911）：基于 syncTracker，要求源 informer 已同步 且 本 listener 已消费完初始 Add 事件。

区别的意义在于：如果你在 informer 启动之后才注册 handler，AddEventHandlerWithResyncPeriod（:581-636）会持 blockDeltas 锁，把 indexer 里现有的对象合成一批 isInInitialList: true 的 Add 事件喂给这个新 listener。这样新 handler 的 HasSynced 就不会被误判成"已经同步完了"，控制器也就不会在没看到存量对象的情况下开始工作。

WaitForCacheSync 的实现朴素到有点意外（:327-342）：每 100ms 轮询一次所有 InformerSynced（syncedPollPeriod = 100ms）。没有 channel、没有条件变量，就是轮询。

五、Expectations：分布式系统里最容易被忽略的一处补丁

5.1 问题是什么

控制器通过 informer 缓存读状态，但写操作到缓存可见之间有延迟。上下对比就能看出 expectations 补的是哪个洞：

5.2 实现

两个关键点：

其一，超时是必须的。isExpired（:216-218）判断 RealClock.Since(exp.timestamp) > ExpectationsTimeout，而 ExpectationsTimeout = 5 * time.Minute（:70）。

为什么必须有超时？因为 expectations 是乐观的：如果它期待 3 个 Pod 创建事件，但其中一个创建请求失败了（配额不足、webhook 拒绝），事件永远不来，计数永远减不到 0，控制器就会永久卡死。5 分钟超时是"宁可重复一次操作，也不能永远不工作"的兜底。这也解释了为什么控制器逻辑必须幂等——超时兜底意味着重复执行是设计内的行为。

7.3 并发模型

Filter 和 Score 对节点的遍历是并行的，但并行度不是拍脑袋定的：

分块大小取 √n 和 n/16 的较小值。1000 个节点时：√1000 ≈ 31，1000/16 = 62，取 31 → 分 33 块。100 个节点时：√100 = 10，100/16 = 6，取 6 → 分 17 块。

这是标准的蓄水池采样（reservoir sampling），在 O(N) 内从所有最高分节点中等概率挑一个。

为什么不是"取第一个最高分"？因为如果所有节点同分（比如一个完全空闲的同构集群），取第一个会让所有 Pod 都挤到同一个节点上，直到它不再是最高分——这是典型的热点问题。随机化把负载摊开了。

十一、从 kube-scheduler 到自研：什么时候原生不够

kube-scheduler 的设计目标很明确：把单个 Pod 放到最合适的节点上，延迟有界。这个目标下有几个它天然不擅长的事：

需求 kube-scheduler 的处境
Gang 调度（全有或全无） 单 Pod 贪心，先调度成功的一半会占着资源等另一半，可能死锁

其二，失败可整体回滚。 如果 Job 的某个 task 放不下，Discard 会把之前所有 task 的操作逆序撤销，Job 回到干净状态，下个周期重来。这解决了批调度里最烦人的部分成功问题：不会出现"一个 gang 的 3 个 task 调度成功、2 个失败，成功的那 3 个占着资源干等"。

其三，卷绑定被拉进了同一个事务。 statement.go:441-454 在 Allocate 里同步做 GetPodVolumes → AllocateVolumes，失败就 RevertVolumes。对比 kube-scheduler 的 VolumeBinding 插件需要靠 Reserve/Unreserve 两个扩展点来保证可回滚性，这里因为有了事务栈，可以直接同步做——框架能力决定了插件能有多简单。

11.4 Action 流水

Action 的顺序不是硬编码在 Go 里，而是在默认配置 YAML 中（pkg/scheduler/utils.go:14-59）：

reclaim 和 backfill 的分工很有意思，两者服务完全不同的队列：

  • reclaim：服务在线/配额队列。走"驱逐低优 task + Pipeline 预占节点"，是抢占路径（reclaim/preempt.go:72 的 stmt.Evict，:84-88 的 stmt.Pipeline）。
  • backfill：只服务 Spot 队列，直接在节点上找空隙 stmt.Allocate（backfill.go:235），不驱逐、不改配额绑定。

把"抢占"和"填缝"拆成两个 action 的好处是策略可以分别配置权重，坏处是要多维护一条流水线。

11.5 插件参数的组合：表达式引擎

kube-scheduler 里，多个 Score 插件的分数是加权求和（framework.go:1177），这个组合方式是写死的。

Sky-Scheduler 把它做成了可配置的表达式（pkg/scheduler/expr/）：

session_plugin.go:55-63 的 DefaultExpressions 把插件名拼成表达式串，比如 JobReady 默认是 OpAnd（所有插件都说 ready 才 ready），JobPipelined 默认是 OpMin（取最小值），NOrder 默认是 OpSum（分数求和）。

这是"不改代码就能调策略"的实现方式：想让某个插件在 JobReady 判定里有一票否决权，把 and 换成 firstNotPass 就行。对比 kube-scheduler 需要重新编译插件，这是自研框架能拿到的额外灵活度。

11.6 拓扑插件：这个项目最值得看的部分

pkg/scheduler/plugins/topology/ 和它的 algos/ 子目录，是 Sky-Scheduler 相对 Volcano 的核心增量。

拓扑数据的来源是独立的 discovery 进程：

api/topology.go:39-45 生成拓扑 key 的优先级是：annotation → node label zone → 由交换机名生成。nodetopology.go:84-104 的 genRDMAZoneName 取 IB（优先）或 RoCE 的所有 SwitchName，排序后 md5 作为 zone 名——zone 就是"挂在同一组交换机下的节点集合"。

algos/ 里有三种算法实现：

算法 文件 思路
continuity algos/continuity.go 节点索引连续（delta==1）的切分为一个 zone，fix() 在 :70-103
rdma algos/namedzone.go 按 help.ZoneName 分组，同 zone 同名才算有效（ValidateZone :186-201）

选择算法的接口是统一的 TopologySchedulingAlgo（algos/base.go:20-28）：Init / PredicateForJob / PredicateForTask / AntiAffinityScore / Allocate / DeAllocate / ValidateZone。

IsZoneMember（factory.go:77-79）的判定条件是：节点 ready、无 quota 占用、无 taint——即"这个节点干净且可用"。AntiAffinityScore 则实现打散：namedzone.go:157-165 用的是 1/zone.Len()，zone 越大分越低，鼓励把任务铺开。

11.7 可观测性：三个 HTTP 服务

自研调度器相比 kube-scheduler 的一个明显优势是诊断能力（pkg/scheduler/service/）：

端点 用途

11.8 一个值得注意的工程细节：依赖版本错配

看 go.mod 会发现版本并不统一：

原因是 pkg/kubernetes/volume/scheduling/ 这套卷调度代码是从上游 VolumeBinding 插件整体搬运改写的（volume_binding.go:1-15 保留了 Apache 头），它依赖 k8s.io/kubernetes 里 1.28 版本的 scheduler framework API。主流程用 client-go 0.32，搬运来的代码用 1.28 的框架——两套 k8s 依赖并存。

这是"fork 上游代码"这种做法的典型代价：改起来快，但从此背上了一个版本升级的包袱。值不值，取决于这段代码的定制程度——这里它被改造成了 VolumeBinder 接口（cache/default.go:156-208），嵌进 Statement 事务，定制程度已经不低。

十二、两种调度模型对照

把 kube-scheduler 和 Sky-Scheduler 放在一起看：

维度 kube-scheduler Sky-Scheduler
调度单位 Pod Job（PodGroup）/ Task
触发 事件驱动，Pod 入队即调度 周期驱动，默认 1s 全量重扫
主循环 wait.UntilWithContext(ScheduleOne, 0)，单 goroutine wait.Until(runOnce, 1s)，单 goroutine
绑定 异步 goroutine（bindingCycle） 异步（cache.Bind 里 go Binder.Bind）
队列 activeQ / backoffQ / unschedulablePods 三级 无 Pod 队列；JobQueue 是业务语义的 FIFO

一句话总结差异：kube-scheduler 优化的是"单个 Pod 的调度延迟"，Sky-Scheduler 优化的是"一批任务的整体调度质量"。前者的敌人是节点数（所以有采样、有并行、有 assume），后者的敌人是约束的组合爆炸（所以有事务、有配额层、有拓扑算法）。目标函数不同，架构就必然不同。

十三、总结

回到开头说的两个难点。

控制器的难点在并发，而 K8s 的解法可以概括成三句话：

  1. 事件只用来提示，状态才是真相——所以回调里只做 queue.Add(key)，逻辑在 worker 里重读状态。
  2. 写操作要记账，账要能超时——expectations 保证不会因缓存延迟而重复操作，5 分钟超时保证不会因事件丢失而永久卡死。
  3. 批量操作要限速和慢启动——BurstReplicas=500 和 slowStartBatch 的 1→2→4 是同一类保护。

调度器的难点在契约，而 kube-scheduler 的解法是用扩展点把"策略"和"机制"彻底分开：

  • 框架只负责什么时候调用谁（PreFilter → Filter → PostFilter → Score → Reserve → Permit → PreBind → Bind），插件只负责单个判断。
  • Unschedulable vs UnschedulableAndUnresolvable 的分级、QueueingHint 的按需唤醒、percentageOfNodesToScore 的采样——都是在用有界延迟换近似最优。
  • Assume + cleanupAssumedPods 是这个取舍最赤裸的表达：先假定成功，出错再收拾。

而自研调度器的价值，恰恰在于它展示了当目标函数变了，框架该怎么重写：把调度单位从 Pod 提到 Job，把状态从 CycleState 提到 Session，把直接改缓存换成 Statement 事务。kube-scheduler 的框架很优雅，但它的优雅是为"单 Pod、低延迟"这个目标服务的；换一个目标，优雅的地方就变成了束缚。

读源码的收益，大概就在这一层——不是记住某个函数在哪一行，而是理解某个设计在为什么样的约束服务。
