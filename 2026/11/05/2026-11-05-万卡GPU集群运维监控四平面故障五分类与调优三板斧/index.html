万卡 GPU 集群运维：监控四平面、故障五分类与调优三板斧

发表于2026-11-05|更新于2026-11-05|AI Infra
|浏览量:

一句话结论：把 RoCEv2 网络配成无损只是让集群「能跑起来」，真正吃掉算力的在后面——几万张卡在几个月里不停地出故障、掉速、Hang 住，而你要在没有用户配合、看不到业务代码的情况下，判断这一次的锅是硬件、是网络还是调度。

这篇给一套可执行的方法：四个监控平面分工排查、五类故障定性定位、RoCE 三种典型病的判据、三板斧的调优顺序，最后落一份巡检清单。

开场先看一个真实场景。 某集群上一个 2048 卡预训练任务，MFU 长期在 38% 上下波动。团队查了两周网络：PFC 计数正常、ECN 标记率正常、交换机上零丢包、ib_write_bw 端到端带宽也达标。

最后在 DCGM 的 SM Clock 指标上发现问题——256 台机器里有一台的 8 张卡，SM 时钟长期跑在 1.1GHz，其他机器都是 1.9GHz。这台机器是慢节点，它在每一个 AllReduce 里拖后腿，整条 ring 都要等它。换掉之后 MFU 回到 45%，而且不再波动。

这类问题在交换机上永远查不到，因为网络侧所有计数都是干净的。

边界说明：文中命令以 NVIDIA DCGM 与 nvidia-smi、Mellanox/NVIDIA OFED、Prometheus 体系为例。字段编号、默认值、阈值随驱动、固件、NCCL 与交换机版本变化，请以对应版本的官方文档与现网实测为准，先在测试环境验证。

一、先立监控：四个平面

监控做不好的根因通常不是「指标不够多」，而是「层次没分开」。GPU 集群的指标天然分四个平面：任务、GPU、网络、链路。四个平面各管一件事，出问题时从上往下逐层排除，能省掉大量反复。

平面 回答什么问题 核心指标 主要采集源
任务 任务跑得快不快、有没有卡住 MFU、samples/sec、单 step 耗时、loss 曲线、日志最后更新时间 用户日志锚点、K8s Event、Prometheus
GPU 卡有没有在用、有没有坏 Utilization、SM Active、SM Occupancy、Tensor Active、SM Clock、显存占用、Xid、NVLink 带宽 DCGM / dcgm-exporter、nvidia-smi、dmesg
网络 无损机制有没有生效 PFC 暂停帧计数、ECN 标记率、队列深度、headroom 余量、CNP Slow Restart、RDMA 重传 交换机计数、ethtool -S、rdma stat
链路 物理层是不是干净的 CRC 错包、收发光功率、BER、端口翻转次数、LLDP 邻居、卡间拓扑 ethtool -S/-m、display interface、nvidia-smi topo -m

1.1 任务平面：不看业务代码也能判断快慢

任务平面是大盘的第一行，它要给三个数：

  • MFU —— 唯一能把硬件、框架、并行策略的差异都归一化掉的可比指标，跨集群、跨模型都能横向比；
  • 单 step 耗时 —— 方差比均值更有意义，方差大说明有 Straggler；
  • 日志最后更新时间 —— 最便宜的 Hang 检测手段，任务日志超过 5 分钟没有新输出就告警，比任何探针都早发现 NCCL Hang。

第二个抓手是日志锚点。训练代码里在初始化、每个 step、每个 epoch 边界打印可识别的标记，NCCL 侧会自然产生 NCCL INFO Bootstrap 和 NCCL INFO xxx Init COMPLETE 这类行。这些锚点的价值在于对齐：把 256 个 Worker 的 Init COMPLETE 时间戳拉到一张表上，谁慢了 3 分钟一眼就能看出来——而这 3 分钟在指标图上是看不出来的，因为初始化阶段的 GPU 利用率本来就接近 0。

1.2 GPU 平面：四个利用率指标的读法

DCGM 里有四个容易被当成一回事、其实含义完全不同的利用率指标：

指标 含义
DCGM_FI_PROF_GR_ENGINE_ACTIVE 一个周期内 Graphics/Compute 引擎处于 Active 的时间占比
DCGM_FI_PROF_SM_ACTIVE 至少一个 Warp 在 SM 上 Active 的时间占比（对所有 SM 取平均）
DCGM_FI_PROF_SM_OCCUPANCY 驻留 Warp 数与该 SM 最大可驻留 Warp 数的比
DCGM_FI_PROF_PIPE_TENSOR_ACTIVE Tensor Core 处于 Active 的时间占比

⚠️ 一处命令要改：原稿给的采集命令是 dcgmi dmon -e 1001,1002,1003,1005。按 DCGM 源码 dcgm_fields.h 的字段表，1005 是 DCGM_FI_PROF_DRAM_ACTIVE（DRAM Active），Tensor Active 是 1004：

field ID 字段
1001 DCGM_FI_PROF_GR_ENGINE_ACTIVE
1002 DCGM_FI_PROF_SM_ACTIVE
1003 DCGM_FI_PROF_SM_OCCUPANCY
1004 DCGM_FI_PROF_PIPE_TENSOR_ACTIVE
1005 DCGM_FI_PROF_DRAM_ACTIVE

正确命令是 dcgmi dmon -e 1001,1002,1003,1004。

这四个数的组合，能在完全不看业务代码的前提下给出性能判断：

Utilization SM Active Tensor Active 判断 下一步
低 低 低 数据加载或 CPU 侧预处理占比过高，算力没喂饱 看 DataLoader、num_workers、/dev/shm、CPU 占用
高 低 低 通信占比高，GPU 在等数据 看 NVLink 与网卡吞吐、AllReduce 耗时
接近 100% 接近 0 接近 0 通信阻塞（NCCL Hang 或等待） 看 NCCL 日志、找掉队 Rank
高 高 低 模型中非矩阵计算占比过高 看算子构成，不是网络问题
高 高 超过 50% 算力已接近吃满 停止优化，接受这个数

Util 打到 100% 而 SM Active 接近 0，是 NCCL 阻塞的特征指纹。 这个组合看起来反直觉——GPU 明明 100% 忙碌，为什么是「卡住了」？

原因是 Utilization 统计的是引擎有没有在被占用，而 NCCL 在等待对端时确实在轮询式地占着引擎；SM Active 看的是有没有真正在算东西，等待期几乎没有 Warp 在执行。

判断方法很直接：把这张卡的指标和其他卡对比——如果全集群的卡都是这个形状，就是集体阻塞；如果只有一两张，那两张就是掉队节点。

1.3 采样间隔：一笔必须算的账

DCGM 的采集间隔与训练事件的时间尺度严重不匹配：一个训练 step 通常在几百毫秒到几秒之间，一次 AllReduce 在 8 卡 200Gbps 上只有百微秒到毫秒量级——十秒一个采样点对毫秒级事件是瞎的。

⚠️ 更正一处数字：原稿写「DCGM 常见的采集间隔是 10 秒」。dcgm-exporter 的 collect-interval 默认值是 30000 ms（30 秒），不是 10 秒。这个更正让「采样对毫秒级事件是瞎的」这个论点更强了，不是更弱。

结论有两条：

  1. 计数器类指标必须按增量看——Xid、PFC 帧、ECN 标记、CNP Slow Restart、CRC 都用 increase() 或 rate() 而不是瞬时值，瞬时值会把一次突发抹平；
  2. 事件型信息必须靠日志补——监控采不到的那部分只能靠锚点和 dmesg。

还有一类典型盲区是 GPU OOM：显存瞬间冲顶又释放，30 秒的采样点可能完全采不到，只能从用户日志里的 OutOfMemoryError: CUDA out of memory 拿到。

1.4 GPU 平面的核心指标与命令

指标 含义 采集命令 关注点
Utilization / SM Active / Occupancy / Tensor Active 四个维度的忙闲程度 dcgmi dmon -e 1001,1002,1003,1004 组合判断，见上表
SM Clock 卡的实际运行频率 nvidia-smi -q -d CLOCK 与基线比，掉到 1/2 即严重降频
显存占用 显存水位与碎片 nvidia-smi -q -d MEMORY OOM 风险与抢占判断
Xid Error 硬件/驱动层错误码 dmesg -T | grep -i xid、DCGM_FI_DEV_XID_ERRORS 见第二节
NVLink 吞吐 机内卡间带宽 dcgm-exporter 的 NVLink 指标 判断 TP 是否真的在机内跑
卡间拓扑 NVLink/PCIe 连接关系 nvidia-smi topo -m 交付后与变更前后各存一份

SM Clock 是最容易被漏掉的一个，而它恰恰是慢节点的主要信号——开头那个案例就是靠它定位的。

1.5 网络平面：三个数必须常驻大盘

网络平面只需要三个数常驻大盘，其余按需下钻。它们分别回答无损网络的三个独立问题：

  • PFC 暂停帧计数 → 有没有发生反压；
  • ECN 标记率 → 拥塞控制有没有提前介入；
  • headroom 余量 → 反压发出去到生效之前，buffer 还撑不撑得住。

只看其中一个会得出完全错误的结论：

  • PFC 计数在涨的同时仍有丢包 → headroom 不足；
  • ECN 标记一直在涨但吞吐不降 → CNP 通道断了；
  • PFC 计数长期为 0 而吞吐上不去 → 流量压根没进无损队列。

第四个建议常驻的是 CNP Slow Restart（RoCE 场景一般对应 roce_slow_restart_cnps）。这个计数涨，说明发送端频繁进入慢启动重来，是链路质量差、降速或网络侧有隐性丢包的强信号——它的价值在于能把「网络看着正常但任务慢」这种最难受的情况量化出来。

1.6 链路平面：物理层的四个证据

链路平面经常被跳过，但它决定了上面三层的数据可不可信。四个证据必须能拿到：CRC 错包、模块收发光功率、BER/前向纠错情况、端口翻转次数。

CRC 错包是最硬的那一个。 一条健康链路的 CRC 错包计数应该长期为 0，出现即说明物理层已经出问题，而且是「无声」的——交换机不会把它算进拥塞丢弃，上层只会看到重传变多。

光模块功率靠 ethtool -m 读 DDM 信息。接收光功率接近或低于模块标称的接收灵敏度，误码就是必然的——这类问题在夏天高温和光模块老化时集中爆发。

端口翻转（flapping）要看事件而不是看瞬时状态。短到几秒的 down/up 在状态图上根本看不出来，但足以触发 NCCL 侧 port error / port active 的重连。

第四个证据是拓扑校验：交付后和每次网络变更后都要各存一份基线——nvidia-smi topo -m 校验卡间是不是完整的 NV8、lldp 校验每张网卡接到了预期编号的交换机端口。这两份基线是后面所有「拓扑变了」类问题的唯一对照物。

二、故障五类与定位路径

大规模集群的故障可以收敛成五类：硬件异常、通信故障、性能瓶颈、任务调度与资源利用、OOM。

分类的意义在于先定性再动手——五类的定位成本差一个数量级，定错方向就是两周。

2.1 第一类：硬件异常

硬件异常的主要信号是 Xid Error——NVIDIA 驱动在运行中遇到硬件或驱动层错误时打出的错误码，可以通过 DCGM 的 DCGM_FI_DEV_XID_ERRORS 拿到最近一次错误码，也可以直接在 dmesg 里抓。

Xid 含义 节点侧日志特征 用户侧表现 处置
31 GPU memory page fault MMU Fault、FAULT_PDE ACCESS_TYPE_VIRT_READ an illegal memory access was encountered 绝大多数是业务代码问题；极少数是硬件或驱动
48 Double Bit ECC Error（不可纠正） An uncorrectable double bit error uncorrectable ECC error encountered 硬件问题，终止进程并重置 GPU，反复出现即报修
62 Internal micro-controller halt 引擎/微控制器相关报错 — 复位 GPU；频繁出现需报修
63 GPU memory remapping event（行重映射） Row Remapper 相关 — 信息类事件，官方处置为 IGNORE
74 NVLink Error NVLink 链路报错 通信异常、AllReduce 失败 检查 NVLink 与 NVSwitch，常需整机维护
79 GPU has fallen off the bus（掉卡） GPU has fallen off the bus No CUDA GPUs are available 严重硬件故障，停卡报修
94 Contained memory error — 受影响应用需重启 错误被隔离在单个应用内
119 GSP RPC Timeout Timeout after 6s of waiting for RPC response from GPUx GSP! unspecified launch failure 复位；反复出现按 GPU Debug Guidelines 处理
120 GSP Error errorString CTX SWITCH TIMEOUT 同上 同上
109 Context Switch Timeout Error — — 复位 GPU / 联系支持

⚠️ 三处更正（原稿的 Xid 表有分类错误）：

  1. Xid 63 不是「不可纠正 ECC 双位翻转」。 官方定义是 INFOROM_DRAM_RETIREMENT_EVENT / “GPU memory remapping event”——它是行重映射/内存重映射事件，属于信息类，官方处置是 IGNORE。原稿把 63 同时列在「不可纠正 ECC」和「GPU 内部错误」两行里，两边都不准确。
  2. Xid 94 不是 DBE。 官方是 ROBUST_CHANNEL_CONTAINED_ERROR / “Contained memory error”——错误被隔离在单个应用内，处置 RESTART_APP。它可能与 ECC 处理相关，但不等同于双位翻转。
  3. Xid 109 不是 GSP 错误。 官方是 ROBUST_CHANNEL_CTXSW_TIMEOUT_ERROR / “Context Switch Timeout Error”，与 119（GSP_RPC_TIMEOUT）、120（GSP_ERROR）是三个不同的码。只有 119/120 属于 GSP。

Xid 79 就是掉卡，没有第二种解释。 看到它就走报修流程，不要试图复位重试。

ECC 错误的判断要更谨慎：一次单发的 ECC 可以复位后继续观察，但同一张卡反复报错就应该摘掉——万卡集群里一张反复报错的卡，代价不是这张卡的算力，而是它拖垮的每一次长任务重启。

⚠️ 一条经验判断要标注：原稿写「同一张卡一周内出现两次就应该直接摘掉」。NVIDIA 官方没有这个规则——官方 RMA 判定基于 row-remapping failure flag 与 SRAM UCE 阈值，由 Field Diagnostic 工具裁定（例如「同一 bank 内超过 8 个不可纠正错误行已重映射后再次触发」「累计 512 次重映射」等）。「一周两次」是运维经验，不是官方阈值。

Xid 之外还有三类硬件异常值得单独盯：

PCIe 降速和 GPU 降频都不会中断业务，只让任务变慢——这是它们最危险的地方。

PCIe 降速在日志里的形态是 PCIe 16x Link -> 2x Link，速率可能从 252.048 Gb/s 掉到 31.506 Gb/s；用 lspci 看 PCI 总线配置，异常设备的 LnkSta 与正常设备明显不同，还会带 (downgraded) 标记。

降速的卡不报错、不掉线，只是带宽变成八分之一，而跨机通信本来就只有机内 NVLink 的二十四分之一，再打个对折，这个节点立刻变成慢节点。GPU 降频同理，供电或散热问题会让 SM 时钟从 2GHz 掉到 500MHz，性能直接掉到四分之一。

这类问题的唯一发现手段是基线比对：每台机器的 SM Clock、每张网卡的协商速率都要有基线值和自动比对。

第三类是频繁异常节点。 相比慢节点，故障节点容易定位，但它对集群有效算力的杀伤更大——每一次故障都意味着一次重启和一段从上个 Checkpoint 到现在的算力浪费。

Meta 在论文 Revisiting Reliability in Large-Scale Machine Learning Research Clusters（arXiv:2410.21680，HPCA 2025）里把这类作业失败率显著高于平均水平的节点称为 Lemon 节点，定义是「cause repeating job failures but cannot be identified by existing mechanisms like health checks and repair workflows」。他们报告的收益是：

Our lemon node detection mechanism led to 10% reduction in large job failures (512+ GPUs), from 14% to 4%.

集群生命周期里的故障率通常呈浴缸曲线：早期因为各系统没磨合好、频繁异常节点没被识别出来，故障很密集；中期稳定在恒定水平，故障随机；末期因为器件老化磨损，故障率重新抬头。新集群上线头三个月应该按早期阶段管理，主动做节点筛选，而不是等故障来了才处理。

2.2 第二类：通信故障

通信故障里最高频的是 NCCL Hang 与 Timeout。

⚠️ 一处版本差异要说明：原稿写「默认超时是 30 分钟，日志里表现为 Timeout(ms)=1800000」。这个串来自 PyTorch 的 ProcessGroupNCCL watchdog（不是 NCCL 库本身——NCCL 库没有通用的操作超时环境变量）。

而 PyTorch 的默认值分后端：非 NCCL 后端（gloo）是 30 分钟（1800000 ms），但 NCCL 后端自 PyTorch v2.2.0 起是 10 分钟（600000 ms）。所以看到 Timeout(ms)=1800000 说明用的是旧版 PyTorch、或显式设过 30 分钟、或走的是 gloo。

缩短超时可以更快失败、更快重启，但太短会让一次网络抖动就直接把任务杀掉——这个取舍要按集群的实际抖动频率定。

定位路径按三个方向切：

方向一：通信操作不匹配。 这是最常见的一类——代码里有逻辑分支，导致一部分 Rank 走 AllReduce、另一部分走 AllGather，谁也等不到谁。判断依据在 Watchdog 日志里：

把全部 Worker 的 OpType 和 SeqNum 拉出来对齐，就能看出在哪一步分叉了。

方向二：物理层与链路。 网卡抖动表现为短暂的 Link down / Link up，NCCL 侧对应 port error / port active——如果抖动够短，重试成功后任务会继续；如果网卡彻底不可用，就会走到 Timeout。

方向三：初始化阶段 Hang。 这一类概率低但排查成本极高，常见原因与 nvidia-fabricmanager 有关——Fabric Manager 负责配置 NVSwitch 内存结构、协调 GPU 初始化、监控 NVLink 与 NVSwitch 错误。

典型现象是AllReduce 测试也 Hang，但设 NCCL_ALGO=Ring 就能跑——因为 NCCL 从 2.17 起支持的 NVLink Sharp（NCCL_ALGO=NVLS、NCCL_NVLS_ENABLE 默认值 2 即启用）依赖 Fabric Manager 正常。重启 fabricmanager 通常就能解决。

初始化阶段还有两类不属于 NCCL、但经常被归到「通信故障」里的问题：

  • PyTorch 的 MASTER_PORT 被占用（Address already in use）；
  • torch.distributed.DistStoreError: Socket Timeout——Worker 与 Master 建连默认 300 秒超时（PyTorch Store 的 kDefaultTimeout）。

后者最常见的原因是启动不同步：所有 Worker 在调用 torchrun 之前装依赖、编包，网络差异导致启动时间拉开五分钟以上。解决办法是在调用 torchrun 之前打印一条带 Rank 编号的日志，用时间戳就能判断谁没启动、谁晚了多少。

2.3 第三类：性能瓶颈

性能瓶颈里有三件事要分开：确定性降速（PCIe 降速、GPU 降频）、慢节点、调度导致的降速。

慢节点是大规模训练里最值得投入的一类。 它的表现是同一个任务、同一套配置，多次启动的训练速度差 10% 以上——而这个差距往往超过很多优化方案的收益。

字节在 MegaScale 论文（arXiv:2402.15627）里的量化更具体：

a minor fraction of machines (approximately 0.5%) exhibit substantially slower performance during training … specific hosts took approximately 10% more time to execute the same forward computations compared to other ranks.

论文还指出一个容易被忽略的现象：MFU 会随训练时间逐渐下降（“The MFU for various training tasks gradually declines over time”）——也就是说有些慢节点不是一开始就慢，而是在训练过程中逐渐变慢。

定位慢节点靠两条路：

  1. 用 Prometheus 加 Node Exporter 收集 CPU、GPU、PCIe 带宽指标做横向比对——缺点是差异可能很不显著；
  2. 结合通信时间分布（NCCL 里的 send/recv 耗时）看谁 consistently 落在尾部——后者更灵敏。

周期性降速是另一类隐蔽问题。 表现是任务每隔一段时间掉一次速，怀疑过 DataLoader、怀疑过 Checkpoint、怀疑过节点上的定时任务，全部排除后，最终定位到某个 Rank 里 Python 的垃圾回收持有 GIL，导致这个 Rank 变成 Straggler；任务规模大时，多个 Rank 陆续变成 Straggler，影响被放大。

Megatron-LM 提供了主动 GC 的选项——--manual-gc 与 --manual-gc-interval，官方注释写明了用途：

Manual garbage collection helps to align the timing of the collection across ranks

在固定 step 后让所有 Rank 同时 GC，把各自的 GC 时间对齐到同一时刻，就能把这个抖动压下去。

调度导致的降速：8 卡任务被调度到两台机器上，TP 需要跨机通信，速度直接差一倍。根因是细粒度调度没有做拓扑约束——这在第四节的第三板斧里展开。

2.4 第四类：任务调度与资源利用

集群通常不是专用于单一任务的。Meta 的论文给了一组很说明问题的数据（Observation 7）：

Over 90% of jobs are less than 1 server large, but represent less than 10% of GPU time.

这个「少量大任务 + 大量小任务」的分布决定了调度策略必须双轨：

  • 大任务按节点粒度调度，整节点分配，保证通信效率；
  • 小任务按 GPU 粒度调度，允许多个小任务共享同一节点，避免碎片化。

按 GPU 粒度调度带来的副作用是抢占。如果隔离不彻底，用户强制使用非分配的 GPU 就会影响别人的任务——典型现象是监控里只有一个 GPU 的 SM Active 很高、其他都很低，定位后发现用户改了配置用了 0 号卡，而实际分配的是 7 号卡。

隔离靠 CUDA_VISIBLE_DEVICES 和 NVIDIA_VISIBLE_DEVICES，容器里还可以用 NVIDIA_DRIVER_CAPABILITIES 精细控制可用功能。

2.5 第五类：OOM

OOM 有四个变种，定位入口完全不同：

  • Shared Memory OOM —— 表现是 Bus error: nonexistent physical address，常见于 DataLoader 多进程共享内存不足。容器环境的 /dev/shm 默认偏小是高频触发点（Docker 默认 64MB）。
  • GPU OOM（任务自身） —— PyTorch 会打印详细日志，包含已用显存和尝试分配的量，例如 this process has 79.24GiB memory in use、Tried to allocate 3.38 GiB。
  • GPU OOM（抢占导致） —— 某个 GPU 刚启动就占用明显偏高即可疑。
  • GPU OOM（初始化型） —— 最容易误判的一种：PyTorch 用 lazy init 初始化 cuDNN，显存已经吃满时初始化会失败，抛出 cuDNN error: CUDNN_STATUS_NOT_INITIALIZED——这个报错里完全没有 “out of memory” 字样。
  • NCCL 侧的 OOM —— NCCL WARN CUDA failure 2 'out of memory'。
  • Host OOM —— 比 GPU OOM 好查，dmesg 里通常有明确信息，常见于按 GPU 数量平均切分 Host Memory 之后，Master 进程全量加载或保存 Checkpoint。

显存碎片有一剂便宜的药：PYTORCH_ALLOC_CONF="expandable_segments:True"，对输入 shape 频繁变化（图像尺寸、序列长度）导致频繁分配释放的场景效果明显，代价是可能影响分配性能。

⚠️ 一处变量名要更新：原稿写 PYTORCH_CUDA_ALLOC_CONF。PyTorch 现在的规范名是 PYTORCH_ALLOC_CONF，PYTORCH_CUDA_ALLOC_CONF 是向后兼容别名，仍然可用（没有被删除）——官方文档原话：“PYTORCH_CUDA_ALLOC_CONF is its alias and is provided only for backward compatibility.”

三、RoCE 网络的三个典型病

配好 PFC、ECN、headroom、DSCP 映射之后，还会得三种病。三种病的共同点是：交换机上的总丢包计数可能都是 0，但任务就是慢或者就是挂。

3.1 病一：PFC 风暴

表现：PFC 暂停帧计数暴涨、上行口也被反压、连 SSH 和监控采集都跟着卡、吞吐掉一大截。

定位时先看一件事：接入口的 PFC 计数涨了，上行口有没有跟着涨。

  • 跟着涨 → 反压在逐跳扩散，这才是风暴；
  • 只在接入侧涨、上行侧干净 → 正常的局部反压。

根因集中在三处：

  1. 开了过多的无损优先级 —— PFC 的暂停粒度是优先级，开得越多暂停面越大，一次 GPU 侧的 incast 就能把管理流量一起暂停。行业通识是只给 RoCE 数据优先级开 no-drop，其余全部可丢；
  2. headroom 不足导致反压提前触发，反压又逐跳向上游扩散，最终形成大面积暂停域；
  3. incast 规模本身过大 —— 一次 AllReduce 的 ring 或 tree 阶段，几十上百个发送端会在毫秒级的时间窗里同时往一个接收端打数据，队列深度不是缓慢爬升而是瞬间冲高。

止血顺序：先确认无损优先级是不是只有一个，再确认 headroom 是不是自适应、有没有覆盖当前链路距离，最后确认死锁检测有没有开。极端情况下可以临时把 PFC 关掉保住业务连通性，代价是丢包全部交给上层重传——这只能当临时手段。

一个绝对不能犯的错：CNP 那个优先级绝对不能开 no-drop。CNP 是 ECN 闭环里通知对端降速的信使，它一旦被暂停，闭环就断了。这个错误的隐蔽性在于——你去看 ECN，标记计数在涨；去看 PFC，它也在工作；但吞吐就是上不去，重传计数一直在涨。

3.2 病二：ECN 失灵

ECN 失灵有两种相反的表现，判据也不同。

第一种：门限过高、来不及标记。 等队列涨到门限才开始标记，CNP 走一个 RTT 回到发送端、降速生效，这段时间里队列还在涨，等降速起作用时可能已经丢包了。判据是：压测时吞吐上不去，而 ECN 标记计数几乎不涨，同时队列深度已经很高。

第二种：门限过低、误标记。 门限定得太低，队列刚有点排队就开始标记，发送端无谓降速，吞吐长期上不去。判据是：ECN 标记率很高、吞吐上不去、但 PFC 计数和丢包计数都很干净。

⚠️ 原稿这里有一个数字我要删掉：它写「在 200GE 端口上，如果排队 100KB 就开始触发标记，链路利用率可能长期卡在六成」。这组对应关系找不到一手依据，而且与经典结论相悖——DCTCP 的结论是标记阈值 K 需要大于约 BDP/7 才能保住满吞吐；200GE + 10µs RTT 时 BDP ≈ 250KB、BDP/7 ≈ 36KB，100KB 已经明显大于该值，理论上不该把利用率压到六成。这个「六成」我删了，保留定性的「门限过低会导致无谓降速」。

门限到底该定在哪，取决于一条链路的带宽时延积（BDP）。 取一个具体算法：100GE 端口跨一跳，RTT 约 10 微秒，BDP = 100 Gbps × 10 µs = 125 KB——也就是说 headroom 至少要能吃下这个量级的突发，否则就是「反压发出去了但还是丢包」。200GE 时这个数字翻倍，跨机房长距链路还要再往上加余量。

这就是为什么各家都推动态门限——静态门限无论拍在哪个值，都只是在「误标记」和「来不及」之间取折中，而不同模型、不同并行策略、不同批量下的最优门限还不一样。

第三种失灵：流量压根没进无损队列。 判据最干脆——无损队列的报文计数为 0，而缺省队列在涨。根因来回复现过好几次：交换机接口漏配 trust dscp，或者主机侧没设 ToS（NCCL_IB_TC=106 对应 DSCP 26），报文按缺省优先级 0 进了尽力而为队列。

3.3 病三：无声丢包

第三种病最难受：交换机上看不到任何拥塞丢弃，PFC 和 ECN 计数都干净，端到端带宽测试也达标，但 roce_slow_restart_cnps 在涨、RDMA 重传计数在涨。

这种丢包不发生在队列里，发生在物理链路上。

定位顺序是先易后难：交换机 display interface 看 CRC 错包与对齐错误 → 主机 ethtool -S 看 CRC 与各类错误计数 → ethtool -m 读光模块 DDM 看接收光功率与温度 → 最后看端口翻转事件计数。

一条健康链路的 CRC 应该长期为 0，出现即物理层问题；接收光功率接近或低于模块标称接收灵敏度，误码就是必然。

根因集中在光模块和光纤：模块老化或端面污染、光纤弯曲半径过小、跳线质量差、高温导致功率下降。这类问题在集群运行一年后会明显变多，和浴缸曲线的末期阶段是重合的。

四、调优三板斧

调优的顺序不能乱：先集合通信，再数据加载与存储 IO，最后任务排布。 理由是收益递减的反面——任务排布错了，前两项做到满分也补不回来。

4.1 第一板斧：集合通信调优

第一件事是把主机侧与交换机侧的 DSCP 对齐。 交换机按 DSCP 26 映射本地优先级 3，主机就必须发出 DSCP 26 的报文。

⚠️ 三处参数说明：

  1. NCCL_IB_TC=106 的位运算是对的：106 = 0b01101010，高 6 位 = 26（DSCP 26 / AF31），低 2 位 = 2（ECN）。但要注意 NCCL 官方文档对该变量只写了「Defines the InfiniBand traffic class field」，没有给 106 的位含义——「DSCP 26 → 优先级 3」是交换机侧的映射约定（AF 类标准映射 AF11→1、AF21→2、AF31→3），不是 NCCL 官方口径。
  2. NCCL_IB_TIMEOUT=22 合法：超时公式 4.096 µs × 2^timeout，取值范围 0—31，官方默认是 20（2.23 起；2.14—2.23 是 18）。22 意味着更长超时。总等待时间 = NCCL_IB_TIMEOUT × NCCL_IB_RETRY_CNT（默认 20×7 ≈ 30 秒）。
  3. NCCL_IB_GID_INDEX 不该写死：官方明确要求「See the InfiniBand show_gids command in order to set this value」，而且NCCL 2.21 起在不设置该变量时会自动选 GID。上面写 3 只是示意，实际必须按本机 show_gids 输出选 RoCEv2 那一行。

第二件事是拓扑感知。 NCCL 会读系统的 PCI 与 NUMA 信息构建拓扑，nvidia-smi topo -m 的输出就是它的输入之一：GPU 之间是 NV8 表示 8 条 NVLink；GPU 与网卡之间是 PXB（只跨 PCIe 交换芯片）、NODE（跨 PCIe 主机桥）、SYS（还要跨 NUMA）三档。

这个输出必须在交付验收时存档，之后每次硬件变更重新采集比对——一张卡被换到另一个槽位，拓扑就从 PXB 变成 SYS，性能掉一截而没有任何报错。

第三件事是版本。 集群里 NCCL 版本不统一，是很多「同一套配置在不同机器上表现不同」的根源。

⚠️ 原稿在这里举了一个具体 bug：「NCCL 2.20.x 有 Message truncated : received 1024 bytes instead of 256 的已知问题，2.21 以上已修复」。这个具体报错串与版本对应关系找不到官方出处——可查到的相关官方记录是 NCCL 2.3.7 的 release note（“Fixed issue causing ‘WARN : Message truncated’ errors”），版本和字节数都对不上。版本统一这个建议本身是对的，但具体案例我删掉了。

验收工具两件套：ib_write_bw 验点对点带宽与抖动；all_reduce_perf -b 8M -e 4G -f 2 -g 1 验集合通信。后者比前者更能反映真实训练，因为它把 incast 形态带进来了。

4.2 第二板斧：数据加载与存储 IO

这一板斧的全部内容可以概括成一句话：存储流量不能和训练流量抢同一张网。

典型 8 卡 A100 主机的内部拓扑是 2-2-4-6-8-8：2 片 CPU（NUMA）、2 张存储网卡、4 个 PCIe Gen4 交换芯片、6 个 NVSwitch、8 个 GPU、8 个 GPU 专属网卡。

  • 存储网卡直连 CPU，承担读训练数据、写 Checkpoint、SSH 管理和监控采集；
  • GPU 专属网卡通过 PCIe 交换芯片连到各自的 GPU，专跑跨机集合通信。

这是两套物理上分开的通路，对应两张网络。

顺带纠正一个常见记混：HGX A100 的 8 卡基板是 6 颗 NVSwitch（官方博客原文 “eight A100 Tensor Core GPUs and six NVSwitch nodes”），不是 4 颗——4 颗是 H100/H800 的 HGX 机型。

混在一起的后果非常具体：Checkpoint 写入的突发流量打满 Leaf 上行 → 触发 PFC 反压 → 反压沿着无损优先级一路传到 GPU 训练流量上 → 整网降速。而根因看起来只是「有人存了个模型」。

Checkpoint 的账要算清楚，它决定了存储网要多大。以 70B 参数 bf16 训练为例：

项 计算 大小
参数（bf16，2 字节/参数） 70e9 × 2 140 GB
Adam 优化器状态（12 字节/参数） 70e9 × 12 840 GB
合计 ≈ 1 TB

12 字节/参数的构成是 fp32 master weight 4 + 一阶矩 m 4 + 二阶矩 v 4——这正是 ZeRO 论文里 K = 12 的口径。

不分片的话：单节点写 1TB 到存储，按存储网 2×100Gbps 折算 25GB/s 计算要 40 秒——这 40 秒里训练要么停，要么被打满的上行反压拖慢。

做了 ZeRO 类分片之后：假设 DP 并行度 128，每个节点只保存自己那一份分片，写出量降到 1TB/128 ≈ 8GB，25GB/s 下约 0.32 秒。

⚠️ 原稿这里写的是「约 0.4 秒」，精确值是 0.32 秒（7.8GB ÷ 25GB/s = 0.31s）。量级对，但差了 25%，我按精确值改了。

这就是分片保存和异步保存必须做的理由——不是「优化」，而是不做就跑不动。

Checkpoint 间隔是另一笔账：间隔越长，故障时的算力浪费越大（浪费量等于故障点与上个 Checkpoint 之间的全部计算）。大规模任务因为节点多、故障率高，很多团队把间隔压到 30 分钟甚至 5 分钟。压到 5 分钟的前提是把上面那笔分片账做完了，否则写 Checkpoint 本身就把训练拖死了。

最后一个细节是 Shared Memory：DataLoader 的多进程共享内存不足会直接报 Bus error: nonexistent physical address，容器里 /dev/shm 的默认值（Docker 默认 64MB）经常不够，需要在 Pod 规格里显式加大。

4.3 第三板斧：任务排布

第三板斧回答「为什么任务怎么摆影响这么大」——答案全在带宽账里。

链路 单向带宽 相对机内 适合放什么
机内 GPU↔GPU（NVLink3，A100） 300 GB/s（双向 600） 1 倍 TP，通信量最大
机内 GPU↔GPU（NVLink3，A800） 200 GB/s（双向 400） 1 倍 TP
机内 GPU↔专属网卡（PCIe Gen4） 32 GB/s（双向 64） 慢约 9 倍 跨机通信的必经之路
跨机 100Gbps 12.5 GB/s 慢 24 倍 DP 梯度同步、PP 激活传递
跨机 200Gbps 25 GB/s 慢 12 倍 贴近 PCIe Gen4 单向上限
跨机 400Gbps 50 GB/s 慢 6 倍 须配 PCIe Gen5 才跑得满

⚠️ 两处规格表述要改：

  1. A100 是「12 条 link」，不是「12 lane」。 每条 link 每方向用 4 个差分信号对（=4 lanes），每对信号速率 50 Gbit/s，折合每条 link 每方向 25 GB/s。12 × 25 = 300 GB/s 单向 / 600 GB/s 双向——总量数字是对的，但「lane」和「50GB/s」两个词都用错了（应为 link，且 50 是 Gbit/s 而非 GB/s）。
  2. A800「被阉到 8 lane」没有官方依据。 NVIDIA 官方只公布聚合带宽 400 GB/s（双向）/ 200 GB/s 单向，未公布 lane/link 数量。「8」是 400/600 = 2/3 = 8/12 推出的 8 条 link，而且官方没说清是减 link 数还是降每 link 速率。另外要强调：A800 与 A100 的差异在 NVLink（GPU↔GPU 互连），不是 NVLink-C2C——NVLink-C2C 是 Grace 与 GPU 之间的芯片间互连，与 A800 无关。

先看这张表对应的数字。 以 A100 平台为例：同主机 GPU 之间走 NVLink，A100 单向 300 GB/s，A800 单向 200 GB/s；同主机 GPU 到自己专属网卡走 PCIe Gen4 交换芯片，单向 32 GB/s；跨主机 GPU 之间看网卡，主流 100Gbps 折算 12.5 GB/s。

跨机比机内慢 24 倍。

200Gbps 折算 25 GB/s，已经贴近 PCIe Gen4 的单向带宽（32 GB/s，占比约 78%）；400Gbps 折算 50 GB/s，超过 PCIe Gen4 单向，必须配 PCIe Gen5 才发挥得出来——佐证是 400G 的 ConnectX-7 本身就是 PCIe Gen5 x16 接口。

这 24 倍直接决定了并行策略怎么落：

  • TP（张量并行） 的通信量最大，每次都要做 AllReduce，所以只要有条件就把 TP 限制在一台机器内走 NVLink——「TP 的大小不要超过 8」这条经验就是这么来的；
  • PP（流水线并行） 只在阶段边界传激活值，通信量小得多，可以跨机，甚至跨 POD；
  • DP 的梯度同步量介于两者之间，是 AllReduce 的主力。

调度上最常见的坑就是这条：一个 8 卡任务，调度到一整台机器上时，TP 全程走 NVLink，速度快；被拆到两台机器上时，TP 跨机，走 12.5GB/s 的网卡，速度差一倍。

所以大任务必须按节点粒度调度，并且要有拓扑约束——不只是「8 张卡」，而是「同一台机器的 8 张卡」。

跨机部分还有一个摆放技巧，通常叫 rail-optimized：把一台机器上第 i 张卡的网卡接到同一台 Leaf，让一次跨机集合通信里同号卡之间的路径尽量短、跳数尽量一致。它的价值在于让 AllReduce 的 ring 上每一段的代价接近，否则快慢不一的段会让整环在最快的那段上也不能提速。

5.3 基线：没有它，前面所有现象你只能靠「感觉变慢了」

基线至少要留三组数，并且在交付验收阶段就采集存档：

  1. 点对点带宽（ib_write_bw）
  2. 集合通信带宽（all_reduce_perf）
  3. 单节点训练的 MFU

这三组数的作用不只是「变慢了能发现」，更重要的是「变慢了多少、什么时候开始慢的」能说清楚——后者才是推动供应商和硬件团队处理问题的凭据。

变更管理只有一条硬规矩：任何网络侧和硬件侧变更，前后都要跑一遍基线测试并存档。绝大多数「运行三个月突然变慢」的问题，追到最后都是三个月里某次没人记录的变更。

六、结语

把这五段串起来，其实只说明一件事：无损网络不是配一次就结束的项目，它是一套需要长期维护的指标体系和处理流程。

从 PFC 和 ECN 的配置，到 SM Clock 的基线比对，中间所有的命令和阈值都指向同一个目标：让几万张卡在几个月里稳定地把算力交出去。

三个最值得记住的判断：

  1. Util 100% 而 SM Active 接近 0 = NCCL 阻塞，这是唯一能在不看业务代码的情况下识别集体卡顿的特征指纹；
  2. 跨机比机内慢 24 倍，这一个数字就决定了 TP 必须限制在机内、大任务必须按节点粒度调度；
  3. 无声丢包不发生在队列里，发生在物理链路上——队列计数干净但 CNP Slow Restart 在涨，就该去看光功率了。
