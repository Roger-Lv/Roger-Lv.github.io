从 K8s 到 AI Infra：跨越五道技术鸿沟

发表于2026-11-05|更新于2026-11-05|AI Infra
|浏览量:

一句话结论：K8s 把 GPU 当作 nvidia.com/gpu: 8 的整数资源来分配，但对 GPU 实际的 SM 占用、NVLink 拓扑、跨机 HCA 带宽一无所知。这种「只分配、不感知」的鸿沟贯穿调度、网络、存储、虚拟化、可观测性五个维度，是 AI 训练吞吐上不去的真正根因。

上一讲（K8s 很熟，为什么月薪卡在三万）讲的是怎么看——nvidia-smi topo -m 的六个缩写、NCCL 日志怎么读、AllReduce 的木桶效应。这一讲讲怎么修：五道鸿沟各自的工程解法。

本文对照 Volcano 源码、NVIDIA MIG User Guide、NCCL 官方文档与源码、JuiceFS 官方文档逐条核对过。核对中发现原稿有十余处需要更正，其中三处会导致读者照着配置失败，已在文中以 ⚠️ 标注。

五道鸿沟总览

维度 K8s 原生方案 AI 训练瓶颈 生产级方案 核心工具链
调度 kube-scheduler 逐 Pod 打分 部分 Pod 无法调度导致整组死锁 Gang 整组调度 + 多维配比 Volcano PodGroup
网络 TCP Socket + 默认网卡 AllReduce 延迟放大数十倍 RDMA 直通 + 拓扑亲和 NCCL + InfiniBand/RoCE
存储 直挂 NFS/S3 冷启动打满源站带宽 分布式缓存 + 预热 JuiceFS + NVMe 二级缓存
虚拟化 Device Plugin 整卡分配 资源浪费、拓扑错配 MIG 硬件切分 + 拓扑感知 NVIDIA MIG + GPU Feature Discovery
可观测性 cAdvisor + kubectl top GPU「利用率 100% 却在空等」 端到端数据面指标 DCGM + NCCL 日志 + MFU

一、调度鸿沟：别把 GPU 当 CPU 调度

1.1 传统 K8s 调度的致命问题

kube-scheduler 的 Filter + Score 机制是「逐 Pod 逐节点」的贪心算法：每个 Pod 独立参与调度，与其他 Pod 没有「整组」概念。微服务场景下任意副本可独立服务，这套机制没问题；但 AI 训练的 Worker 之间存在强同步语义——所有 Rank 必须同时进入 init_process_group，任何一个 Worker 没到位，先启动的 Worker 会一直阻塞在 barrier，持有 GPU 却不做任何有效计算。

具体场景：8 卡训练任务需要 4 个 Worker，每 Worker 占 2 张 GPU，集群剩余 5 张卡分散在 3 台机器（2+2+1）。默认调度器会先把 2 个 Worker 调度到 4 张卡上，剩下 2 个 Worker 因凑不齐 2 张卡而 Pending。最终 4 张 GPU 被两个「半启动」的 Worker 长期占用，集群 GPU 利用率显示 80%，但训练吞吐为 0。

  • MIG 模式下 Device Plugin 未正确上报：需要给 device plugin 传 --mig-strategy，取值是 none | single | mixed，默认 none（原稿只写了 single/mixed，漏了 none 和默认值）。为 none 时节点只上报整卡。
  • 节点驱动与 K8s 版本错配：内核升级后 /dev/nvidia* 消失，Device Plugin 报错但 DaemonSet 仍显示 Running。

二、网络鸿沟：TCP 扛不住集合通信

2.1 为什么 AllReduce 对网络如此敏感

数据并行训练的每个 step 都会对所有参数做一次 AllReduce。先把数学写对：

⚠️ 更正（这条是原稿的硬伤）

原稿写「通信复杂度为 O(2(N-1)) 步，每步数据量为 2(N-1)/N × |M|」。这是把「每卡累计发送量」当成了「每步数据量」。

正确的三组数：

量 公式
总步数 2(N−1)（ReduceScatter 阶段 N−1 步 + AllGather 阶段 N−1 步）
每步每卡发送量 |M| / N（张量切成 N 个 chunk，每步收发一个）
每卡累计发送量 2(N−1)/N × |M|

验算一下原稿的公式：代入 N=64，每步就是 1.97×|M|——比整个张量还大，显然不可能。

代入具体数字：70B 模型 FP32 梯度 = 70×10⁹ × 4 B = 280 GB；2(N−1)/N（N=64）= 126/64 ≈ 1.969。

⚠️ 口径必须写清楚：280 GB × 1.969 = 551 GB ≈ 550 GB，这是每张卡的发送量（接收量相同），不是集群总流量。

集群聚合总流量 = N × 每卡发送量 = 64 × 551 GB = 约 35.3 TB。两者差了 64 倍，混淆会让人误判网络压力。

为什么 TCP 扛不住——三个原因：

  • CPU 协议栈瓶颈：每收发一个包都要内核中断、协议栈处理、拷贝，CPU 占用极高，与训练任务抢核；
  • 滑动窗口限制：TCP 拥塞窗口在长肥管道上利用率不足；
  • 丢包放大：AllReduce 强同步，任何一个 Rank 丢包重传，所有 GPU 都要等它。

⚠️ 一处数字要改：原稿写「1% 的丢包率可能放大为 50% 以上的端到端延迟」。这个说法找不到权威出处。 检索到的最接近来源是厂商博客的「1% 丢包率会导致计算集群约 50% 的性能损失」——那是吞吐结论，不是延迟。业界常引的小丢包→RDMA 劣化原始研究是 Microsoft SIGCOMM 2016《RDMA over Commodity Ethernet at Scale》，同样是吞吐口径。建议按机制描述（丢包触发大粒度重传 → 强同步放大），不套用具体的百分比。

按「每卡 550 GB、单卡 TCP 1—2 Gbps」核算，单次 AllReduce 需 37—73 分钟，「超过 30 分钟」在该假设下成立。但要注明这个吞吐假设非常悲观——常规 10/25/100 GbE 的 TCP 实测远高于此。

2.2 RDMA + NCCL：绕过内核

RDMA 的核心是网卡（HCA）直接读写对端内存，绕过双方内核协议栈。配合 GPUDirect RDMA，网卡还能直接访问 GPU 显存：

方案 带宽 延迟量级 成本 适用场景
InfiniBand（NDR 400G） 400 Gbps 亚微秒级 高 大规模预训练集群
RoCEv2（以太网） 100—400 Gbps 微秒级 中 中小集群，可复用以太网
TCP（fallback） 10—100 Gbps 数十 µs 低 单机或调试

⚠️ 延迟这一列的精确数字（0.5 µs / 1.4 µs）找不到 NVIDIA 官方一手来源，且原稿没区分「交换机 port-to-port」与「端到端 MPI 延迟」。上表已改为量级表述。引用精确数字前请自行核实口径。

NCCL 在底层自动选择 Ring / Tree / CollNet 算法，并按硬件拓扑选路（NVLink 优先，跨机走 IB/RoCE，必要时混合两级环）。

2.3 K8s 中启用 RDMA

  1. 物理机启用 SR-IOV，把物理网卡切成多个 VF；
  2. 部署 sriov-network-device-plugin（或 Mellanox 的 RDMA device plugin），把 VF 上报为扩展资源；
  3. Pod 声明该资源，并通过 SR-IOV CNI 把 VF 直通到容器 netns；
  4. 容器内出现 /dev/infiniband/uverbs*，可直接调用 ibverbs API。

2.6 网络层面高频踩坑

  • 未设 NCCL_IB_HCA，选中错误网卡：机器上可能同时有存储用 RoCE 卡和计算用 IB 卡；
  • 未设 NCCL_SOCKET_IFNAME，bootstrap 走了外网网卡：对端不可达，rank 握手挂起或极慢；
  • PFC/ECN 未配置：以太网承载 RoCE 需要交换机侧配 PFC + ECN，否则拥塞时静默丢包，AllReduce 随机挂起。

⚠️ 关于「CNI 未配 MTU → RoCE 被 VXLAN 封装后超限」：MTU 黑洞机制本身成立（VXLAN 开销 50 字节，Pod MTU = Host MTU − 50），但RDMA/RoCE 通常绕过 CNI overlay（走 SR-IOV / macvlan / host network / 独立 RDMA 网段），且 RoCE 用的是 IB 链路 MTU（1024/2048/4096），与内核 TCP MTU 不是一回事。这是特定部署下才成立的场景，不宜作为通用结论。

三、存储鸿沟：冷启动打满源站

3.1 痛点量化

70B 模型 FP16 权重约 140 GB。用 S3 CLI 直拉（出口带宽约 110 MB/s）冷启动需要 约 21 分钟；集群中 10 个节点同时拉同一份权重，S3 出口带宽被瞬间打满；Pod 被驱逐重建、节点扩容都要重新拉全量，没有任何缓存复用。

3.2 JuiceFS + 分布式缓存 + 预热

JuiceFS 把对象存储作为持久层，在计算节点本地维护块级缓存，对外提供 POSIX 接口。核心架构是元数据服务（Redis/TiKV） + 对象存储 + 本地缓存三层解耦。

关键设计差异：JuiceFS 的缓存是块级缓存，落在本地磁盘（推荐 NVMe）。CSI 场景下缓存目录在节点主机上，因此 Mount Pod 重建通常不影响缓存——这是它与 page cache 的关键区别。

⚠️ 一处需要补全：原稿把 JuiceFS 一概描述为「磁盘缓存、不随 Pod 消亡」不完整——JuiceFS 也支持 --cache-dir memory（缓存直接放客户端进程内存）或 /dev/shm，这种模式进程重启就丢。另外 CSI 有 juicefs-clean-cache: "true" 注解会在 Mount Pod 退出时清理缓存。所以「Pod 增删不影响缓存」是默认行为，不是绝对保证。

分布式缓存组：--cache-group 让同名客户端组成一个缓存组，内部是一个一致性哈希环——每个数据块的归属节点由一致性哈希算出，组内共享。读请求会直接从负责该块的成员节点取。所以「任一节点缓存了、其他节点都能拉」方向正确，但机制是「哈希指定归属 + 组内共享」，不是任意节点随意互拉。

⚠️ --cache-priority 和 --cache-group 都是 企业版/云版特性，社区版只有 --cache-dir。

四、虚拟化鸿沟：GPU 不是更快的 CPU

4.1 三层失效

第一层：cgroup 不生效。 cgroup 的 cpu controller 在 CFS 调度器层面限制时间片，memory controller 在内核页分配器层面限制内存。但 GPU 执行路径是 进程 → 用户态 CUDA → NVIDIA 驱动 → GPU 硬件调度器，旁路 Linux 内核调度。

第二层：Device Plugin 只上报整数。 nvidia.com/gpu: 8 只传递设备 ID 列表，不携带 NVLink 拓扑、PCIe 亲和性、显存水位。调度器不知道「GPU0 和 GPU1 通过 NVLink 互联」，可能把需要高速互联的进程调度到跨 PCIe root 的卡上。

第三层：共享 GPU 无隔离。 time-slicing 或 CUDA_VISIBLE_DEVICES 切分本质是时间片轮转，多 Pod 争抢 SM、Tensor Core、L2、显存带宽，且任何一个 Pod 触发 OOM 都可能波及其他 Pod。

4.2 MIG：硬件级切分

MIG（Multi-Instance GPU） 把一张物理 GPU 在硬件层切分为多个独立实例，每个实例有独立的 SM、L2、显存控制器和故障域。

⚠️ 更正（原稿这张表标错了代次）：原稿写「A100 80GB 的典型 MIG 配置」并给出 7g.40gb / 4g.20gb / 2g.10gb / 1g.5gb——这组 profile 全部是 A100 40GB 的。NVIDIA MIG User Guide 原文：「For A100-SXM4-80GB, the profile names will change according to the memory proportion – for example, 1g.10gb, 1g.20gb, 2g.20gb, 3g.40gb, 4g.40gb, 7g.80gb」。

A100 40GB A100 80GB
1g 1g.5gb 1g.10gb
2g 2g.10gb 2g.20gb
3g 3g.20gb 3g.40gb
4g 4g.20gb 4g.40gb
7g 7g.40gb 7g.80gb

SM 比例是对的（两者都是 7/7、4/7、3/7、2/7、1/7——每片显存取总显存 1/8、每片 SM 取总 SM 1/7），错的只是显存大小与型号的对应关系。

MIG 实例在 Device Plugin 层被上报为独立资源，格式是 nvidia.com/mig-<slice>g.<mem>gb（属实）——调度器可以直接按实例粒度分配，硬件本身就完成了隔离。

「MIG 最多 7 个实例」对 A100/H100 成立，但不是全平台通例（例如 RTX PRO 6000 Blackwell 的 1g profile 只有 4 个实例）。

4.3 拓扑感知

用 nvidia-smi topo -m 看拓扑（缩写的完整定义见上一讲）。生产中通过 GPU Feature Discovery 把拓扑信息以 Node Label 暴露。

⚠️ 更正两个标签名：正确的标签是 nvidia.com/gpu.product（点号，不是连字符 gpu-product），示例值 A100-SXM4-40GB。而 nvidia.com/nvlink 不存在——与 NVLink/fabric 相关的真实标签是 nvidia.com/gpu.clique（GPUFabric ClusterUUID + CliqueID），另有 nvidia.com/gpu.family、nvidia.com/gpu.memory、nvidia.com/gpu.count 等。

4.4 用 DCGM 看真实利用率

核心指标（这四个名字都是 dcgm-exporter 实际暴露的 Prometheus 指标名，可直接查）：

指标 含义
DCGM_FI_DEV_GPU_UTIL GPU 时间片利用率（Busy 或 Idle）
DCGM_FI_PROF_SM_ACTIVE SM 活跃度
DCGM_FI_PROF_PIPE_TENSOR_ACTIVE Tensor Core 活跃度
DCGM_FI_PROF_GR_ENGINE_ACTIVE Graphics Engine 活跃度

⚠️ 补一层版本对照：这四个名字在 DCGM 源码 dcgm_fields.h 里都是旧名/别名，规范名已改成 *_UTIL_RATIO：

常用名（dcgm-exporter） DCGM 规范名

典型异常模式：SM_ACTIVE 长期 >80% 但 PIPE_TENSOR_ACTIVE <30%，说明 GPU 在用 CUDA Core 执行本应由 Tensor Core 承担的矩阵运算——这是模型代码层面的优化信号，不是基础设施问题。

⚠️ 一处口径要收：原稿说 DCGM_FI_PROF_* 系列「会影响性能」。官方口径是 low overhead，唯一的明确限制是 profiling 计数器资源会与 Nsight 等开发者 profiler 冲突（需 dcgmi profile --pause 让出）。另外部分 DCGM_FI_PROF_* 在 dcgm-exporter 默认 collector CSV 里是注释掉的，需要自行开启。

五、可观测性鸿沟：利用率 100%，却在空等

5.1 传统监控的盲区

nvidia-smi 显示的「GPU-Util 100%」，官方定义是「过去一个采样周期内，至少有一个 kernel 在 GPU 上运行」。

⚠️ 更正：原稿说采样周期是「1 秒」。官方原文是「The sample period may be between 1 second and 1/6 second depending on the product」——不是固定 1 秒。

它无法区分：有效矩阵计算、数据搬运（H2D/D2H）、NCCL 通信等待、数据加载等待。一个真实 case：所有 GPU 利用率 100%，但训练吞吐只有理论值的 1/3。Profile 后发现每个 step 里 75% 的时间 GPU 在等 NCCL 通信完成——GPU 显示 busy（有等待 kernel 在跑），实际什么有用功都没做。

5.2 正确指标：MFU + 通信占比 + Step 分解

MFU（Model FLOPs Utilization） 是唯一真正反映硬件有效算力的指标：

⚠️ 公式要标注是近似：PaLM 论文的完整式是 6N + 12LHQT（含 dense self-attention 的额外项），6N 是忽略注意力项的近似。PaLM 自己说明该项对大模型很小，所以工程上常用 6N——但引用时宜注明是近似。

三个口径问题必须钉死：

  • 稠密 vs 稀疏算力：H100 SXM 的 BF16 官方数字是 稀疏 1979 TFLOPS、稠密约 989 TFLOPS，必须用稠密口径，否则 MFU 虚高一倍。

⚠️ 补两处限定：一是官方 datasheet 把 989 标注为「TF32 Tensor Core（with sparsity）」，BF16 列的是 1979（with sparsity）——数值上 BF16 稠密 ≈ 1979/2 ≈ 989 成立，但引官方表时要注意标注；二是 989/1979 是 H100 SXM 的数字，H100 PCIe 是 BF16 稀疏 1513 / 稠密约 756，不加「SXM」限定口径不完整。

  • 是否含通信：把 AllReduce 算进分母的 MFU 更低但更真实（端到端），只看计算时间的高但掩盖通信瓶颈。两种都报，先固定定义；
  • 精度口径：BF16 与 FP8 峰值不同，混用会测出两种 MFU。

参考值：Llama 3 405B 论文报告的整体 BF16 MFU 是 38—43%（三个配置分别 43% / 41% / 38%，属实）。

⚠️ 一处来源要改：原稿写「nanoGPT 多卡约 50%+，单卡约 35-40%」。追到原始出处是 Karpathy nanoGPT 仓库的 transformer_sizing.ipynb：单卡实测 37.14%（与「35-40%」吻合），但 50%+ 是作者写的期望目标（“we’d prefer to be somewhere around 50%+, and not just for a single GPU but for an entire DDP run”），不是实测达到的多卡 MFU。

另外「MFU 显著低于 30% 时一定存在可优化瓶颈」没有官方来源，属社区经验法则。措辞宜改为「经验上低于约 30% 通常意味着存在可排查的瓶颈」，不宜用「一定」。

BusBW 与 algbw 的区别（nccl-tests）：algbw = S/t；busbw 是对 algbw 乘一个与集合操作和 rank 数相关的修正因子（AllReduce 是 2(n−1)/n），用来反映互连硬件瓶颈速率，从而可与硬件峰值带宽直接对比。看 busbw 列，不看 algbw。

六、面试深挖：cgroup 为什么管不住 GPU？

分三层回答。

第一层：机制层——GPU 执行路径旁路内核调度。
CPU 路径是 进程 → 内核（CFS + cgroup controller）→ CPU 时间片；GPU 路径是 进程 → 用户态 CUDA → NVIDIA 驱动 → GPU 硬件调度器。Linux 内核在这条路径上只是「传话筒」。NVIDIA 驱动注册 /dev/nvidia* 字符设备，用户态通过 ioctl 提交命令——cgroup 的 device controller 可以允许/禁止访问设备节点，但无法计量、无法限制进程提交的 kernel 数量、显存申请量或 SM 占用时长（device controller 是纯访问控制，没有计量能力，这一点核实属实）。

第二层：资源模型层——Device Plugin 只有「整数」。
Kubernetes 的 ResourceName → Quantity 模型里，Device Plugin 上报的是 nvidia.com/gpu: 8，协议只传设备 ID 列表。调度器无法回答：GPU0 和 GPU1 之间是 NVLink 还是 PCIe？当前剩余多少显存？某个 Pod 实际用了多少算力？（nvidia-smi 的利用率是设备级全局值，不是 per-process。）

第三层：补救手段层——四种方案。

方案 原理 隔离强度 适用场景
MIG 硬件切分 SM / L2 / 显存控制器 硬件级强隔离 A100+ 多租户推理
Time-slicing 用户态轮转 kernel 提交 弱（无隔离） 开发测试
MPS 用户态合并多进程 kernel 提交 中等 低延迟推理共享
拓扑感知调度 调度器约束 GPU 选择 不隔离，只优化位置 单租户训练

MPS 的隔离强度值得说准：它有地址空间隔离（fully isolated GPU address spaces），故障隔离是有限的（一个 client 的致命 fault 会波及共享该 GPU 子集的所有 client），SM 是软限制（“does not reserve dedicated resources”），显存需要显式配置才有隔离。

⚠️ 一处时效性更正（原稿的结论已经过时）

原稿的收尾断言是：「只要 NVIDIA 驱动不对 cgroup v2 暴露 nvidia/memory.max 等 controller 接口，K8s 的 Pod 级别细粒度 GPU 资源 QoS 就永远是『尽力而为』，而非『硬保障』。」

这个结论现在不成立了。 NVIDIA 已通过 MPS v3 memory partitioning 提供了 cgroup v2 的 GPU 显存限制，官方原文：

“MPS v3 memory partitioning fractionalizes a GPU’s device memory across cgroups and containers… Unlike the older userspace memory limits, this feature accounts for all device memory and integrates with the Linux kernel cgroup controllers.”
“Hard limit maps to dmem.max… Soft limit maps to dmem.min.”
后端：kernel 6.14+ 有 DMEM controller 时用 dmem；否则回退到驱动内部的 misc 后端做 per-cgroup 记账。需要 cgroup v2 且 CUDA 13.4+，且不支持 MIG 设备。

接口名是内核标准的 dmem.max / dmem.min，不是 nvidia/memory.max。设置方式：nvidia-smi memory-limits --set -n <cgroup路径> --hard-limit ... 。

所以准确的结论是：GPU 显存的 cgroup 级硬限制已经存在，但很新、对内核版本（≥6.14）与 CUDA 版本（≥13.4）有要求、且不支持 MIG。旧结论不是错，是过时。

七、生产避坑清单

调度层

  • Gang 语义失效时先看 Pod 是否永久 Pending、schedulerName 是否指向不存在的调度器（不是「不写 schedulerName」）；
  • MIG 模式下 device plugin 需传 --mig-strategy（none|single|mixed，默认 none）；
  • 内核升级后 /dev/nvidia* 可能消失，Device Plugin 报错但 DaemonSet 仍 Running。

网络层

  • NCCL 静默回退 Socket 是最隐蔽的坑——默认 WARN 级别看不到回退消息，必须开 NCCL_DEBUG=INFO 主动 grep；
  • NCCL_IB_HCA 记得加 = 前缀（否则前缀匹配会误命中 mlx5_1x）；
  • NCCL 2.21+ 不要再手动设 NCCL_IB_GID_INDEX，让它自动选；
  • PFC/ECN 未配 → 拥塞时静默丢包，AllReduce 随机挂起。

存储层

  • cache-dir 必须指向独立持久卷，不能是 emptyDir；
  • cache-size 单位是 MiB，默认 102400（=100 GiB）；
  • CSI 挂载参数写在标准 mountOptions 字段，不是 juicefs/mount-options；
  • 随机读放大调的是 --prefetch，不是 --readahead；
  • 预热任务避开训练高峰，或用 -p/--threads 限流。

可观测性层

  • MFU 口径（稠密/稀疏、含不含通信、精度）必须在团队内钉死；
  • DCGM 指标名有 *_ACTIVE → *_UTIL_RATIO 的改名史，跨版本做面板要映射；
  • kubectl top 看不到 GPU——它只采 cgroup 数据。

八、集群自查速查

九、结语：跨越鸿沟的本质是建立数据面思维

AI Infra 的核心不是「学几个新工具」，而是从控制面思维转向数据面思维——关注点从「资源能否被分配」变成「数据能否被高效搬运和计算」。

五道鸿沟对应五个数据面本质：

  • 调度的本质是「同步语义的资源整组性」；
  • 网络的本质是「绕过内核的数据直通」；
  • 存储的本质是「缓存层与持久层的解耦」；
  • 虚拟化的本质是「硬件级隔离与拓扑亲和」；
  • 可观测性的本质是「从时间占用到有效算力的度量」。

当你能从一次训练的 NCCL 日志反推出物理网络拓扑，能从 MFU 的下降趋势定位到具体是通信还是数据加载瓶颈，能解释清楚 cgroup 管不住 GPU 的三层机制（以及它正在被 MPS v3 补齐）——三万薪资天花板，自然就不再是天花板。
