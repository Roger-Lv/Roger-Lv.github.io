C++ 库为什么对外提供 C 接口（从 extern "C" 到 ABI）

Published2026-11-23|Updated2026-11-23|系统编程

一个库可以用 C++ 实现对象管理、模板和多态，同时在动态库里对外导出一组 C 函数。调用方只需要知道该找哪个函数、怎样传参数，以及如何释放库创建的对象。库的内部实现可以继续演进，已发布的调用约定则由团队按目标平台和版本维护。

本文从两个求最大值的函数出发，先用 nm 看编译器生成的符号，再用 Python 加载同一个 C++ 动态库。问题的核心是 ABI（Application Binary Interface，应用二进制接口）。

本文受夏曹俊老师关于 C++ 库为何对外提供 C 接口的技术分享启发。下面的代码与符号输出来自本文的独立实验。

1. API 让源码知道怎么写，ABI 让二进制知道怎么调用

假设你在程序里写下 c_max(3, 7)。编译器读到头文件里的 int c_max(int a, int b); 后，会检查参数，并生成调用指令。链接器或动态加载器还需要在库中找到这个符号。调用发生时，库和程序必须对参数放在哪些寄存器或栈位置、返回值放在哪里有一致的理解。

层次 它约定什么 调用 c_max 时的例子
API 源码怎么调用、函数做什么 接收两个整数，返回较大值
ABI 编译后的程序和库怎样交接 符号名、C int 的表示、调用约定、返回值的位置

源码兼容通常意味着旧调用代码可以用新头文件重新编译。向后二进制兼容意味着原本针对旧库构建的程序，在库支持的环境里可以加载新库并按原有约定运行。比如 C++ 类新增一个私有成员后，原来的源码调用可能照常通过编译，但类的大小和成员偏移可能已经变化。旧程序里编译进去的布局信息仍来自旧版本。 Itanium C++ ABI 对数据布局与调用的约定

cpp_max 使用 C++ 语言链接。按照 Itanium C++ ABI，这个普通函数的名称编码为 _Z7cpp_maxii。7 是 cpp_max 的长度，ii 对应两个 int 参数，普通非模板函数在这套规则里通常不把返回类型编码进符号。C++ 支持重载，链接器需要借助这种编码区分同名的不同函数。macOS 的 Mach-O 符号在这两个编码之外还各有一个平台前导下划线。 Itanium C++ ABI §5.1 名称修饰 · LLVM 关于 Mach-O 符号前缀的说明

extern "C" 指定语言链接。这个例子里的自由函数 c_max 采用目标平台的 C 符号命名规则，函数体依旧由 C++ 编译器编译，可以调用 C++ 函数或创建 C++ 对象。它也可以用在 C++ 头文件里声明由 C 源码提供的函数。动态库的导出需要另行配置，例如 Windows DLL 的 __declspec(dllexport) 或导出定义文件，以及启用隐藏可见性时显式导出需要的符号。 C++ 工作草案关于语言链接的规定 · Microsoft DLL 导出文档

3. 同一个 Clang 换目标平台，输出也会变

使用 Clang 生成汇编就能观察目标平台的名称规则。这个例子不依赖系统头文件，生成汇编即可读符号，无需 Windows SDK 或 Linux 运行环境。

目标 C++ 入口 C 入口
macOS arm64，Mach-O __Z7cpp_maxii _c_max
Linux x86-64，ELF _Z7cpp_maxii c_max
Windows x64，MSVC ABI ?cpp_max@@YAHHH@Z c_max
Windows x86，MSVC ABI，默认 __cdecl ?cpp_max@@YAHHH@Z _c_max

这些是对应目标的符号名。32 位 Windows 上如果使用 __stdcall，C 名称还可能带参数字节数后缀，例如两个 4 字节整数对应的 _c_max@8。这解释了为什么某些工具会显示 _c_max，而源码里写的是 c_max。共享库的最终导出名还会受到链接器配置影响。 Microsoft 关于 C 和 C++ 名称修饰的文档

工具链能否混用，要看它们面向的 ABI 与运行时。 在常见 Linux 目标上，GCC 和 Clang 都采用 Itanium C++ ABI 的规则，使用兼容的标准库和编译配置时可以互操作。即使都用 GCC，libstdc++ 的 _GLIBCXX_USE_CXX11_ABI 也会影响 std::string 等类型的二进制接口。在 Windows 上，clang-cl 面向 MSVC 工具链和 ABI；具体 C++ 特性的支持和库的要求仍需对照文档。是否能编译某些 SIMD 内建函数，属于指令集特性和编译器行为，单独看它无法判断两个库的 ABI。 GCC libstdc++ Dual ABI · Clang 的 MSVC 兼容性与 SIMD 内建函数说明

这种调用也叫 FFI（Foreign Function Interface，外部函数接口）。Python 和 C 程序可以通过相同的 C 入口调用库内部的 C++ 实现。

    flowchart TD
    P["Python 程序"] --> F["ctypes"]
    C["C 程序"] --> H["通过 calc.h 编译并链接"]
    F --> E["动态库导出 c_max"]
    H --> E
    E --> I["库内调用 C++ 函数 cpp_max"]

这里同时有两个约定。名字 c_max 用于查找入口，argtypes 和 restype 使 Python 按 C 函数的签名传参和读回结果。如果新版本仍导出 c_max，却把参数改成 double，旧程序可能照样找到符号，随后仍按整数传参。在 Linux x86-64 的 System V ABI 中，这两类参数通常使用不同的寄存器。符号查找成功只完成了第一步。 Python ctypes 文档 · System V x86-64 psABI

Python 还有另一种接入方式。pybind11 的 PYBIND11_MODULE 生成 CPython 扩展入口，扩展通过 CPython 的接口注册可调用对象。Python 执行 module.func(...) 时，由生成的包装代码转换参数、调用 C++ 函数并转换返回值。原始 C++ 函数可以保持 C++ 链接。Java 的 JNI 也有自己的函数签名和对象管理约定，Java 调用和 C++ 实现之间通过本地方法适配。 pybind11 入门文档 · CPython 扩展模块接口 · JNI 设计规范

5. 怎么把 C 接口真的维护成稳定 ABI

一个要长期分发的库，通常把外部入口设计成有限的 C 函数，让复杂对象留在库里。例如有状态的计算器可以在头文件里声明下列接口，并沿用前面的语言链接写法。

这里 struct calc_handle 是不完整类型。调用方可以保存、传回指针，结构体的字段和大小由库内部定义。实现可以调整字段、改用 C++ 容器，或者把对象存储迁移到另一套实现。创建和销毁都由库提供，有助于避免跨运行时或分配器释放内存。接口文档还要约定 calc_create 失败时返回空指针，以及 calc_set_mode 的成功值和各类错误码。

需要维护的约定 可以怎么设计
导出符号与调用约定 保留原入口和签名，新增功能时新增符号
参数、数据布局与缓冲区 用双方理解一致的整数类型，以及指针加长度。需要共享结构体时约定大小、对齐和扩展规则
对象和内存的所有权 用 opaque handle 隐藏对象布局。库分配的对象由配对的库函数释放，或者让调用方提供缓冲区
错误处理 在 C++ 包装层内捕获异常，转换为文档定义的错误码
发布与验证 明确支持的系统、架构和运行时，让用旧头文件编译出的程序直接加载新库做回归测试

本文的动态库实测采用了同样的方法。保留已经编译好的 C 客户端，在动态库里新增 c_min 并保留 c_max，然后重新启动原客户端和 Python 脚本。两者仍能得到原来的结果。

C++ 自身也能维护长期的 ABI。PIMPL（Pointer to Implementation）可以用一个实现指针把私有字段移到类外，降低改动对象布局的概率。公开方法的签名、虚函数布局、内联函数和标准库类型等仍要按发布承诺管理。对于预编译动态库，能否只升级库文件取决于它是否保留了旧程序依赖的符号、布局、调用约定、运行时和行为。 Itanium C++ ABI 的类布局 · Microsoft C++ 二进制兼容条件

6. CUDA 和 PyTorch 如何划分边界

CUDA 的 Driver API 提供 cuMemAlloc、cuMemFree 这样的 C 风格入口。调用方按文档使用句柄和资源管理函数。NVIDIA 还约定了 Driver API 的函数 ABI 版本和版本混用规则。编译 CUDA 源码时使用哪个宿主编译器，则由工具链支持范围决定。 CUDA Driver API 内存管理 · CUDA ABI 版本混用规则 · NVIDIA nvcc 文档

PyTorch 提供常规 LibTorch C++ API，也为扩展提供一组范围有限的 Stable ABI 接口。后者把稳定的 C 层与面向用户的 C++ 包装结合起来，为支持范围内的自定义算子提供跨 PyTorch 版本的兼容性。使用常规 C++ 接口的扩展，需要与目标版本的二进制和构建配置匹配。开源便于按目标环境重新构建；已经发布的二进制能否直接复用，仍由项目的兼容承诺决定。 PyTorch LibTorch Stable ABI 文档

下次看到一个 C++ 库发出 C 头文件和动态库，可以先看三件事。头文件声明了哪些入口，每种参数和返回值怎样跨过边界，内存与错误由谁管理。把这三项约定和库的版本支持范围对上，就能判断调用方需要重编译，还是可以直接使用新库。
