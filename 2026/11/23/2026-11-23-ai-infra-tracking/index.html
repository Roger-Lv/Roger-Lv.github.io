AI Infra 技术追踪｜2026-11-23

Published2026-11-23|Updated2026-11-23|AI Infrastructure

一句话结论： SGLang 把部分 KV 写回的等待从调度线程移到 GPU stream；TorchTitan 把激活重计算覆盖到 MTP；NIXL 让可直达的 NVLink 操作绕过 CPU proxy，打断一类 EP barrier 死锁。

追踪自 11 月 22 日约 01:13 UTC 的上次扫描截止点。以下区分正式发布、主线合并和作者实验；本文未独立运行 GPU 或集群实验。

1. 推理｜SGLang HiCache 写回不再阻塞满足条件的调度循环

原来的瓶颈。 L2 write-back 淘汰 GPU KV 页时，要先完成 GPU→CPU（D2H）复制，才能安全重用 GPU 页。旧路径会让调度线程等复制，哪怕 CPU 本来可以准备下一批。新路径没有省掉复制，也没有放松内存生命周期约束。

这次改动。 SGLang #50469 于 11 月 22 日 16:46 UTC 合入主线。匹配 write/load fence stream 才走新路径；不开 overlap 时当前 stream 也要等待。排除 L3 存储、buffer pipeline、linker、统一内存及 P/D 的 decode 侧。不能据此推断 Redis、Mooncake Store 或 RDMA 变快。合入代码

收益与代价。 作者在 GB300 上使用 DeepSeek V4.1 Flash，14 台 prefill server + DEP16 decode，开启 overlap，两组均含 #47650。相同镜像、单一中等并发的多轮请求回放，每组 2 次、每次 1,200 秒。端到端 tokens/s/GPU +4.2%，TTFT p90 12.0→9.6 s，TPOT p90 7.25→7.32 ms（略慢）。它是特定负载下以更快 prefill 换来更满 decode 的结果，不是所有吞吐、尾延迟指标同时改善。GSM8K 是冒烟测试，不是匹配基线的逐输出一致性验证。作者数据与条件

值得怎么试。 先在同模型、同请求轨迹、同缓存状态下 A/B，分别收集 prefill/decode 的吞吐、TTFT/TPOT 和 CPU 调度线程等待。另做一个独立生命周期试验：让复制完成事件延后，区分 KV 页能否安全重用，与 drain/flush/挂载存储前能否判为 idle。合入的 mock 回归覆盖 stream wait 和没有 host synchronize，但事件立即就绪；代码评审提示 idle 检查需要留意尚未结束的 fenced acknowledgments，这不是已证实的生产故障。评审讨论

2. 训练｜TorchTitan 把激活重计算扩展到 MTP 层

原来的缺口。 激活重计算在反向阶段重做一部分前向，以减少保留的激活。开启 activation remat 过去不等于每条模型分支都被覆盖：MTP（多 token 预测）有单独的 mtp_layers，之前只遍历常规 layers 的路径会漏掉它。

这次改动。 TorchTitan #6246 合入提交 于 11 月 22 日 15:05 UTC 落地。每个 model part 一次遍历其声明的 block 容器，使 decoder、MTP、视觉 encoder 的组合能复用策略。encoder 区域用完整名称避免和 decoder 同名；启用激活卸载时仍是每个 part 共用一个 offloader。这里的 checkpointing 指激活重计算，不是用于宕机恢复的持久化 checkpoint。

证据与边界。 作者在 4×GH200、FSDP 4 的 DeepSeek-V3 debug 配置中做了 10 步确定性对照：Default 策略和 16,384 序列长度的 Full 策略分别对照此前 main，loss 和梯度范数逐位一致。独立的 CUDA 回归检查实际包装了两层 MTP，并以不做 remat 为基线校验输出和参数梯度。没有公开实测说明能省多少显存、增加多少重算时间或避免生产 OOM，也不是 DeepSeek-V4 端到端训练修复。

值得怎么试。 固定模型、MTP 层数、数据、精度、FSDP 与序列长度，仅切换是否覆盖 MTP，再拉一条序列长度曲线。先看 loss/梯度，再分别记每 rank 峰值 allocated/reserved、step time 与 tokens/s。不要把“更长序列能跑”和“同样负载更快”混成一个指标。

3. GPU 互连｜NIXL 用 NVLink 直访打断一类 EP barrier 死锁

原来的等待环。 一些 GPU 设备侧操作走 CPU proxy。EP（专家并行）kernel 等 proxy 做 put 或计数器更新时，如果 proxy 进入同步 CUDA 调用、反过来等这个 kernel 退出，就会互相等待。这是传输路径的进展问题，不是节点故障或网络丢包。

这次改动。 NIXL #2701 于 11 月 22 日 22:06 UTC 合入主线。源和目的都有直达指针时，设备侧直接执行 put；计数器有直达指针时，直接执行具有 system scope 的原子加。不满足条件的操作继续走 proxy。新路径针对具备直接访问条件的显存，不代表远端 RDMA 路径也能绕开 proxy，更不是 RoCE 或 InfiniBand 故障切换。合入代码

证据与边界。 作者在 NIXL EP CPU-proxy 模式下用 2×4 GB200、16 channels、128 tokens、每 rank 32 experts，各跑一次：78.2→76.7 GB/s、281.8→287.4 μs。不能用单次结果判断性能回归或收益。这个变更的价值是解决特定等待环；PR 没有增加专门的死锁回归测试，不能声称覆盖了所有 GPU 拓扑和 proxy 路径。

值得怎么试。 在隔离测试环境固定 NIXL/CUDA 版本、拓扑与 EP 负载，用看门狗记录 barrier 完成率、耗时和是否超时，而不是只测链路带宽。分别确认直访条件成立的 peer 与必须经 proxy 的 peer，验证写入内容和 counter 计数，再对比多轮吞吐与尾延迟。优先用它排查确实使用 NIXL 设备侧 proxy 的任务，不需要据此改 NCCL 或集群网络配置。
