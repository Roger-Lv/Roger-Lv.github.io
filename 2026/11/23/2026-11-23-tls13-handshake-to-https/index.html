TLS 1.3 完整通信过程（从 TCP 建连到 HTTPS 数据传输）

Published2026-11-23|Updated2026-11-23|计算机网络

一次新的 HTTPS 连接里，TCP 先建立可靠的字节流，TLS 再协商密钥并验证服务器身份，最后才沿这条连接传输 HTTP 请求和响应。TLS 1.3 在收到 ServerHello 后已经能加密后续握手消息，客户端还要验证证书、CertificateVerify 和 Finished，才会发送普通的 HTTP 请求。

本文以 HTTP/1.1 over TCP、首次连接、X25519 密钥交换、服务器证书认证 为例。正文末尾用本地 OpenSSL 实验观察握手、加密记录和连接关闭。

1. 从 DNS 和 TCP 建连看完整时序

访问 https://example.com/api/users 时，客户端先通过缓存或 DNS 获得地址，再向目标地址的 TCP 443 端口建连。TCP 的 SYN、SYN-ACK 和 ACK 建立连接并同步初始序号。此时双方有了可靠的字节流，TLS 的加密和身份认证从下一阶段开始。

    sequenceDiagram
    participant C as 客户端
    participant S as 服务器
    C->>S: SYN
    S->>C: SYN-ACK
    C->>S: ACK
    C->>S: ClientHello
    S->>C: ServerHello
    Note over C,S: 双方派生握手密钥
    S->>C: EncryptedExtensions
    S->>C: Certificate
    S->>C: CertificateVerify
    S->>C: Finished
    Note over C,S: 客户端验证服务端身份和握手
    C->>S: Finished
    C->>S: HTTP 请求
    S->>C: HTTP 响应

图中的箭头表示逻辑消息。TLS 握手消息、TLS Record 和 TCP 段各有边界。服务器可以在一次发送中写出多条握手消息，TCP 也可以把一条 Record 拆成多个段。读抓包时，需要先按 TCP 字节流重组，再按 TLS 记录层识别消息。图中两个 Hello 使用明文记录，EncryptedExtensions 到双方 Finished 使用握手密钥，HTTP 请求和响应使用应用流量密钥。 RFC 9293 TCP 规范 · RFC 8446 §2 握手时序

2. 两个 Hello 协商了什么

客户端在 ClientHello 中给出可以接受的参数，并为一个或多个支持的组提前生成密钥份额。以下是一组可以完成本文握手的组合。

项目 ClientHello 中的示例 协商结果或用途
legacy_version 与 supported_versions 0x0303 和 0x0304 旧字段保留兼容值，TLS 1.3 由扩展中的 0x0304 标识
cipher_suites TLS_AES_128_GCM_SHA256 等 服务器选一个套件，此处为 AES-128-GCM 和 SHA-256
supported_groups x25519、secp256r1 列出支持的密钥交换组
key_share x25519: A 提供客户端已经生成的临时公钥
signature_algorithms rsa_pss_rsae_sha256、ecdsa_secp256r1_sha256 等 声明客户端可验证哪些握手签名
server_name（SNI） example.com 供共享 IP 和端口的网关选择虚拟主机及证书
ALPN http/1.1 提议应用层协议，服务器在 EncryptedExtensions 返回选定项

ServerHello 选定 TLS 1.3、密码套件和密钥交换组，并在 key_share 返回服务器的 X25519 临时公钥 B。TLS 1.3 套件名里的 SHA-256 用于 HKDF 和握手摘要，AES-GCM 用于记录层认证加密。密钥交换组和数字签名方案各自协商，所以同一个套件可以搭配 X25519 和 RSA-PSS 握手签名，也可以搭配 X25519 和 ECDSA 握手签名。

如果服务器需要的组在客户端的 supported_groups 里，但客户端还没为该组提供 key_share，服务器可以发送 HelloRetryRequest，要求客户端补发第二个 ClientHello。这多一次 TLS 往返，首个 Hello 仍参与握手摘要，协议用它的哈希构造一条合成的 message_hash 消息。 RFC 8446 §4 握手消息与扩展

通常能从明文 ClientHello 读出 SNI。采用 ECH（Encrypted ClientHello）且协商成功时，实际服务名可以放在加密的内层 ClientHello 中。外层 Hello、目的 IP 和连接时序依然可见，普通 DNS 查询也可能单独暴露域名。 RFC 9849 TLS Encrypted Client Hello

3. ECDHE 如何得到相同的共享秘密

以 a、b 表示两端临时私钥，用圆括号里的参数写出各自调用 X25519 的方式。X25519 在公钥和共享结果里使用曲线点的编码，下面的 aG 只是标量乘法的直觉记法。

网络中交换的是 A 和 B。在安全实现下，只观察这些公钥无法高效算出共享秘密。TLS 对 X25519 的全零共享结果要求中止握手。短期私钥按握手生成并妥善销毁时，即使服务器证书私钥日后泄露，仅凭它和此前被动录下的流量也无法还原这次 ECDHE 的共享秘密，这就是此场景中的前向保密。 RFC 7748 §6.1 X25519 密钥交换 · RFC 8446 §7.4.2 ECDHE

4. HKDF 按方向和阶段派生密钥

ECDHE 输出作为密钥调度的输入。TLS 1.3 用 HKDF-Extract 提取秘密，再借助带标签的 HKDF-Expand 派生不同用途的材料。Transcript-Hash 对规定范围内的已编码握手消息计算摘要，包含握手消息类型和长度，记录层头部、TCP 头部以及兼容性的 ChangeCipherSpec 均在这个计算范围之外。

    flowchart TD
    E["Early Secret（无 PSK 时用零串）"] --> H["Handshake Secret（混入 ECDHE）"]
    H --> HS["握手流量秘密（两个方向）"]
    H --> M["Master Secret"]
    M --> AS["应用流量秘密（两个方向）"]
    M --> R["Resumption Master Secret"]
派生分支 Transcript 截至 用途
client_handshake_traffic_secret / server_handshake_traffic_secret ServerHello 各自派生握手记录的 key、IV 和 Finished key
client_application_traffic_secret_0 / server_application_traffic_secret_0 服务器 Finished 各自派生初始应用记录的 key 和 IV
resumption_master_secret 客户端 Finished 搭配 ticket nonce 派生恢复用 PSK

无 PSK 的首次连接仍有 Early Secret，输入里的 PSK 用定长零串代替。Handshake Secret 从 Early Secret 的 derived 分支与 ECDHE 输出提取，Master Secret 从 Handshake Secret 的 derived 分支与定长零串提取。图中省略了 derived 标签和 exporter 分支。Record 层再从一个方向的流量秘密分别以 key、iv 标签扩展出实际使用的密钥和 IV。客户端写入用的密钥对应服务器读取用的密钥，反方向用另一组材料。 RFC 8446 §4.4.1 握手摘要 · RFC 8446 §7.1–7.3 密钥调度

5. 服务器用证书和握手签名证明身份

服务器先发送 EncryptedExtensions，再用同一方向的握手密钥保护 Certificate、CertificateVerify 和 Finished。接收端通过三项检查确认服务端身份和握手状态。

检查对象 客户端如何验证 通过后确认什么
Certificate 用本地信任锚验证证书路径，检查 URL 主机名是否匹配证书 SAN，以及有效期、用途和路径约束 服务器证书公钥可以用于认证这个服务身份
CertificateVerify 用叶证书公钥验证当前握手的签名 对端持有证书对应的签名私钥，并对本次握手内容作了签名
Finished 用服务器方向的握手流量秘密派生 Finished key，重算握手摘要的 HMAC 对端掌握正确的握手秘密，双方的握手记录一致

证书链与主机名

叶证书携带公钥、签发者、有效期和 subjectAltName（SAN）等字段。服务器通常发送叶证书和需要的中间证书，根信任来自客户端本地配置的信任锚。证书上的签名用于验证签发关系，客户端还根据本地策略检查证书撤销状态、算法强度等条件。

访问 https://example.com 时，参考身份是 URL 里的 example.com，匹配 SAN 中的 dNSName。若直接以 IP 地址访问，则检查 SAN 中相应的 iPAddress。RFC 9525 将服务身份放在 SAN 中，Common Name 不参与这套匹配。SNI 帮服务器挑证书，客户端仍要单独校验目标身份。 RFC 5280 §6 证书路径验证 · RFC 9525 TLS 服务身份

CertificateVerify 与 Finished 的覆盖范围

在本文的全握手里，服务端用证书私钥对下面的数据签名，摘要覆盖到服务端 Certificate。

这把证书身份和两个 Hello 中的协商参数、临时公钥绑定在一起。主动中间人即使分别为两侧建立共享秘密，也得为被改动的握手生成可用的证书签名。验证所依赖的是正确的参考身份、信任锚和受保护的签名私钥。

随后双方各用自己方向的握手流量秘密派生 finished_key，计算 verify_data = HMAC(finished_key, transcript_hash)。服务器的摘要覆盖到它的 CertificateVerify。本文没有客户端证书认证，客户端的摘要覆盖到服务器的 Finished。如果开启 mTLS，服务器还会发送 CertificateRequest，客户端的 Certificate 和有证书时的 CertificateVerify 插在客户端 Finished 前，并进入相应的摘要。 RFC 8446 §4.4 认证消息

6. HTTP 字节怎样变成加密的 TLS Record

客户端发出自己的 Finished 后，可以紧接着发送 HTTP 请求。前一条消息仍用握手密钥，后面的请求用客户端应用流量密钥。TLS 也允许服务器发出自己的 Finished 后先写应用数据，此时服务器还没收到客户端的握手确认。典型的 HTTP 请求响应仍由客户端先发请求。 RFC 8446 §4.4.4 Finished

以 AES-128-GCM 为例，TLS 记录层做三件事。

  1. 组装待加密内容。 把一段 HTTP 字节加上内层内容类型（应用数据为 0x17）和可选的零填充。内层类型也能表示握手消息或警报，接收端解密后据此分发。
  2. 计算 nonce。 将该方向当前密钥的 64 位记录序号按网络字节序编码，左侧补零至 IV 长度，再与 write IV 异或。序号从 0 开始，每条加密记录递增，换密钥时重新计数。记录序号由两端维护，TCP 序号另属传输层。
  3. 认证头部并加密。 AEAD 以 5 字节外层记录头为关联数据，对内层明文加密并带上认证标签。接收端从头部取长度，按当前方向的 key、IV 和序号重建 nonce，通过认证后才交付明文。

例如在一条记录里放 100 字节 HTTP 数据、1 字节内层类型、无填充，AES-GCM 再加 16 字节认证标签，外层 length 是 117，包含头部总共 122 字节。抓包看到外层类型为 Application Data 时，里面可能是加密的握手、HTTP 或 Alert。未解密时仍可观察 IP、端口、记录长度和流量时序。 RFC 8446 §5.2–5.3 记录保护与 nonce

如果链路是客户端到网关再到后端，客户端 TLS 会话在执行解密的网关处终止。网关到后端的转发方式另行配置，启用 TLS 时会建立独立会话。常见服务用 OpenSSL 等用户态库处理握手和 Record，Linux kTLS 可以把已建立连接的部分记录层收发交给内核。工程上可以分别看新建连接速率、握手 CPU、连接复用率和稳定连接吞吐，定位成本来自建连还是数据传输。 Linux 内核 kTLS 文档

7. 一次往返、会话恢复与 0-RTT

1-RTT 全握手指客户端从发出 ClientHello 到收到并验证服务端首轮握手消息，典型情况下等待一个网络往返，然后发出 Finished 和 HTTP 数据。新建 TCP 连接还要计入 TCP 建连，DNS 也可能另外消耗时间。如果触发 HelloRetryRequest，TLS 再多一次往返。

握手完成后，服务器可以发出加密的 NewSessionTicket。客户端将票据与派生出的恢复 PSK 关联，下次建立连接时提供票据身份，并用 PSK binder 将其绑定到新的握手。服务器接受 PSK 后可以继续用 PSK 完成 1-RTT 恢复，也可以在 PSK 基础上重新做 ECDHE，让协商完成后的流量获得新的前向保密材料。每个新会话都派生自己的应用流量密钥。 RFC 8446 §2.2 和 §4.6.1 会话恢复

0-RTT Early Data 允许启用该能力的客户端在发出恢复用 ClientHello 的同一轮先发应用数据。早期数据的密钥来自 PSK 和 ClientHello 的摘要，此时尚未混入本次 ECDHE。服务端可以拒绝早期数据并继续握手。接受时，应用还要处理跨连接重放的可能性。有扣款或提交任务等副作用的操作需要按应用语义决定能否重放，单看 HTTP 方法不足以判断。HTTP 服务可返回 425 Too Early，让客户端在完成握手后重新发送。 RFC 8446 §2.3 早期数据 · RFC 8446 §8 0-RTT 重放 · RFC 8470 HTTP Early Data

8. TLS 如何更新密钥和关闭连接

长连接可以用握手后的 KeyUpdate 更新某个发送方向的应用流量秘密，随后重新派生该方向的 key 和 IV。发送方用旧密钥保护 KeyUpdate 自身，从下一条记录开始切换。接收方处理消息后同步更新读密钥，另一方向可以单独更新。 RFC 8446 §4.6.3 KeyUpdate · RFC 8446 §7.2 流量秘密更新

双方各自在关闭自己的写方向前发送 close_notify，已经发出错误警报的情况除外。收到 close_notify 表示对端结束了这个方向的 TLS 数据，TLS 1.3 允许两个方向分别关闭。若只看到 TCP FIN 或 EOF，TLS 层无法确认对端是否完整发完，HTTP 层还要按自己的消息定界判断响应是否完整。连接结束后，该连接的流量密钥退出使用，恢复票据所需的状态可以按策略继续保存。 RFC 8446 §6.1 关闭警报

9. 用本地 OpenSSL 验证一次完整握手

在第一个终端用 OpenSSL 3 或更新版本创建临时实验目录和本地证书。记下 pwd 打印的路径，服务器只绑定回环地址。

在第二个终端进入同一目录，用 localhost.crt 作为这条实验连接的信任锚，并明确校验 localhost。这里通过标准输入送入一个带 CRLF 和终止空行的 HTTP 请求。

本地实测协商出 TLS 1.3 和 ALPN http/1.1，证书验证返回 0 (ok)。测试服务器的响应状态行为 HTTP/1.0 200 ok，随后可看到 close_notify。服务端 Certificate 与 CertificateVerify 可在 -msg 输出中辨认，因为这是 TLS 端点解密后的消息日志。只看网络上的记录头时，这些消息位于外层类型为 Application Data 的密文中。OpenSSL 的兼容模式也可能在日志中出现 ChangeCipherSpec，TLS 1.3 密钥切换由握手状态和密钥调度决定。实验结束后可在第一个终端按 Ctrl-C 停止服务器。 OpenSSL s_client 文档 · OpenSSL s_server 文档
