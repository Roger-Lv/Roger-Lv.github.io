从 runc 到 microVM：容器里的内核失守后，宿主机为什么还能守住？

Published2026-11-27|Updated2026-11-27|容器与虚拟化

假设你在做一个多租户开发机平台。Alice 和 Bob 的开发机调度到了同一台 Kubernetes 节点，两个人都可以在自己的环境里运行任意代码。现在，Alice 触发了一个 Linux 内核漏洞，导致内核崩溃。Bob 正在跑的训练任务会不会跟着掉？

用 runc 运行两个 Pod 时，崩溃的是节点内核，Bob 的任务会随节点一起中断。用 Kata 给两个 Pod 分别创建虚拟机时，如果崩溃的是 Alice 的虚拟机内核，Bob 的任务通常还能继续。即使三处运行的是同一版本的 Linux，这个区别依然成立。

“有独立内核更安全”说的就是这件事。要理解它，需要分清两个问题：谁执行租户的系统调用？当这个内核已经失守，谁还在执行租户之间的隔离？

从一次 socket() 调用看起

Alice 的程序调用 socket(AF_INET, SOCK_STREAM, 0) 创建一个 TCP socket。此时甚至还没连接远端，也没有任何网络包需要发出去。

在普通 runc 容器里，这次调用直接进入宿主机 Linux 内核。runc 启动容器时设置好 namespace、资源限制和权限，之后应用像其他 Linux 进程一样发起系统调用，无需经 runc 转发。内核根据 Alice 进程所在的 network namespace 创建 socket。Alice 和 Bob 可以各有自己的路由表，也可以分别监听同一个端口，因为这些网络状态彼此隔离。处理两个租户 TCP 请求的，仍然是同一个内核实例。runc 项目文档 · Linux network namespace 手册

在 Firecracker microVM 里，同一次调用进入 Alice 的虚拟机内核，下文简称 guest 内核。它可以在自己的内存里创建 socket，整个过程无需宿主机替 Alice 建立一个对应的 TCP socket。等到真正向外发包，guest 的网络驱动才把数据交给虚拟网卡。在 Firecracker 的常见配置中，宿主侧后端从 virtio-net 接收数据，再交给 TAP 设备。跨过虚拟机边界的是网络帧，创建 socket 的系统调用早已在 guest 内完成。 Firecracker 架构设计

Kata 和 Firecracker 在这里承担的职责也各不相同。

组件 承担的职责 在这个例子里的隔离粒度
runc 按 OCI 规范在现有 Linux 内核上启动容器进程 容器进程受 namespace、权限和系统调用策略约束，同一节点上的普通容器共享节点内核
Kata Containers 为容器运行时接入轻量虚拟机，在 guest 内创建容器 Kubernetes 下通常一个 Pod 对应一台 VM，同一 Pod 的主容器与 sidecar 共享 guest 内核
Firecracker 作为虚拟机监控器（VMM），借助宿主机的 KVM 运行 microVM 并提供虚拟设备 每台 microVM 运行独立的 guest 内核。平台决定哪些工作负载进入同一台 VM

所以，只有当 Alice 和 Bob 被放进不同的 VM，两人才获得虚拟机级别的隔离。如果把两个工作负载放进同一个 Kata Pod，它们仍要共同信任那个 Pod 的 guest 内核。Kata Containers 架构 · Firecracker 架构设计

一个真实的内核漏洞，能波及谁？

2022 年披露的 CVE-2022-0185 出现在 Linux 文件系统代码中。内核检查挂载参数长度时存在缺陷，可能造成内核堆内存越界写入。阿里云 ACK 的安全公告记录了两类可能后果：节点内核崩溃，或者容器中的进程逃逸并获得宿主机 root 权限。能否触发取决于内核是否已修补，以及容器的权限、user namespace 和 seccomp 等配置是否允许进程触达相关接口。Red Hat 漏洞说明 · 阿里云 ACK 安全公告

把这个真实漏洞放回两台开发机的假设场景。我们让 Alice 面对同样有缺陷的内核，并假设已经满足漏洞的触发条件。

同一次越界写入 Alice 的开发机用 runc Alice 的开发机独占一台 VM
谁解析挂载参数？ 节点内核 Alice 的 guest 内核
哪块内存被破坏？ 节点内核的堆内存 Alice 的 guest 内核的堆内存
如果内核崩溃 整个节点上的工作负载受影响 通常只有 Alice 的 VM 及其中的工作负载中断
如果 Alice 获得该内核的执行能力 管理节点和其他租户的内核已失守 她能控制自己的 VM，宿主机仍在 VM 外实施隔离

在 runc 下，mount namespace 可以决定 Alice 能看到哪些挂载点，seccomp 可以阻止某些系统调用。一旦允许的调用进入有缺陷的代码，负责解析参数的正是维护这些 namespace 的节点内核。在 VM 下，即便同样的缺陷让 Alice 完全控制了 guest 内核，宿主机还掌握着两项她需要的权力：决定她的 CPU 指令能访问哪些物理内存，以及决定她的虚拟设备实际连到什么资源。

即使知道 Bob 的物理地址，Alice 能直接读吗？

假设 Alice 已经可以修改 guest 内核，甚至知道 Bob 的某一页内存在宿主机上的物理地址。她能不能改一下自己的页表，让一个指针指向那一页？

以启用 EPT（Extended Page Tables）的 Intel x86 主机为例，CPU 执行一次内存访问时，最终地址由两级映射共同决定。

地址转换 谁建立映射 它回答的问题
Guest 虚拟地址 → Guest 物理地址 Guest 内核管理自己的页表 这个指针指向 VM 里的哪一页？
Guest 物理地址 → 宿主机物理地址 宿主侧 KVM 管理 EPT，由 CPU 执行转换和权限检查 这台 VM 的这一页落在机器的哪一页？允许读写吗？

举个数字例子。假设 Alice 的 VM 和 Bob 的 VM 都有一个 guest 物理地址 0x4000。宿主机可以把 Alice 的 0x4000 映射到物理页 A，把 Bob 的 0x4000 映射到物理页 B。两个人在各自的 VM 里读同一个地址，CPU 最终读取的是不同的内存。

现在 Alice 把物理页 B 的宿主机地址填进自己的页表。CPU 取到这个数以后，仍会把它当作 Alice 的 guest 物理地址，继续查 Alice 的 EPT。只有宿主侧已向 Alice 授权映射到 B，她的这次访问才可能落到 B 上。知道地址的数值，不能替她建立这条映射。Linux KVM 内存管理文档

这也解释了为什么连“已经控制 guest 内核”都不够。在 Intel 的虚拟化机制下，guest 内核可以运行在自己系统的最高特权级 Ring 0，同时 CPU 仍处于受虚拟化限制的 VMX non-root 模式。普通指令可以直接执行；遇到被配置为需要宿主侧处理的事件，CPU 会发生 VM exit，把控制权交回宿主侧。宿主侧处理程序及其权限由宿主机决定。guest 内核可以更换自己的页表，却无权更换宿主机为它选定的 EPT。Intel 软件开发者手册，第 3C 卷

VM 总要读磁盘，为什么这条通路也有边界？

假设平台在宿主机上准备了两个磁盘镜像 alice.img 和 bob.img，只把前者配置成 Alice 的 Firecracker 虚拟块设备。Alice 在开发机里读取 /etc/passwd，一次未命中缓存的读取大致这样完成。

  1. Guest 内核解析路径。 它在 Alice 的根文件系统里查找 /etc/passwd，由 guest 文件系统确定需要读取哪些磁盘块。
  2. 虚拟块设备接收请求。 Guest 的 virtio-blk 驱动提交读请求，其中包含扇区位置、长度和接收数据的缓冲区。
  3. 宿主侧设备后端完成读取。 Firecracker 从这块虚拟盘绑定的后端 alice.img 读取相应数据，交还给 guest。Firecracker 块设备文档

这里有个很实际的区别。Alice 拿到 guest root 后，可以绕过自己 VM 内的文件权限，直接读取整块虚拟盘。但整块盘对应的仍是 alice.img。即使她自己写一个块设备驱动，接口提供的也是“读这块盘的第 N 个扇区”。选择宿主机上哪个文件作为这块盘后端的配置权，仍在平台手里。

这也说明 VM 边界可能在哪里失效。如果平台误把 bob.img 挂给 Alice，她通过正常读盘接口就能访问 Bob 的数据。 另一种情况是虚拟设备后端或 KVM 自身存在安全缺陷，使 guest 的请求产生了超出接口授权的效果。这属于虚拟化边界自身的问题，需要与前面那个发生在 guest 文件系统里的漏洞分别分析。Firecracker 采用精简的设备模型，并支持用 jailer 降低 VMM 进程权限、用 seccomp 限制其系统调用，正是为了减少宿主侧暴露的代码和权限。Firecracker 架构设计

回到多租户开发机

评审这类平台时，我会追着一个故障问到底：假设某个租户的内核已经完全失守，现在还有谁能阻止它读另一个租户的内存和磁盘？

如果两个租户共享节点内核，失守的恰好是执行这项隔离的内核。如果每个租户独占 VM，即使租户控制了自己的内核，CPU 仍执行宿主侧设定的内存映射，设备后端仍按平台配置选择磁盘。而如果两个租户共用一个 Kata Pod，或平台把同一份敏感存储授权给两台 VM，这些资源就落在共同的信任范围内。对开发机而言，“每租户一台 VM”的价值，最终体现在一个具体结果上：Alice 可以把自己的内核弄崩，Bob 的训练仍然继续。
