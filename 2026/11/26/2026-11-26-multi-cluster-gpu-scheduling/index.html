不使用 Karmada，怎样调度多集群 GPU 作业

Published2026-11-26|Updated2026-11-26|AI Infra
|Views:

训练团队提交一个任务，需要四台各有八张 H100 的机器，四台还要位于同一个 RDMA 域。集群 B 报告有 64 张空卡，却只凑得出两台完整八卡机。即使中心正确地选中了另一座集群 A，两个并发任务仍可能同时拿走账面上最后 16 张卡。选得到集群、占得到资源、把作业送到成员，是三个独立的承诺。

假设一个训练作业的所有 Worker 都跑在同一成员集群，各集群保留自己的调度器，成员 Agent 能主动连到中心。下文用已有的 Kubernetes API、etcd 和 Agent 设计一条链路。示例中的 ClusterInventory、Reservation、Work 都是平台拟定的 CRD，容量、评分和超时都是演算值。

四个控制器各自写什么

逻辑模块 读取什么 有权写什么
Cluster Manager 已注册的身份、成员 Lease、维护计划 Cluster 的就绪条件，准入新任务与排空策略
Resource Manager 成员汇总的节点、Pod 请求与分配、设备、配额、拓扑 带采样时间和版本的 ClusterInventory
Global Scheduler 作业需求、租户配额、库存、已有预留 有版本的集群选择和资源账本，驱动预留状态
Work Distributor 已获准执行的绑定、对象 UID 和代次 每成员的 Work；成员 Agent 负责同步本地 CR 及回报

初期四个协调循环可以放进同一个 Controller Manager。它们共用平台现有 API，但有各自管理的字段、队列和指标。中心决定把作业交给 A，A 的 kube-scheduler 或 Volcano 再给每个 Pod 找节点。平台可以从成员得到失败原因，重新排队或更换候选。

集群健康和 GPU 库存分开记

每个成员用独立凭证注册。中心分配集群身份、工作命名空间和最小 RBAC。Agent 续对应的 coordination.k8s.io/v1 Lease，并上报版本和容量。管理员决定 spec.schedulable；成员无权自行取消维护状态。假设每 10 秒续租一次、30 秒未收到续租就标记 Unknown，这个阈值要用跨地域延迟和丢包数据校准。失联时先暂停新调度；存量工作是否停下，需要独立的执行权证据。退役时先停止接单，再排空，最后撤销凭证。Kubernetes Lease

成员 Agent 用 Informer 观察 Node、Pod、ResourceQuota、启用 DRA 时的 ResourceClaim，以及设备插件或业务系统维护的 GPU 与网络拓扑。先在成员侧去重汇总，再上传快照，附采样时间、序号、库存口径和拓扑域标识。中心只对足够新的库存进行选址；库存过期时触发刷新。下表假设三个集群 GPU 都是 H100，且暂时没有尚未记入分配数的预留。

分配要按设备或实际申请量计账。某租户占用的 GPU 在一分钟内利用率为零，可能正在等数据，所有权仍在租户手上。Prometheus 的利用率适合识别热点、调优打分。控制面计算还能承诺多少资源时，要扣除已分配资源和尚未计入已分配数的有效预留。二者通过 workload UID 和执行代次去重。

四台八卡机怎样选出一个集群

可以借鉴 Kubernetes Scheduling Framework 的扩展点，在平台调度器内实现以下流程。队列按租户与作业优先级取任务；PreFilter 把业务 CR 解析成四台完整八卡机和同域约束；Filter 检查健康、新鲜度、SKU、拓扑、配额、数据集与存储可达性；Score 只比较留下来的候选。之后 Reserve 尝试预留，Permit 等成员准入，Bind 固化结果，失败由 Unreserve 释放。每个阶段都应留下可查询的拒绝原因。Kubernetes Scheduling Framework

用上表的数据，B 在 Filter 阶段出局。A 余卡较少，但刚好能把四台机器装在一个域里；C 也满足硬约束。假设 A 已缓存这份作业的 checkpoint，C 的单位 GPU 成本更低。给每项指标先归一到 0–100 分，并统一为越高越好；最后用“各项权重乘分数之和 ÷ 权重总和”比较。权重只改变 A、C 的先后，不能让 B 凭便宜重新入围。

最后 16 张卡，只能承诺一次

中心看到 A 还有 16 张卡。任务甲和乙各要 16 张，都读到同一份快照，也都能成功创建名字不同的 Reservation。此时 API 只保证创建了两个不同对象；没人对同一份余额做过互斥更新。

我的做法是给每个独占资源池设一个权威账本，在同一个 Kubernetes 对象里记录可用预算、按任务 UID 与尝试代次索引的活动预留，以及它们对应的拓扑份额。用带原始 metadata.resourceVersion 的 Update 条件写入。下面的伪代码只描述单账本上的一次扣减。

若甲先写成功，乙用旧版本更新会收到 409 Conflict；重读后余额为零。进程若在扣账成功、写 Reservation.status 前崩溃，新副本能按同一 key 找回预留。租户配额跨池时，还要对其权威账本单独取得额度，再明确补偿责任；任一额度没拿齐都不能执行。Kubernetes API 的这个保证止于单对象，不会替 Reservation、业务 CR 和 Work 做跨对象事务。Kubernetes API 更新与资源版本

成员还要真正占住资源。 中心发一份带 UID、代次和期限的准入请求，成员的队列或准入控制器将它和本地提交的作业一起计账。带物理拓扑要求时，还要能约束后续的整组节点分配。Agent 再查一次余卡只能得到一次观测；查完到启动之间，本地任务照样可能把卡拿走。使用 Kueue 时要区分逻辑配额预留与拓扑感知准入，并验证所有竞争负载都受同一机制约束。Kueue 作业准入

中断位置 恢复时的处理
中心已扣账，成员拒绝准入 核对 UID 和代次，撤销对应预留并重排
成员已准入，确认消息丢失 用同一 key 查询已有准入，重发确认；进入待核实状态期间保留份额
中心等待超时，旧成员仍可能执行 停止签发旧代次的新 Work；先确认撤销，或让执行端强制拒绝旧令牌，再释放或重派
预留转为实际占用，库存随后上报 用同一身份将账本条目转为已分配，和新快照对齐，避免重复扣卡
作业取消或完成 先确认本地占用已释放，再幂等归还份额；重复回调不重复入账

用 Work 交付通过准入的作业

下面是平台自己的 Work 协议示例。生产协议还需定义版本、准入凭据的校验和成员可执行的资源范围。已通过准入的作业要引用同一份预留；成员只能兑现仍有效的执行代次。

Agent 用 Informer 监听本集群命名空间的 Work，WorkQueue 按键退避重试。RESTMapper 将 GVK 映射到 GVR，Dynamic Client 通过 Server-Side Apply 写入平台负责的字段。平台还需验证允许的资源类型和目标租户命名空间，用受限身份执行，防止一份 Work 越过成员授权边界。已有同名对象先核对归属 UID，遇到字段冲突让负责人决策。成员业务 Operator 负责把 TrainingJob 翻译成实际工作负载。Server-Side Apply 字段所有权

API 至少公开三个不同条件：Scheduled 表示已有集群绑定，Applied 表示成员 API 已接受相应代次的 CR，Running 表示业务 Operator 观察到实际训练启动。它们各自带目标集群、尝试号和观测代次，过期回报不能覆盖新一轮状态。删除时使用 Finalizer 等待成员确认清理；断线重连先 List 再 Watch，对丢失和重复事件均按当前期望收敛。多副本 Agent 可以选主，重试和所有权检查仍应保持幂等。

哪些部分可以直接采用开源实现

方案 能直接接走什么 平台还要负责什么
自研 Work + Agent 复用现有 API、etcd 与成员主动出站连接 注册、授权、分发、状态和清理协议，以及 GPU 决策
OCM Hub 上的 ManagedCluster、Placement/PlacementDecision、ManifestWork，成员侧注册与 Work Agent GPU 权威账本、原子预留、资源兑现和业务字段解释
MultiKueue Manager/Worker 作业派发、本地队列准入和作业状态同步 对接支持的 Job 类型，配置队列、网络、拓扑和物理容量保证
Karmada 独立控制面上的通用分发策略、差异覆盖、多集群编排与故障转移机制 GPU 准入、拓扑约束、checkpoint 与执行权隔离，以及新增控制面运维

OCM 适合以现有 Kubernetes 集群作 Hub。Placement 产生 PlacementDecision，可引入 AddOnPlacementScore 参与评分；平台根据选中的成员创建 ManifestWork，Work Agent 执行，并可通过 JSONPaths 只回传关注的业务字段。选中了集群只是一个决策结果，GPU 份额仍要落在账本和成员准入上。OCM 集群注册 · Placement · ManifestWork

MultiKueue 更适合已经采用 Kueue 的批作业。Manager 上的 Workload 获得逻辑配额后，dispatcher 将候选 Workload 送往一个或多个 Worker。某个 Worker 准入后，Manager 在入选集群创建对应 Job，清理其他候选，并同步作业状态。可以用 external dispatcher 定制候选选择。常规连接由 Manager 访问 Worker API，网络规划要单独验证，开发机等自定义类型也要确认是否有对应的 Job 集成。MultiKueue 调度流程 · 多集群拓扑配置

怎样分阶段落地

  1. 先验证指定集群下发。 交付 Cluster、Inventory、Work 和成员 Agent；用断线期间更新再删除的开发机检验能否收敛。验收看对象实际状态、归属和清理结果。
  2. 再打开自动选址和预留。 实现 Filter、Score、单账本扣减与成员准入。用两个并发请求争最后 16 张卡，分别在扣账前后、成员确认前后重启控制器；验收看最多一个作业取得有效执行权，账本最终对平。
  3. 最后接 Spot、跨集群抢占和容错续训。 在旧成员仍能写 checkpoint 的网络分区里演练迁移，验证旧代次被写入端拒绝，再测恢复耗时。账本竞争、库存时效、准入延迟和因 GPU 碎片导致的拒绝次数，都会影响下一步该优化哪里。

对已有 Agent 的团队，我会把第一轮研发投入留给拓扑库存、原子预留和本地准入。若团队的反复故障主要出在 CR 分发，就先评估 OCM 等现成实现。决定引入完整多集群编排前，可以沿一份真实 Job 算清研发和长期运维责任。AI 算力平台该不该引入 Karmada？
