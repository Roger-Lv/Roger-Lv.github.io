Kubernetes Admission Webhook 的注册机制与请求生命周期

发表于2026-11-19|更新于2026-11-19|AI Infra
|浏览量:

在 Kubernetes 训练平台中，提交一个作业后，常见的两种结果是：API 直接返回“禁止使用这个队列”；或者作业创建成功，但一直等待 GPU。

这两种结果发生在不同阶段。前者可以由 Admission Webhook 在 API 请求处理过程中作出决定；后者通常由作业控制器和调度器在对象创建之后处理。

Admission Webhook 的核心机制是：我们运行一个 HTTPS 服务，再通过 Kubernetes API 对象声明调用规则；API Server 在处理匹配的请求时，同步调用这个服务，根据响应继续修改、接纳或拒绝请求。

本文以 VolcanoJob 为例，介绍 Webhook 如何注册、API Server 如何回调、AdmissionReview 如何表达校验结果，以及它与 Controller、资源调度之间的职责边界。文中的 training-policy-webhook 是假设的训练平台组件，队列限制和默认值均为示例策略，并非声称 Volcano 默认采用这些规则。

一、Admission Webhook 在 API 请求中的位置

客户端向 Kubernetes 提交对象时，API Server 需要处理身份认证、权限检查、对象校验和持久化等工作。Admission，也就是准入控制，位于认证与授权之后、对象持久化之前。它能够检查请求，并在允许的阶段修改请求中的对象。1

这里需要区分两个“Webhook”概念：

名称 所在位置 作用
MutatingAdmissionWebhook、ValidatingAdmissionWebhook API Server 内置的准入插件 读取注册配置，匹配请求，调用外部服务
我们编写的 Webhook Server 独立运行的 HTTPS 服务 执行平台自己的修改或校验逻辑

业务代码运行在外部服务中。API Server 内置的是调用机制。1

两类动态 Webhook 的主要分工如下：

类型 能否修改对象 能否拒绝请求 常见用途
Mutating Webhook 能，通过返回补丁 能 注入字段、补充平台默认值
Validating Webhook 不能 能 检查字段关系、限制允许的配置

从理解调用链的角度，可以把相关阶段概括为：修改对象、检查修改后的对象、通过后持久化。Mutating 阶段在 Validating 阶段之前；对象自身的 API 校验也必须通过。实际请求还可能包含类型转换、默认值处理等步骤，不能把这个概括当作全部内部处理步骤的严格排序。2

Admission 并不拦截所有请求。GET、LIST、WATCH 这样的读取操作不经过准入控制；创建、更新、删除等操作是否触发某个 Webhook，还取决于它的匹配规则。1

二、所谓注册，是向 API Server 声明调用规则

实现一个可用的 Webhook，需要准备三个部分：

  1. 服务实现：接收 AdmissionReview 请求，运行检查或修改逻辑，返回 AdmissionReview 响应。

  2. 访问入口：让 API Server 能通过 HTTPS 访问服务，配置服务端证书和信任关系。

  3. 注册对象：创建 ValidatingWebhookConfiguration 或 MutatingWebhookConfiguration，描述什么请求要调用哪个端点。2

“组件向 API Server 注册”是一种方便的说法。准确地说，注册是创建 Kubernetes 配置对象。这个对象可以由 Helm、安装清单、Operator，或者程序启动逻辑创建。Webhook 服务进程本身不一定负责注册。

还要区分两层配置：程序中的 /validate-vcjob 路由决定服务收到请求后调用哪个处理函数；WebhookConfiguration 决定 API Server 何时向这个路由发请求。只写好了 HTTP Handler，API Server 并不会自动发现它。

正常的业务拒绝，应以 HTTP 200 返回有效的 AdmissionReview，再通过 allowed: false 表达。 上例 status.code: 403 属于协议中的拒绝信息，并不是要求 Webhook 的 HTTP 层直接返回 403。HTTP 层异常会进入调用失败的处理路径，语义不同。25

创建请求被拒绝时，本次请求不会创建新对象；更新请求被拒绝时，本次变更不会落盘，原有对象仍然存在。后者尤其重要：新规则不会自动修改或删除已有对象，但它们之后进行匹配的更新时，即使只是修改标签，也可能因为最终对象不符合规则而遭到拒绝。上线时应考虑存量迁移或基于 oldObject 的过渡策略，并确认目标资源允许修改哪些字段。

四、Mutating Webhook 如何修改对象

修改型 Webhook 通常通过返回 JSON Patch，让 API Server 修改当前处理中的对象。Webhook 不需要再向 API Server 发起一次更新请求来完成这次修改。45

这里有三个实现细节：

  • 只补缺省值。 用户显式设置 0 或其他合法值时，不应把它当成“未填写”。

  • 保持幂等。 同一个对象再次进入处理函数时，不应不断追加内容或反复改变默认值。

  • 校验最终状态。 不应依赖多个 Mutating Webhook 的固定调用顺序；关键约束放到 Validating 阶段检查，因为后续修改可能影响前面的结果。6

本例限定在 CREATE 时默认，避免某次普通更新意外改变已有作业的保留策略。如果实际业务要求所有作业都必须设置 TTL，则应明确设计存量迁移和更新校验，不能靠一个“顺手补默认值”的逻辑隐含完成。

五、一次创建请求的完整调用链

下面把注册后的运行过程串起来。图中用同一个 Webhook 服务承载两个端点，省略其他准入插件和部分内部校验步骤；假设请求已经命中配置规则。

    sequenceDiagram
    participant U as 客户端
    participant A as API Server
    participant W as Webhook 服务
    participant E as etcd
    participant C as Controller
    U->>A: 创建 VolcanoJob
    A->>A: 认证与授权
    A->>W: AdmissionReview /mutate-vcjob
    W-->>A: allowed=true 与补丁
    A->>A: 应用补丁并完成相关校验
    A->>W: AdmissionReview /validate-vcjob
    alt 明确拒绝
        W-->>A: allowed=false 与原因
        A-->>U: 创建失败
    else 所有检查通过
        W-->>A: allowed=true
        A->>E: 持久化对象
        E-->>A: 写入成功
        par 返回客户端
            A-->>U: 创建成功
        and 传播对象变化
            A-->>C: Watch 事件
            C->>C: 执行协调逻辑
        end
    end

这个调用链说明，Webhook 位于原始 API 请求的同步路径上。它迟迟不返回，客户端的写请求也会等待；Controller 则通过观察已经存在的对象，持续推动实际状态接近期望状态。17

图中把创建成功响应和 Watch 事件画成并行分支，是为了避免一个常见误解：不需要等客户端收到成功响应，Controller 才“被允许”开始工作。对象成功持久化后，响应返回和变化传播之间不应被业务代码假定为严格的先后关系。

还需要记住，Webhook 的 allowed: true 发生在持久化之前。它证明当前检查通过，不能用来证明作业已经入库，也不能用来证明作业已经开始执行。

平台对它至少会作出三类不同决策：

阶段 主要问题 典型结果
API 准入 请求的对象定义是否允许进入集群？ 补充 TTL、允许创建，或拒绝不符合队列规则的请求
Controller 协调 已保存的作业需要哪些关联对象和状态转换？ 根据作业推进 PodGroup、Pod 等对象的创建和状态管理
调度与资源准入 队列和集群当前能否承接作业，Pod 应落到哪里？ 进入等待、满足准入条件、选择节点并执行绑定

Volcano 的 enqueue Action 会处理作业进入可调度阶段的资源准入；后续分配还涉及节点资源与 Gang 等约束。具体行为取决于 Volcano 的版本、调度配置和插件。8

因此，在本例策略下：

情况一：把队列改成 team-b。 自定义 Validating Webhook 返回拒绝；本次创建失败，没有新作业进入后续调度流程。

情况二：队列正确，但当前 GPU 不足。 API 请求可以通过，Job 对象可以保存下来；后续组件依据队列和资源条件决定何时推进运行。具体停留在什么状态，取决于启用的准入和调度策略。

情况三：队列正确，资源条件也满足。 API 准入通过后，控制器与调度器继续处理，最终由节点上的 kubelet 负责启动已绑定的 Pod。

这里的设计原则是：需要持续等待、重试和观察资源变化的工作，应放在协调或调度循环中。 不应让 Webhook 保持 HTTP 请求，等待未来某个时刻释放 GPU。根据 API 请求同步等待的性质，可以直接推导出这种做法会把资源排队变成 API 请求超时。

Webhook 也可以修改对象，让它携带后续等待所需的状态，例如注入某种暂停标记或调度门控。但 Webhook 完成对象修改后就应返回，后续等待与解除条件由相应组件处理。

七、failurePolicy 处理的是调用故障

failurePolicy 最容易引发的误解是：配置 Ignore 之后，Webhook 的拒绝是否也可以被忽略？

答案是否定的。它处理的是调用异常或超时，并不把正常返回的业务拒绝变成允许。23

Webhook 调用结果 failurePolicy: Fail failurePolicy: Ignore
有效响应，allowed: true 继续其他检查 继续其他检查
有效响应，allowed: false 拒绝请求 拒绝请求
连接失败、TLS 校验失败、超时等调用错误 以准入调用失败结束请求 忽略本次调用错误，继续其他检查

所以，“Webhook 认为不允许”和“API Server 没能正常调用 Webhook”是两条处理路径。

在示例训练平台中，队列隔离属于平台希望强制保证的约束，因此示例选择 Fail。这同时意味着：一旦该 Webhook 不可用，匹配的 Job 写请求可能受阻。选择策略时，需要同时考虑规则的重要程度和服务的可用性。

Ignore 可以降低调用故障对 API 写入的影响，但不能保证该规则一定执行。采用它的前提，应当是平台明确接受这段时间内可能放过未检查的请求，或者存在其他可靠的约束机制。

同样，不要为了“拒绝用户”直接返回 HTTP 500。那表示服务调用出了问题，会受到故障策略影响。业务拒绝应按 AdmissionReview 协议表达。

八、部署和排障时，沿着调用链定位

TLS、Service 和网络必须同时成立

如果使用 clientConfig.service，API Server 需要信任 Webhook 服务端证书。配置中的 caBundle 提供用于验证服务端证书的 CA；证书需要包含与 Service 相应的 DNS 身份，例如本例的：

同时，API Server 到该服务的网络路径必须可达。仅仅在某个业务 Pod 内能访问 Webhook，并不能证明控制平面也能访问。23

因此，部署时需要把几项配置对应起来：注册对象中的命名空间与 Service 名称、Service 的端口与后端监听端口、证书中的服务名，以及签发 CA。它们中任何一处不一致，都可能在业务校验逻辑运行之前导致调用失败。

不要把耗时任务放进准入处理

Webhook 增加了 API 写请求的延迟，应缩小匹配范围、控制执行时间，并减少对外部服务的同步依赖。多个修改型 Webhook 还会累积延迟。6

本例中的队列规则可以来自稳定的平台配置。如果每次校验都串行查询多个业务系统，那么这些系统的延迟和故障会传递到 Job 创建过程。使用缓存时，也必须明确：缓存陈旧到什么程度仍可以接受，数据不可用时应当拒绝还是放行。这是业务规则的可靠性设计，不能只由默认错误处理决定。

sideEffects 是对实现行为的声明

sideEffects: None 表示声明该 Webhook 不产生对象修改之外的副作用，并不会自动阻止程序调用外部系统。3

例如，在准入时直接创建云主机、扣减外部额度或写入不可回滚的账单，会遇到一个问题：Webhook 完成后，后续校验或对象持久化仍可能失败。此时外部动作已经发生，Kubernetes 对象却未必存在。

更容易恢复的设计，是在对象成功创建后，由 Controller 依据对象状态执行可重试、可协调的外部操作。7

如果使用服务端 dry-run，Webhook 也需要遵守对应的副作用声明和 request.dryRun 语义。试运行不是“只在本地检查 YAML”，它仍可能触发服务端准入流程。35

九、写 Webhook 之前，先判断规则应该放在哪里

Webhook 适合把平台逻辑接入准入流程，但每增加一个外部回调，就增加一项需要部署、升级和维护的服务依赖。

可以先按规则性质选择实现位置：

需求 优先考虑的位置
字段类型、范围、必填项、静态默认值 CRD 的 OpenAPI Schema 与默认值
同一自定义资源内部的字段关系 CRD 的 CEL 校验规则
可用声明式表达式描述的集群准入策略 ValidatingAdmissionPolicy 与对应 Binding
复杂的准入判断、必须接入外部平台信息 Admission Webhook
创建关联资源、持续观察状态、重试外部操作 Controller
等待资源、队列公平性、节点分配 调度与资源准入组件

CRD Schema 和 CEL 可以直接表达多种结构与字段约束；ValidatingAdmissionPolicy 则提供 API Server 内执行的声明式校验机制。这些能力可以减少为了简单规则而单独维护 HTTPS 服务的需要。1011

前文的 TTL 默认值示例主要用来说明 JSON Patch 协议。若它只是某个自定义 API 的统一静态默认值，Schema 默认值通常更直接；若默认值取决于租户、环境或平台策略，才需要进一步评估 Webhook 等方案。对第三方 CRD，还应考虑升级和维护责任，避免把业务需求变成难以跟随上游升级的改动。

设计 API 扩展时，先明确规则约束的是“请求中的对象”，还是“对象创建后的运行过程”。前者可以进入准入逻辑，后者通常需要一个能够持续观察和协调的组件。这个职责划分，会直接影响故障范围、重试方式和系统的可维护性。
