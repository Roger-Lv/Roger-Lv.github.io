Volcano Action 与 Plugin 如何协作：生命周期、扩展点与调用关系

Published2026-11-19|Updated2026-11-19|AI Infra
|Views:

源码基准：Volcano v1.16.0。

本文聚焦 Scheduler 中的 Action、Session 与调度插件，使用对照表解释实际调用关系。ssh、svc、env 等 Job Controller 插件属于另一套生命周期，不纳入下面的 Action 映射。

理解 Volcano 时，很容易把插件想成一组依次运行的步骤：先执行 priority，再执行 gang，最后执行 predicates。实际结构更适合用“流程与策略”来理解：Action 组织调度流程，Plugin 提供策略函数，Session 保存本轮状态并负责调用、组合这些函数。

因此，“插件融入各个 Action 的执行过程”这个理解基本正确，但还需要补上一个边界：插件实例的生命周期属于 Session；Action 在执行过程中使用插件注册的回调。 同一个插件可以服务多个 Action，同一个 Action 也会使用多个插件。Session 框架

1. Session、Action、Hook、Plugin 分别是什么

概念 负责的事情 示例
Session 保存一次集群调度周期的快照、策略回调和临时核算 本轮的 Jobs、Queues、Nodes，以及已经模拟的分配
Action 决定执行什么调度流程 enqueue、allocate、preempt、reclaim
Hook / 扩展点 定义流程在某个位置要询问什么问题 JobEnqueueable、Predicate、NodeOrder、Reclaimable
Plugin 为一个或多个扩展点提供具体实现 gang、capacity、predicates、nodeorder

例如，allocate 处理“给待调度任务选择节点并形成可提交分配”的流程。在其中，它需要依次解决队列排序、作业排序、额度、节点约束、节点偏好和 Gang 条件等问题。不同问题对应不同扩展点，再由插件提供答案。Allocate 实现

这里有三层不同的对应关系：

  • Action 与扩展点是多对多关系。 allocate 和 backfill 都可以使用节点过滤、节点打分；一个 Action 也会调用多个扩展点。
  • Plugin 与扩展点也是多对多关系。 capacity 不只注册一个函数；同一个排序或过滤扩展点也可能有多个插件实现。
  • Action 与 Plugin 的关系由扩展点连接。 配置了一个插件，并不意味着每个 Action 都会调用它的每个函数。

这些关系由 Session 中的注册表和分派逻辑连接起来。扩展点实现

1.1 Session 怎样把扩展点接到插件

拿 JobOrder 来看，框架会把注册与调用分成两个入口。插件在 OnSessionOpen 中调用 ssn.AddJobOrderFn(插件名, 比较函数)，Session 将函数存到本轮的 jobOrderFns[插件名]。AddJobReadyFn 会写入另一张 jobReadyFns 表。扩展点决定用哪张表，插件名决定从表里取哪一个回调。 因此，同一插件可以在多张表中有记录，同一张表也可以容纳多个插件。同名插件如果对同一个扩展点重复注册，后写入的函数会覆盖先前的记录。Session 扩展点实现

真正比较作业时，allocate 为每个队列创建以 ssn.JobOrderFn 为比较器的优先队列。比较器依次遍历 tiers 和其中的插件，检查该插件的 enableJobOrder，再按配置中的插件名查表。只有开关启用、且查到对应回调时，才会执行这个插件的比较函数。配置加载了谁、谁注册了回调、这次调用会执行谁，是读代码时要分开检查的三件事。allocate 入口 Session 作业排序

1.2 用 JobOrder 和 JobReady 看清多对多

扩展点 v1.16.0 中的回调示例 Session 如何使用返回值
JobOrder priority 比优先级，gang 比作业当前是否就绪，drf 比主导资源份额 第一个非零比较结果决定先后。各回调都返回 0 时，按创建时间和 UID 排序
JobReady gang 检查任务、子作业和整个作业的就绪条件 任一参与的回调返回 false，整体就绪检查失败
JobPipelined gang 检查任务、子作业和整个作业是否满足预留条件 按扩展点自己的 tier 投票规则组合 Permit、Reject 和 Abstain

假设排序插件在配置中的顺序是 priority → gang → drf，三者都启用了作业排序。比较同一队列里的两个作业时，如果优先级不同，priority 就能决定结果。如果优先级相同、两个作业的就绪状态也相同，前两次比较都返回 0，才会轮到 drf 比份额。这一次调用里，三种策略按顺序处理同一个问题。priority gang drf Session 比较规则

再看同一个 gang 插件。把它的 enableJobOrder 设为 false 后，Session 会在作业排序时跳过它。若它的 enableJobReady 仍开启，gang 的就绪回调仍能参与 allocate 在提交临时分配前发起的 JobReady 检查。配置开关控制的是某个插件在某个扩展点上的参与，具体返回值怎么影响调度，由该扩展点的分派规则和 Action 的调用位置决定。配置字段 gang 注册代码 allocate 提交检查

2. 一轮调度中的插件生命周期

2.1 插件先注册，Action 再调用

v1.16.0 的调度器每轮打开一个 Session，按照配置执行各个 Action，最后关闭 Session。打开时会查找插件 builder，构造本轮插件对象，并调用 OnSessionOpen。调度主循环 插件创建与关闭

时机 框架做什么 插件做什么 是否处于某个 Action 内部
Session 开始 创建本轮上下文和插件实例 执行 OnSessionOpen，初始化状态并注册回调 否，发生在配置的 Action 执行之前
Action 执行 在排序、过滤、准入、回收等位置调用 Session 的扩展点 对具体输入返回比较结果、允许/拒绝、得分或候选集合 是
临时分配与回滚 更新本轮 Task、Node 等状态，触发资源变化通知 更新配额、份额或其他本轮核算 通常由 Action 的操作间接触发
Session 结束 调用关闭回调并处理状态更新 执行 OnSessionClose，完成本轮收尾 否，发生在本轮 Action 执行之后

下面的时序图省略具体插件名称，用一个 Plugin 参与者表示本轮加载的插件集合：

    sequenceDiagram
    participant R as Scheduler
    participant S as Session
    participant A as Action
    participant P as Plugin
    R->>S: OpenSession
    S->>P: 构造插件，调用 OnSessionOpen
    P->>S: 注册策略回调与事件处理器
    loop 按配置执行各个 Action
        R->>A: Execute(session)
        loop 排序、准入、过滤、评分等决策点
            A->>S: 调用扩展点
            S->>P: 分派到启用的回调
            P-->>S: 返回判断或策略结果
            S-->>A: 返回组合后的结果
        end
        A->>S: 临时分配、提交或回滚
        S->>P: 按操作触发资源变化通知
    end
    R->>S: CloseSession
    S->>P: OnSessionClose

图中的资源变化通知表示对应操作会触发相关处理器，不表示每次 Commit 都统一再调用一次所有 Allocate 回调。临时分配和回滚时的记账有自己的发生位置。Statement 实现

2.2 同一轮中不会为每个 Action 重建所有插件

假设配置包含 enqueue、allocate、reclaim、backfill，本轮的容量插件可以在准入、分配和回收等位置反复参与判断。它不会因为从 allocate 切换到 reclaim，就重新按旧快照初始化全部用量；分配和回滚事件会维护本轮核算。

另一方面，Session 结束也不等于 Job 结束。一个作业可以等待或运行很多轮；部分插件还通过独立缓存或持久化维护跨轮状态。不要把普通插件实例的生命周期与全部业务状态的存续时间混为一谈。框架生命周期

3. Action → 扩展点 → 插件总表

下表列出 主要扩展点和可能参与的代表插件，不是每条分支的完整调用栈，也不是默认启用清单。是否实际调用某个插件，取决于 actions、tiers、回调开关、插件实现和当前执行分支。

各行按职责排列；真正的 Action 执行顺序以 actions 配置为准。调度主循环

Action 它组织的流程 主要扩展点或策略调用 可能参与的代表插件
enqueue 为 Job 排序，判断是否允许入队，并记录入队后的状态 QueueOrderFn、JobOrderFn、JobEnqueueable、JobEnqueued capacity 或 proportion；overcommit、resourcequota；以及相关排序插件
allocate 选择 Queue / Job / Task，寻找节点，形成满足要求的分配 排序、Allocatable、PrePredicateFn / PredicateFn、节点打分、JobReady 等 priority、drf、gang；capacity 或 proportion；predicates、nodeorder、binpack，以及设备与拓扑插件
backfill 对适用的 BestEffort 任务补充调度机会 JobValid、排序、PrePredicate、节点过滤、节点打分、BestNodeFn，随后调用 Session 的分配方法 gang 的有效性检查；predicates、nodeorder、binpack 等过滤和评分插件
preempt 在同一队列范围内组织传统抢占 JobStarving、Preemptable、节点过滤/评分、Allocatable 等 priority、drf、gang、conformance、pdb、cdp 等；另有配额和节点放置相关插件
reclaim 跨队列寻找可回收资源，并验证申请方的调度计划 Overused、Preemptive、Reclaimable，以及相应路径中的 JobPipelined capacity 或 proportion；gang、drf、conformance、pdb、cdp 等
gangpreempt 组织面向 Gang 的队列内抢占，对候选集合进行分组和放置验证 UnifiedEvictable，类型为 GangPreempt；成组放置验证和 JobPipelined 等 受害者筛选的代表是 priority、gang、conformance；节点放置仍使用相关策略
gangreclaim 组织面向 Gang 的跨队列回收，并验证成组放置结果 Preemptive、UnifiedEvictable，类型为 GangReclaim；JobPipelined 等 受害者筛选的代表是 capacity、gang、conformance；另有排序和节点放置策略
shuffle 根据重调度策略取得受害任务，并发起驱逐 VictimTasks，随后对候选调用 ssn.Evict rescheduling、tdm，以及参与 VictimTasks 的 pdb 等保护插件

对应实现：enqueue、allocate、backfill、preempt、reclaim、gangpreempt、gangreclaim、shuffle。

3.1 enqueue 不会在这里直接调用 JobValid

容易因为名字相近，把“作业合法性检查”都放进 enqueue。v1.16.0 的 enqueue 主要调用排序、JobEnqueueable 和 JobEnqueued，没有直接调用 JobValid。

该版本还有一个分支：PodGroup 的 MinResources 为空时，可以跳过 JobEnqueueable 投票条件，随后进行入队通知并更新 Inqueue。由此可见，表中的“主要回调”也不意味着每个 Job 必然调用全部回调。enqueue 源码

3.2 backfill 也会给节点打分

backfill 不仅调用节点过滤，也会调用 Batch / Map / Reduce 等节点评分路径，再选择节点。因此，同一个 nodeorder 或 binpack 策略可以被不同 Action 使用。backfill 源码

还要区分两个同名附近的概念：backfill 中调用 ssn.Allocate，是在调用 Session 的分配方法；它不代表 backfill 又启动了一遍 allocate Action。

3.3 配额插件的“或”有实际含义

表中的“capacity 或 proportion”表示两种不同的队列份额管理方案。它们在传统路径中可能参与相似决策点，但实现和回收边界不同；尤其不能把传统 Reclaimable 能力自动映射到新的 UnifiedEvictable 路径。第 6 节会专门说明这一点。capacity proportion

4. 展开 allocate：一个 Action 如何使用多个插件

假设待调度 Job 有 4 个成员，每个成员请求 1 GPU，最低调度规模是 4。下面按决策职责展开 allocate；拓扑、子组和缓存等分支可能改变实际遍历方式，多个步骤也可能在循环中重复发生。

决策点 allocate 要回答的问题 主要扩展点 代表插件或框架机制
选择 Queue 本轮先给哪个队列调度机会？ QueueOrderFn capacity 或 proportion；启用时的层级公平策略
选择 Job 同一队列中先考虑哪个作业？ JobOrderFn priority、drf、gang 等
选择 Task 该作业内先安排哪个成员或角色？ TaskOrderFn 等排序入口 priority、task-topology 等
检查队列额度 这个队列还能分配当前 Task 吗？ Allocatable 等 capacity 或 proportion
过滤候选节点 节点是否满足资源、亲和、污点、存储或设备约束？ PrePredicate、Predicate 及基础资源适配 predicates、deviceshare、numa-aware 等
给候选节点评分 合格节点中，哪个更符合放置偏好？ NodeOrder 及 Batch / Map / Reduce 评分路径 nodeorder、binpack、resource-strategy-fit、usage 等
临时分配 先把这个 Task 放进本轮资源视图，会怎样影响余额？ 分配操作及 AllocateFunc 事件处理器 Statement；capacity、proportion、drf 等的本轮记账
检查整体可运行性 当前分配是否达到 Job 最低成员和任务组条件？ JobReady 等 gang 等已启用的条件判断
提交或撤销 本轮操作是否可以提交，失败时怎样恢复？ Commit / Discard，撤销时的 DeallocateFunc 等 Statement 和相关插件的记账处理器

这个表说明：allocate 提供的是完整流程，而没有把所有调度策略硬编码成一个算法。 同一流程可以接入不同的排序、资源治理、设备和拓扑策略。allocate 实现

4.1 Gang 在什么时候阻止不完整分配

如果只能为 3 个成员找到位置，而新作业要求最低 4 个成员，gang 的 JobReady 判断可以阻止把不足规模的分配当成完整可运行结果提交。v1.16.0 的 allocate 提交路径会检查 JobReady；仅有 Pipelined 的未来资源规划，不等于已经可以立即绑定。allocate 的提交条件

4.2 为什么需要分配和回滚事件

设队列本轮还有 2 GPU 额度。为一个 1 GPU Task 做了临时分配之后，后续 Task 的额度检查应看到剩余 1 GPU。如果整个作业最终无法提交，又要把相应临时占用还回去。

Allocate / Deallocate 事件处理器就是这种协作的一部分。它们让同一轮内各个决策使用一致的资源账本。Statement capacity 记账

Commit 表示提交本轮规划中的对应操作；分配操作随后进入异步绑定。它不是跨多个 Pod 的 Kubernetes 原子事务，也不是容器同时启动的承诺。

5. 反过来看：同一个插件如何跨越多个 Action

从插件的角度看，可以更直观地理解这种多对多关系。

插件 它提供的策略 在不同 Action 中怎样被复用
gang 作业有效性、最低成员条件、Ready / Pipelined、部分排序和候选相关判断 allocate 检查可提交规模；backfill 使用相应有效性检查；传统 preempt / reclaim 使用对应成员保护；新 Gang 路径还与 Action 的分组逻辑协作
capacity 队列排序、准入、可分配性、申请方回收资格、回收候选过滤和记账 enqueue 判断准入；allocate 判断分配额度；传统 reclaim 使用 Preemptive / Reclaimable；gangreclaim 使用其对应 UnifiedEvictable 分支
priority Job / Task 等对象的优先级比较，以及相应抢占候选判断 多个 Action 使用排序入口；传统 preempt 与 gangpreempt 分别通过各自接口参与受害者筛选
drf 当前多资源主导份额的公平性、传统资源竞争判断和动态记账 在使用相应 Job 排序的 Action 中提供公平性；也参与已实现的传统抢占回收和分配事件处理
predicates 工作负载和节点约束的预处理与过滤 allocate / backfill 判断候选节点；抢占回收路径通过对应过滤和放置评估复用相关约束
nodeorder、binpack 对合格节点计算放置偏好 allocate、backfill 等需要节点评分的流程复用这些策略

这张表也说明了“插件只执行一次”的问题：OnSessionOpen 通常每轮调用一次，但它注册的 Predicate 或排序函数，可能在同一轮中针对不同作业、不同节点被调用很多次。

如果要追踪某个插件是否影响了某次决策，需要定位到“哪个 Action 的哪个扩展点，输入的 Job / Task / Node 是什么”，仅看到插件已经初始化还不够。

6. 传统抢占回收与 Gang 版本使用不同接口

6.1 四个 Action 的受害者入口

Action 主要竞争范围 关键受害者筛选入口
preempt 同一队列内的传统抢占 Preemptable
reclaim 跨队列的传统回收 Reclaimable
gangpreempt 面向 Gang 的队列内抢占 UnifiedEvictable，EvictionKind 为 GangPreempt
gangreclaim 面向 Gang 的跨队列回收 UnifiedEvictable，EvictionKind 为 GangReclaim

这些入口的差异来自实际代码，而不是术语上的同义替换。preempt reclaim gangpreempt gangreclaim

还有一个容易因名字误判的接口：Preemptive 在这里用于检查申请方的回收资格；Preemptable / Reclaimable 用于筛选受害候选。 不应把 Preemptive 填成传统 preempt 的主要受害者过滤接口。

Gang 版本会在 Action 及其辅助逻辑中构造、重组受害任务集合，并进行成组放置验证。传给 UnifiedEvictable 插件回调的候选仍是 Task 列表，不能因为外层处理 bundle，就假定所有插件都直接接收一个完整 Job 对象或 bundle 对象。

6.2 v1.16.0 中哪些典型插件注册了 UnifiedEvictable

下表只回答“是否注册这个特定回调”，不等于判断该插件在整个 Action 中是否还有其他作用。

插件 注册 UnifiedEvictableFn 对新 Gang Action 应怎样理解
priority 是 可参与 gangpreempt 的优先级候选筛选
gang 是 此处与 Action 的成组流程协作；不能把传统逐 Pod 最低成员保护原样搬过来理解
conformance 是 可为新路径提供相应的候选保护过滤
capacity 是 GangReclaim 分支执行回收额度过滤；GangPreempt 分支直接允许候选，不能把回收额度检查一概画到 gangpreempt
proportion 否 可以通过排序、Preemptive 等其他入口参与，但传统 Reclaimable 额度过滤不会因此自动成为 UnifiedEvictable 过滤
drf 否 其传统候选筛选接口不等于已经适配新的 UnifiedEvictable 路径
pdb 否 有传统 Preemptable / Reclaimable 和 VictimTasks 相关能力，不能仅凭启用它就推断新接口获得相同过滤
cdp 否 传统候选冷却保护不能直接等同于新 Gang 接口中的保护

由此可见，替换 Action 时，不仅要看功能名称是否相近，还要核对它实际调用的扩展点，以及配置中的插件是否实现了对应接口。

6.3 启用 gang 插件，不会自动执行 gangpreempt

gang 是插件，gangpreempt 和 gangreclaim 是 Action。前者注册策略；后者必须出现在实际执行配置中，才会组织相应流程。

同样，启用 rescheduling 并不等于调度器会自动执行未配置的 shuffle。rescheduling 提供候选选择策略，shuffle 才是消费相应 VictimTasks 结果并执行驱逐的流程之一。rescheduling shuffle

7. tiers 和 enable 开关怎样改变实际调用

7.1 多个插件的结果并非都采用同一种组合方式

Session 不只是一个函数注册表，还负责组合多个插件的结果。以 v1.16.0 为准：

扩展点类别 主要组合规则 直接影响
Queue / Job / Task 排序 按配置顺序，首个非零比较结果决定先后 前面的排序策略可能已经决定结果
JobReady、Allocatable、Preemptive 启用的判断中任一拒绝，就不能通过 多个硬条件需要共同满足
Predicate 等过滤 出现过滤错误则对应检查失败 节点必须满足参与的约束
节点评分 组合不同 scorer 的得分，包含各自的权重和处理逻辑 多个偏好可以一起影响节点选择
JobEnqueueable / JobPipelined Permit / Reject / Abstain 三态；一个 tier 无 Reject 且有 Permit 时可提前通过；全部 Abstain 最终默认通过 后续 tier 可能不再执行
受害者筛选 按该接口的 tier 规则组合候选，可能提前返回 不能假设所有 tiers 始终构成全局严格交集
Allocate / Deallocate 等通知 通知相关处理器更新状态 本轮余额、份额等随临时操作变化

这些规则需要按具体扩展点阅读，不能把 tiers 简化为一个统一的“逐层执行并全部通过”模型。Session 扩展点组合

8.2 从流程看插件的实际介入位置

阶段 谁在推进 调用或执行的关键逻辑 插件与机制的作用
为 A 判断入队资格 enqueue 排序、JobEnqueueable、JobEnqueued capacity 等准入策略检查队列条件并记账
创建 A 的成员 Pod Job Controller PodGroup 入队后同步 task，执行 Job 插件 env / svc 等准备环境；这一步不属于 Scheduler Action
尝试安排 A allocate 额度、节点过滤、评分和临时分配 capacity、predicates、nodeorder / binpack 等共同参与
当前只有 3 GPU 空闲 allocate 检查新作业的整体可运行性 gang 的 JobReady 不满足 4 成员要求，不能把不足规模结果当成完整作业提交
寻找 B 的可回收成员 reclaim 检查申请方资格，调用 Reclaimable 等 capacity 检查资源权益；gang 等参与候选保护
验证回收后 A 的规划 reclaim 模拟释放与预留，检查相应的 JobPipelined 条件 判断计划是否能覆盖 A 的最低规模，再决定是否提交对应操作
真实资源释放 Kubernetes 与节点组件 处理受害 Pod 删除、资源状态更新 释放结果经缓存进入后续调度视图
推进 A 的分配与绑定 后续 allocate 及绑定路径 可用资源满足后形成可提交分配 JobReady 通过，相关操作进入绑定处理
启动训练进程 kubelet 与应用 容器启动、成员发现和训练初始化 已超出本轮 Scheduler 插件回调的范围

在这个简化例子中，B 从 5 GPU 回到 4 GPU，仍满足其最低成员数和保障额度；A 最终可以获得 4 GPU。具体回收判断由已启用的插件和对应路径完成。传统 reclaim capacity gang

8.3 为什么这一过程能说明多对多关系

同一个 capacity 插件在不同阶段分别承担准入、分配额度、回收资格与资源记账；同一个 gang 插件参与可运行规模、预留规模和相应候选保护。allocate、reclaim 则分别组织自己的流程，向这些策略入口发问。

而 Controller 的 env / svc 插件有独立的生命周期，不需要为了给 Pod 注入环境变量而进入 allocate 的节点评分流程。Job 插件实现

9. 排查插件为什么没有生效

遇到“插件明明配置了，但调度行为与预期不同”，可以沿下面的调用链定位。

检查点 应查看什么 示例
Action 是否执行 实际 Scheduler 的 actions 配置 没有 reclaim，就不会执行传统跨队列回收流程
Action 调用了哪个扩展点 对应版本的 Action 源码 gangreclaim 的受害者入口是 UnifiedEvictable
插件是否实现这个扩展点 插件的 OnSessionOpen 注册逻辑 proportion 有传统 Reclaimable，不代表注册了 UnifiedEvictable
对应回调是否启用 当前插件配置和默认值 enableReclaimable 只控制相应扩展点
该分支是否会进入 本次 Job / Task 的状态和输入条件 enqueue 的 MinResources 为空会改变投票路径
是否被 tier 组合规则提前结束 Session 的分派和结果组合逻辑 前一 tier 的结果可能使后续 tier 不被调用
插件本轮看到的状态是什么 快照、临时分配和回滚后的资源核算 当前 used 与本轮模拟后的 used 不一定相同

这条检查顺序把“插件有没有加载”细化成“它是否在当前 Action 的当前决策点实际参与”。对于配额、PDB、冷却期和 Gang 保护，定位到具体入口尤其有价值。

10. 源码阅读入口

10.1 先读框架，再读某个 Action

入口 重点
scheduler.go 一轮调度怎样依配置顺序执行 Action
framework/framework.go 插件何时构造，OnSessionOpen / Close 何时调用
framework/session_plugins.go 各扩展点怎样分派和组合插件结果
actions/allocate/allocate.go 排序、额度、过滤、评分和 Gang 条件怎样连起来
framework/statement.go 临时分配、提交、回滚和绑定之间的关系
plugins/gang/gang.go 同一插件怎样注册多个扩展点
plugins/capacity/capacity.go 准入、分配、回收和记账怎样共用队列视图

10.2 比较新旧回收路径

阅读 reclaim 和 gangreclaim 时，先定位受害者入口分别调用了哪个 Session 方法，再进入 Session 的分派实现，最后检查相应插件是否注册回调。按照这个方向，可以避免从插件名字推测实际保护范围。

本文表格是 v1.16.0 的调用关系说明。升级版本或替换 Action 后，应重新核对注册和调用位置；同名插件的可用扩展点会随实现演进。
