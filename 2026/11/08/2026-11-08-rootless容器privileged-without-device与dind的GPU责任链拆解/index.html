runc 补篇之后：rootless 容器、privileged-without-device 与 dind 的 GPU 责任链

发表于2026-11-08|更新于2026-11-08|AI Infra
|浏览量:

一句话结论：GPU 在容器里的可见性，不是由 --gpus 或 --device 这一层的写法决定的，而是由最外层那一次分配定死的——下游每一层都只能在集合内部重分配，一张也变不出来。

三条推论：

  1. rootless 影响的不是 request/limit 生效（那发生在宿主机的 kubelet / device plugin 进程里），而是运行时能不能把设备节点塞进去；
  2. privileged 与 device 是两条正交的轴，且 privileged 的默认行为是连设备一起给你——「门全开但屋里没东西」必须靠显式 opt-out 才能达成；
  3. dind 里 --gpus all 的 all 永远是局部 all——它能重分配外层给它的集合，但一张也变不出来。

这篇是《容器运行时拆解·补篇》的续篇。原篇把 runc create 之后的世界切成四个侧面——权限、记账、I/O、退出；这篇顺着同一条责任链往下走，聚焦读者最常追问的三个场景。

① 原理 · 一 ~ 六 —— 先把坐标系立起来：谁在什么时刻决定了什么。

一、先把责任链的三个时刻钉死

原篇的收束句是「runc 只在 create 的那一刻存在，之后的一切都由其他组件接手」。这句话对，但如果把它读成「create 之后就定型了」，就会踩坑。准确的说法是把 GPU 的一生切成三个时刻：

时刻 谁在做 决定了什么
create 之前 kubelet + device plugin 这个 Pod 被分配了哪几张卡（记账、调度、准入）
create 那一刻 运行时（含运行时包装器）+ runc 这些卡以什么形式出现在容器的 /dev 里（设备节点、cgroup 规则、env、驱动库）
create 之后 节点上的监控 / 运维组件 这些卡怎么被观测、怎么被回收——runc 早已退出

⚠️ 更正一（原稿最根本的一处）：原稿写「GPU 的可见性是 runc create 时一次性注入到容器 spec 里的……之后 kubelet 不再介入、runc 也早已退出……它能看到的 /dev 就被这一刻固定了」。

设备节点在 create 之后仍然可以被增删。 只要有一个进程能进入容器的 mount namespace，它就可以在里面 mknod 出新节点、或 rm 掉旧节点——这不需要容器重启，也不需要重新 create。本文第七、九节要讲的 Sky-DevBox，其 GPU 热插拔功能就建立在这一点上：它 nsenter 进正在运行的容器，mknod 一个 /dev/nvidiaN 出来，GPU 立刻可用。

所以真正被「固定」的不是 /dev 的内容，而是最外层那一次分配给出的集合。下游每一层都只能在这个集合内部重新分配，不能把它撑大。这个区别是本文后面所有讨论的基石。

三个时刻里，第一个时刻发生在宿主机侧的 root 进程里，与容器内进程是谁完全无关；第二个时刻才是运行时真正「动手」的地方；第三个时刻属于观测平面。三个问题分别落在这三个时刻上。

2.2 「privileged 看不到新设备」的正确读法

原稿引用的 moby issue 是真实存在的，但结论要精确化。issue #16160 的标题就是 「New devices on host are not exposed to privileged container」，报告者说得很清楚：脚本在容器里挂载 EBS 卷，宿主机的 /dev/xvdc 出现了，容器里没有。社区结论是容器的 /dev 是一份在创建时装配好的快照，不是宿主机 /dev 的实时镜像——有人形容它 「looks like a manually assembled /dev/, and not inherited from the hosts」。

所以准确的表述是：

  • 创建时就存在的设备 → privileged 容器默认就有；
  • 创建之后才出现的设备（热插拔硬盘、后加载的驱动建出来的节点）→ 不会有，因为 /dev 已经装配完了；
  • 想绕开，社区土办法是 -v /dev:/dev --privileged（把宿主机 /dev 整个 bind 进来），但 fabiand 在同帖里指出 /dev/pts、/dev/ptmx、/dev/mqueue、/dev/shm 会有诡异问题。

这条「快照语义」正是热插拔功能存在的原因：要么在创建时把设备给全，要么在创建后想办法把节点补进去。

2.4 小结：两条轴，四个象限

把「权限」和「设备」拆成两条轴，四个象限就清楚了：

无设备注入 有设备注入
非 privileged 默认容器：/dev 只有基础节点，devices cgroup 是白名单 标准 GPU 容器：--device / device plugin 注入
privileged 需要显式 opt-out：privileged-without-host-devices privileged 的默认形态：全量宿主设备 + cgroup 全开

原稿把左下角当成了右下角，这是它后面 Q2、Q3 推理跑偏的源头。

三、mknod 不是空壳：设备节点的真相

⚠️ 更正三：原稿写「即使 privileged + 所有 capabilities 都在，容器内 mknod /dev/nvidia0 c 195 0 也造不出一个可用的 GPU 设备——设备节点只是个入口……而 mknod 出来的节点只是个空壳。所以 privileged-without-device 在 GPU 场景下等价于完全无 GPU」。

设备节点不是空壳，它就是设备的入口本身。 一个字符设备节点的全部内容就是 (type, major, minor) 三元组——内核拿到这三个数就去 cdev 表里找对应的驱动。只要驱动已加载、devices cgroup 放行，mknod 出来的节点和 --device 挂进来的节点在功能上没有任何区别。

这一点不是我推理出来的，是 Sky-DevBox 的生产代码在依赖它：它的 GPU 热插拔实现就是「读宿主节点的主次设备号 → 在容器里 mknod 一个同号的节点」。

3.1 真正拦人的是 capability 的坐标系

mknod 系统调用对字符/块设备节点要求 CAP_MKNOD。关键在于这个检查用哪个 user namespace。user_namespaces(7) 把 CAP_MKNOD 和 CAP_SYS_TIME、CAP_SYS_MODULE 归为一类：

「Only a process with privileges in the initial user namespace can perform such operations.」

也就是说，内核用的是 capable(CAP_MKNOD)（对照 init userns），不是 ns_capable()（对照容器自己的 userns）。这解释了两件事：

  • rootless 容器里 mknod 设备节点一定失败，哪怕容器内的进程「是 root」、capability 全在——因为它的 capability 只在自己的 userns 里有效。
  • 但「从外面伸手进去 mknod」可以成功，只要伸手的那个进程在 init userns 里有 CAP_MKNOD。

所以第五节那张表里的「rootless 容器：容器内无法 mknod」，准确读法是「无法自己造节点」；节点仍然进得来，只是必须由外面的运行时替它挂。这也正好解释了 CDI 为什么在 rootless 下能工作——它走的就是「运行时替你把节点和库配好」这条路，而不是让容器自己 mknod。

3.2 nsenter 的 flag 里没有 -U

Sky-DevBox 的热插拔实现（pkg/dind/server/gpu_hotplug.go）是这样的：

数一下 flag：-m mount、-p pid、-u uts、-i ipc、-n net——没有 -U（user），也没有 -a（all）。

这是个非常刻意的设计：

  • 进入 mount namespace，所以 mknod 创建的文件落在容器的 /dev 里；
  • 不进入 user namespace，所以进程的凭据仍是宿主 root，capable(CAP_MKNOD) 检查通过；
  • 主次设备号是先从宿主机的同名节点上读出来的（ls -l 取第 5、6 字段），保证造出来的节点指向同一个设备。

-m 和 -U 的取舍不是可有可无的细节——如果顺手加了 -a，这个功能就会立刻失效：进程会掉进容器的 userns，capable(CAP_MKNOD) 随即失败。

顺带说，同一个仓库里另一处 nsenter 用法（pkg/utils/cmd_runner.go 里的 HostNSEnterCommandRunner）用的是 --mount --pid --net --ipc --uts --cgroup --target 1——同样没有 --user。在一个代码库里两次独立地做出同一个选择，基本可以确认这是有意为之。

3.3 一个能跑的 GPU 到底需要什么

反过来，也要说清 mknod 单独不够的地方。/dev/nvidia0 只是入口，一个 CUDA 程序要真正跑起来还需要：

要素 谁提供 缺了会怎样
/dev/nvidiaN 设备节点（mknod 或 --device） nvidia-smi 看不到这张卡
/dev/nvidiactl 驱动控制节点 NVML 初始化失败
/dev/nvidia-uvm、/dev/nvidia-uvm-tools UVM 节点 CUDA 上下文创建失败（Failed to initialize NVML / cudaErrorNoDevice 类症状）
devices cgroup 放行 spec.Linux.Resources.Devices open() 被 EPERM 拒绝
用户态驱动库（libcuda.so、libnvidia-ml.so…） NVIDIA Container Toolkit 注入 二进制找不到库
环境变量（NVIDIA_VISIBLE_DEVICES 等） device plugin 的 Allocate 响应 运行时不知道该注入哪些卡

所以正确的结论是：mknod 出来的节点是可用的，但只 mknod 一张 nvidia0 通常不够用——因为 nvidiactl / nvidia-uvm 和用户态库往往不在。手工挂 /dev/nvidia0 之所以「看起来不行」，原因在缺少其余几项，而不是节点本身是假的。

五、rootless：换的是坐标系，不是权限大小

第二节讲的是权限轴，这一节讲坐标系轴。rootless 的关键不是“权限更小”，而是换了一套 uid 映射——理解了这一点，后面所有的“为什么这里会 EPERM”都好解释了。

5.1 机制：容器内的 0 是宿主机的另一个数

rootless 的本质是 user namespace 的 ID 映射。容器内的 uid 0 被映射到宿主机上的一个高位 uid（典型的 /etc/subuid 布局是 alice:100000:65536），于是：

  • 容器内进程 id 显示 uid=0(root)，自我感觉良好；
  • 宿主机上 ps aux 看到的是 uid 100000；
  • 所有 capability 检查都发生在初始 user namespace，容器内那个「root」在宿主机上什么特权都没有。

5.2 K8s 里的 rootless 长什么样

这里要补一个原稿没提、但很关键的事实：Kubernetes 官方并不叫它「rootless 容器」，它叫 user namespaces，入口是 spec.hostUsers。官方文档原文：

「A pod can opt-in to use user namespaces by setting the pod.spec.hostUsers field to false.」

它的版本线是：1.25 alpha → 1.30 beta → 1.33 默认开启 → 1.36 GA（feature gate 已锁定，无法关闭）。

⚠️ 更正六（概念混淆，但很常见）：原稿给的 Pod YAML 里，把「租户容器不给 root」的实现点写成了：

runAsNonRoot 不是 rootless。 它是 kubelet 的一个准入检查——如果镜像的 USER 是 root（或没写 USER），容器会被拒绝启动。它只回答「这个容器以哪个 uid 运行」，完全不涉及 user namespace。容器内 uid 1000 在宿主机上仍然是 uid 1000；文件权限、capability 检查、mknod 规则统统没变。

真正打开 user namespace 的是 hostUsers: false。两者可以叠加，但作用完全不同：

字段 作用层 效果
runAsNonRoot: true kubelet 准入 + 进程 uid 容器不以 uid 0 运行
hostUsers: false 内核 user namespace 容器内的 0 被映射到宿主机的高位 uid

原稿后面所有「rootless 下 mknod / BPF 会被拒」的推理，前提是 hostUsers: false，不是 runAsNonRoot。如果只写了 runAsNonRoot，容器仍然跑在初始 user namespace 里，那些限制一个都不会出现。

前置条件不是免费的：

  • 内核 ≥ 6.3（tmpfs 从 6.3 起支持 idmap mount，而 ServiceAccount token、Secret 都走 tmpfs）；
  • 节点上 /var/lib/kubelet/pods/ 所在的文件系统要支持 idmap mount（ext4 / xfs(ftype=1) / btrfs / tmpfs / overlayfs）；
  • containerd ≥ 2.0 或 CRI-O ≥ 1.25；runc ≥ 1.2 或 crun ≥ 1.9（推荐 1.13+）。

capability 的行为也被官方点明了：

「CAP_SYS_MODULE does not have any effect if granted to a pod using user namespaces, the pod isn’t able to load kernel modules.」

「CAP_SYS_ADMIN is limited to the pod’s user namespace and invalid outside of it.」

5.3 三道关卡

把前面几节的结论合起来，rootless 下的 GPU 有三道互相独立的关卡：

关卡 root 容器 rootless 容器 卡在哪
设备节点可见性 可 mknod、可 bind mount、可 CDI 容器内无法 mknod（capable(CAP_MKNOD) 在 init userns） 只能用「外面伸进来」或「创建时注入」的现成节点
devices cgroup 写权限 运行时以 root 写 devices.allow / 加载 BPF 无 CAP_BPF / CAP_SYS_ADMIN bpf_prog_query(BPF_CGROUP_DEVICE): operation not permitted
驱动 ioctl 权限 capabilities 全开 capability 只在本 userns 有效 个别 ioctl 仍可能被拒

第二道就是下一节的主角。

六、legacy 与 CDI：为什么 rootless 下 legacy 会崩

换了坐标系之后，第一个撞墙的是 NVIDIA 那一层。这一节讲清墙在哪、以及 CDI 是怎么绕过去的——它也是后文讨论“这套实现为什么不用 CDI”时的参照系。

6.1 legacy 模式：prestart hook 要改 cgroup

NVIDIA Container Toolkit 的 legacy 模式下，nvidia-container-runtime 会在 OCI spec 里注入一个 prestart hook，容器创建时由 nvidia-container-cli 去挂驱动库、并把设备规则写进 devices cgroup。

在 cgroup v2 上，devices controller 是 eBPF 程序。要往里面追加规则，得先查询当前挂载的过滤器——这一步需要调用方在初始 user namespace 里有 CAP_BPF/CAP_SYS_ADMIN。rootless 下没有，于是整个容器创建失败。

6.3 CDI：把特权操作换成纯数据合并

CDI（Container Device Interface） 的思路完全不同：把「访问一个设备需要什么」（设备节点、挂载、env、附加 GID）写成一份 YAML，运行时在 create 时读这份 spec 并合并进 OCI spec。这是一次纯数据合并，不需要 mknod、不需要写 cgroup、不需要 BPF。

NVIDIA 官方文档里那句关键的话是：

「CDI also improves the compatibility of the NVIDIA container stack with certain features such as rootless containers.」

版本线（均出自官方 release notes / CDI 文档）：

  • 1.12.0：开始支持生成 CDI spec；
  • 1.18.0：默认模式改为 JIT-CDI——「The default mode of the NVIDIA Container Runtime has been updated to make use of a just-in-time-generated CDI specification」，同时 legacy 模式被标记为 deprecated；
  • 1.19.1：CDI spec schema 默认升到 v0.7.0，会让老运行时（containerd < 1.7.16、docker < 26.1.0、podman < 5.1.0、crio < 1.30.0）不认，需要 no-additional-gids-for-device-nodes 特性开关。

切换命令与产物路径（官方原文）：

  • CDI spec 写在 /var/run/cdi/nvidia.yaml；
  • 由 nvidia-cdi-refresh 这个 systemd service（.path + .service 两个 unit）自动生成；

七、Q1：GPU 的 request/limit 到底在哪一层生效

原理铺完了，从这一节开始正面回答三个问题。第一问最常被问到：写下 resources.limits.nvidia.com/gpu: 2 之后，这个 2 是在哪一层被兑现的？

7.1 标准答案：生效在 create 之前，与容器内 uid 无关

把链路铺平：

  1. 调度：resources.limits.nvidia.com/gpu: 2 让调度器只看 node 的 allocatable；
  2. 准入：kubelet 的 Device Manager 调 device plugin 的 Allocate；
  3. 注入：Allocate 的返回值被塞进 CRI 的 ContainerConfig，containerd 构造 OCI spec；
  4. 落地：运行时（runc，或被包装的 runc）在 create 时把 linux.devices、linux.resources.devices、env、mounts 写进新容器。

官方文档对 Allocate 返回值的描述是：

「An AllocateResponse contains zero or more ContainerAllocateResponse objects. In these, the device plugin defines modifications that must be made to a container’s definition to provide access to the device. These modifications include: Annotations / device nodes / environment variables / mounts / fully-qualified CDI device names.」

第 1、2 步都发生在宿主机侧的 kubelet / plugin 进程里，它们以 root 身份运行。 容器内进程是 root 还是 alice，对这两步没有任何影响。

另外两条硬约束（K8s 官方文档原文）：

「The API server restricts quantities of extended resources to whole numbers.」

「Extended resources cannot be overcommitted, so request and limit must be equal if both are present in a container spec.」

所以 limits: 2 = 独占两张卡；想做「一卡多人」必须换机制（MIG / time-slicing / MPS），不能靠 request/limit。

rootless 真正影响的是第 3、4 步——能不能把设备塞进去。这就回到第六节：CDI 能，legacy 在 rootless 下会崩。

9.1 闭集是一层层传下来的

现象：--gpus all 只挂到 2 张卡。三层原因，逐层回溯：

第一层：外层 Pod 的 /dev 是闭集。 kubelet 调 Allocate 拿到的是具体的设备节点，这些节点被写进 OCI spec 的 linux.devices，由运行时在 create 时创建/挂载进容器。外层容器的 /dev 里只有这 2 张卡的节点，/dev/nvidia2 ~ /dev/nvidia7 根本不存在。

一个实践上的边界：mknod 补进去的节点，对之后新启动的进程立刻生效（新敲一条 nvidia-smi、新起的训练进程都会看到它）；但已经在跑、且已经初始化过 NVML 的进程通常感知不到——NVML 是在进程内初始化时确定设备列表的。所以这个功能定位是「给运行中的开发容器补卡」，而不是「给运行中的训练任务动态加卡」。这也和 9.2 的结论闭环：卡数在进程初始化那一刻就被 NVML 数完了。

但它改变不了集合的边界。 reconciler 的输入 ls /dev | grep nvidia 列的是 dind 自己的 /dev——也就是外层 Pod 给它的那 2 张卡。它能在 2 张里做任意分配（给 A 容器 1 张、B 容器 1 张、或都给 A），但一张也变不出来。

这就是本文最核心的那句话：闭集不是「create 时定死的」，而是「由最外层那一次分配定死的」；下游每一层都只能在内部重分配，不能扩张。

9.4 两条路径与一条不推荐

路径 做法 适用
A（推荐） 不在 dind 里控卡，让外层 K8s 控 外层 Pod 直接申请 N 张，dind 里 --gpus all 继承子集。责任链最干净，记账不漂移
B dind 里用 CDI 名 / NVIDIA_VISIBLE_DEVICES 精确指定 需要外层挂载设备节点；可选范围仍被外层注入集合封顶
C（不推荐） 外层 hostPath 挂全 /dev 见下

路径 C 的问题不只是安全：

  • 它绕过了 K8s 的记账。这 8 张卡在 device plugin 眼里仍然是「已分配给这个 Pod 2 张」，剩下 6 张在调度器看来是空闲的，可以被别的 Pod 抢走——于是两个 Pod 同时用同一张卡，双重记账 / 记账漂移就此发生。
  • 在托管 dind 里这条路通常已经被堵死：Sky-DevBox 的 hijack 层拒绝 IpcMode == "host"，并把所有 mount source 重写到 /mainroot 前缀下——你想挂宿主机的 /dev，挂到的是主容器的 /dev。

③ 取舍 · 十 —— 从一个真实实现往回看，设计是怎么被约束反推出来的。

十、把镜头拉远：这套实现的三个设计取舍

三问答完了。七、八、九节分别讲了「运行时怎么把设备拿到手」「权限模型长什么样」「嵌套之后边界怎么传」——但它们都是局部视角。这一节退一步，看这套实现整体上做过的三个取舍。它们都不是实现细节，而是在 K8s 的能力边界之外做选择——也正是本文标题里「责任链」三个字最具体的含义。

10.1 为什么会有这套东西：从 sidecar 到 sibling

最初的 dind 是一个 sidecar 容器，和主容器同处一个 Pod：

重构方案的设计稿把它的限制列成了四条：

限制 具体问题 用户感受
文件系统隔离 sidecar 挂不到主容器的根目录，只能同步共享存储路径 docker run -v 的挂载路径受限
可观测性缺失 用户看不见、也控制不了 sidecar 容器 出问题拿不到反馈，没法自查自修
配置不可控 改不了 dockerd 配置（比如代理设置） 无法定制，体验差
资源不互通 sidecar 与主容器各有各的 CPU/内存限额 配额不能互相借用，用不灵活

设计稿的结论很干脆：这四条归根结底是 K8s 框架本身的限制——K8s 无法单独管理 Pod 内某个容器的生命周期，也无法绕过自己的资源分配体系让容器之间共享配额。所以方向定为脱离 K8s，从宿主机侧提供 dind 服务。

dind 因此从 sidecar 变成了 sibling：由宿主机的 agent 直接在 containerd 里创建，与主容器平级，K8s 完全不知情。

这一步是理解后面所有设计的钥匙。 一旦 dind 不再是 K8s 管理的容器，K8s 就管不了它——没有 Pod 边界、没有 securityContext、没有 ResourceQuota 覆盖它。平台必须自己把这套治理补回来。 第八节那个 HTTP 劫持层、下面 10.2 的 cgroup 嵌套、dockerctl 的 token 鉴权，全都是在补这一课。

这是最能说明「设计意图 ≠ 落地形态」的一处，也是它和第六节的直接呼应。

为什么放弃？把前几节的结论拼起来就很清楚：

  • dockerd 要的能力和 rootless 正面冲突：挂载、iptables、建网络命名空间、mknod——都要 CAP_SYS_ADMIN，而 userns 里的 CAP_SYS_ADMIN 只在 pod 自己的 userns 内有效（§5.2 的官方原文）。dind 要的恰恰是「对外部世界生效」的那部分特权。
  • rootless dockerd 自己就要一整套配套：rootlesskit、slirp4netns、/etc/subuid 映射，外加 cgroup v2 的委派链。
  • NVIDIA 那一层当时还没准备好：6.2 节那两次回归全都出在 rootless 路径上，legacy 模式在 rootless 下直接崩。

于是这套实现选了另一条路：容器 privileged（要 SYS_ADMIN 就给全），但把设备默认收走（privileged-without-host-devices），再用运行时侧的设备解析（7.2 节）把该给的设备精确补回来，最后用 API 策略层（8.3 节）把租户能做的事框住。

换句话说——它用「显式白名单 + 策略层」换掉了「userns 隔离」。隔离强度不如 userns，但工程上可落地、和 GPU 生态兼容。这是个很务实的取舍，也是本文想传达的核心：责任链上的每一层都在做这种取舍，没有免费的隔离。

一个排查时值得记住的小漂移：设计稿的伪代码写的是 pod.Annotations["<api-group>/dind-enabled"] == "true"，而代码里实际是 pod.Annotations["<api-group>/dind"] == "enabled"。设计稿在前、实现在后，这类漂移很正常，但排查时永远以代码为准。

十二、踩坑清单

按症状查，每条都指回正文对应的小节。

  • 「rootless + legacy nvidia-container-cli = 启动失败」：症状是 bpf_prog_query(BPF_CGROUP_DEVICE) failed: operation not permitted。根治是切 CDI 模式（nvidia-ctk config --in-place --set nvidia-container-runtime.mode=cdi，1.18.0 起已默认 JIT-CDI）。版本要锁到具体小版本——1.17.7 和 1.18.0 都踩过这个坑（见 6.2）。
  • 「privileged 但 nvidia-smi 看不到卡」：先确认是不是真的「privileged 且无设备」。默认 privileged 是带全量宿主设备的；看不到卡，说明有人显式开了 privileged_without_host_devices / privileged-without-host-devices，那就得走 --device 或 CDI 显式注入。别在 privileged 本身找原因。
  • 「容器里有 /dev/nvidia0，CUDA 还是报错」：检查 nvidiactl、nvidia-uvm、nvidia-uvm-tools 和用户态驱动库是否齐全（见 3.3）。手工 mknod 一张卡通常不够。
  • 「dind 里 --gpus all 只看到一部分」：不是 bug，是外层注入的闭集。想扩，改外层 Pod 的 request；想在 dind 里控，走 CDI 或热插拔。
  • 「CDI 名解析失败」：unresolvable CDI devices 说明 spec 里的设备节点路径在运行时自己的文件系统里不存在。CDI spec 不是「挂进去就生效」的配置，它是需要在当前文件系统里解析的实体引用。
  • 「containerd 1.7 上 CDI 不生效」：1.7 默认 enable_cdi = false，2.0 起才默认启用。
  • 「kubelet 重启后 nvidia.com/gpu 从 node status 消失」：这是 device plugin 的已知重启语义（kubelet 重建 socket 目录、插件需要重新注册），排查思路见 为什么 Device Plugin 不必比 kubelet 先启动。
  • 「Pod 里写了 limits 但没生效」：先看 cgroup driver 是否两边一致，再看 GPU 是否走了 device plugin 之外的旁路（例如 hostPath 挂 /dev，导致 kubelet 完全不记账）。

十三、回到原篇

原篇的收束句是「runc 只在 create 的那一刻存在，之后的一切都由其他组件接手」。套到 GPU 上，可以再具体一层——但要修正一处：

  • GPU 的 request/limit 生效发生在 create 之前（kubelet 调 Allocate 拿到设备清单）。它根本不经过 runc；在 Sky-DevBox 那条路线上，它甚至还会在 create 期间被运行时包装器重放一遍。
  • GPU 的可见性发生在 create 那一刻，但不止于那一刻。runc 在这里只做「注入」，不做「决策」；而注入进来的节点，之后还可以被 nsenter + mknod 增删。
  • GPU 的记账与观测发生在 create 之后（DCGM / NVML 采样、cgroup 读数），runc 已经退出。

所以「每一层的能与不能，都是某一次 create 时注入的闭集决定的」这句话，应该改成：

每一层的能与不能，都是由最外层那一次分配给出的闭集决定的。下游可以在这个集合内部任意重分配，但没有任何一层能把它撑大。

这个修正看起来只是措辞，实际影响排查方向：当你在 dind 里发现少了两张卡，不要往下游找——下游（reconciler、--gpus、CDI）都只能重分配。要往上游找，去找那一次 Allocate 给了几张。

这也解释了为什么「谁在什么时刻决定了什么」这个结构比任何具体命令都重要：命令会变（legacy → CDI → JIT-CDI），版本会回归（1.17.7、1.18.0），坐标系会换（rootless 与否），但闭集的边界由最外层分配决定这件事不会变。

最后补一句第十节留下的结论：责任链上的每一层都在做取舍，而取舍会被上游的约束反推着走。 Sky-DevBox 的设计稿写了 rootless，落地时换成了 privileged + opt-out 设备 + 运行时侧设备解析 + API 策略层——不是因为 rootless 不好，而是因为 dockerd 要的特权、rootless 的配套成本、以及当时 NVIDIA 在 rootless 路径上的两次回归，共同把这个选项排除了。看懂这种「约束反推设计」的链条，比记住任何一层的具体配置都更有用。
