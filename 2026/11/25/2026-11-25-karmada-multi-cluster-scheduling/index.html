Karmada 多集群调度实战：一个 Deployment 如何分发到两个集群

发表于2026-11-25|更新于2026-11-25|AI Infra
|浏览量:

假设一套 Nginx 服务需要运行在两个 Kubernetes 集群，总共六个副本。平台希望 member1 跑两个，member2 跑四个，还希望 member2 使用单独的资源请求。用 Karmada 可以把这三个决定分别写进 Deployment、PropagationPolicy 和 OverridePolicy，在一个 API 入口提交，再沿着 ResourceBinding 和 Work 查清每个集群收到了什么。

这里有两次调度。Karmada 选择集群并分配副本，成员集群的调度器再为每个 Pod 选择节点。这个分工也决定了如何排障。一个跨集群调度成功的 Deployment，仍然可能因为成员集群的配额、镜像或节点约束而无法提供服务。

1. 从资源模板到成员集群

Karmada 有自己的 Kubernetes API 入口和存储。在这个入口创建的 Deployment 是待分发的资源模板。部署 Karmada 控制平面的宿主集群、提供 Karmada API 的控制平面，以及实际运行应用的成员集群，各有自己的职责。使用 kubectl 时要先确认连接的是哪一个 API。

模板表达应用本身的期望状态，ResourceBinding.spec.clusters 记录选中了哪些成员及其副本分配，Work.spec.workload.manifests 则包含准备送往该成员的实际清单。对于 Deployment 这一类受支持的资源，Karmada 还可以汇总成员状态。排查单个副本时，成员集群的状态和事件能提供更具体的线索。Karmada 架构 · ResourceBinding API

集群注册有两种通信方向。Push 模式要求控制平面能访问成员 API，控制平面侧的执行控制器负责同步。Pull 模式由成员侧的 karmada-agent 连接 Karmada API，拉取下发清单并回报状态，适合成员 API 位于私网的场景。选型时要确认哪一侧能主动访问对端 API，以及执行组件持有哪些凭证和权限。集群注册

clusterNames 限定候选集合。两个成员都满足调度条件时，Divided + Weighted 会把总共六个副本按 1∶2 分成两份。若改用 Duplicated，每个选中的成员都会收到六个副本。需要把应用集中在尽量少的集群时，可以考虑 Divided + Aggregated。静态权重表示期望的分配比例，集群容量和实际可用副本还要分别核查。v1.17 的静态权重分配不应用 spreadConstraints，因此不能把这两个字段叠在一起当作跨地域高可用保证。分发与副本策略 · 覆盖策略

如果分发的是训练 Operator 的自定义资源，还要核对控制平面和目标成员是否具备相应的 CRD，目标成员是否部署了负责协调该资源的 Operator。Karmada 能理解原生 Deployment 的副本与状态，自定义资源要支持同类能力则取决于已有解释器或自行提供的 Resource Interpreter。对于需要 gang 调度、RDMA 和低延迟链路的紧耦合训练任务，常用做法是先选择一个满足条件的集群，再由成员侧调度器为整组 Pod 选节点。Resource Interpreter

4. 集群故障恢复还要经过流量和数据两层

Ready 变化、禁止新调度、驱逐存量应用是不同的动作。在 v1.17 中，系统可以给异常集群加 NoSchedule 污点；要让 NoExecute 触发存量工作负载驱逐，还需要启用相应的控制器能力，并核对 Failover feature gate、污点来源和应用的容忍规则。恢复能否成功，也取决于其他候选集群能否容纳新的工作负载。集群污点管理 · 集群故障转移

故障演练时，可以分别记录替代集群被选中、替代副本就绪、入口流量恢复的时间。第二个时刻可以从新成员的 rollout 和健康状态确认，第三个时刻要从用户入口探测。即使在两个集群都下发了同名 Service，跨集群发现和流量切换仍需要相应的网络、服务发现或网关配置。多集群服务发现

对有状态应用，还需要验证目标集群能读取 checkpoint 或副本数据。Karmada 的 statePreservation 可以把应用状态中提取的标识传给新实例，例如供 Flink 查找 checkpoint 的 Job ID。数据复制、存储路径的可达性以及双写时的隔离，仍由应用和存储系统处理。尤其是在网络分区下，控制平面失去联系时，旧实例仍可能运行，单写场景需要独立的防双写机制。有状态应用的故障转移
