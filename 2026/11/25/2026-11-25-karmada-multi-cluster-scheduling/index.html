AI 算力平台该不该引入 Karmada？从一次 GPU 作业下发算起

Published2026-11-25|Updated2026-11-26|AI Infra
|Views:

用户申请一台八卡开发机，平台返回了任务 ID，目标集群却迟迟没有 DevMachine。如果平台已经有全局调度器，也有能向指定集群下发 CR 的 Agent，我首先会问值班同事两件事：现在能查到这次请求走到了哪一步？哪一步最经常需要人来补救？这两个答案，比集群数量更能决定引入 Karmada 值不值。

在目标集群已由平台选定、现有 Agent 能可靠下发的前提下，我会先保留现有链路。 当多个团队开始重复实现策略分发、状态聚合、资源漂移修复或跨集群迁移时，Karmada 才有一笔明显的研发成本可以替平台承担。代价也很具体，下一次开发机没有出现，值班人多了几个要负责的控制器和一套要恢复的数据。

一次下发经过哪些对象

Karmada 在成员集群之上提供 Kubernetes 风格的 API。宿主集群负责运行 Karmada 组件，平台将资源模板和分发策略写入 karmada-apiserver，实际的训练和开发机在成员集群执行。这三个角色即使共用基础设施，排障时也要分清各自的 API 入口。集群级调度回答作业去哪里，节点级调度回答每个 Pod 在哪台机器上运行。Karmada 架构

flowchart TD
    platform["平台 API / 自研全局调度器"] --> template["Karmada API：资源模板 + PropagationPolicy"]
    template -->|匹配策略| binding["ResourceBinding"]
    scheduler["karmada-scheduler"] -->|写目标集群| binding
    binding -->|Binding Controller 应用覆盖规则| work["目标成员执行命名空间中的 Work"]
    work -->|Push 执行控制器或 Pull Agent| member["成员 API：Job / DevMachine"]
    member --> operator["Job Controller / 业务 Operator"]
    operator --> pods["本地调度器为 Pod 选节点"]
    member -.状态.-> work
    work -.汇总.-> binding
对象 从哪里能看出进度
Cluster 成员是否注册，是否健康，是否允许调度
PropagationPolicy 选择器命中哪个模板，候选集群和副本策略是什么
ResourceBinding 这份命名空间级模板选中了哪些集群，副本怎样分配
OverridePolicy 在生成成员清单时，哪个集群要改镜像、环境变量或资源请求
Work spec.workload.manifests 是成员应收到的清单，状态记录实际执行结果

在标准部署中，Resource Detector 匹配模板与策略，调度器写入绑定结果，Binding Controller 为每个目标集群生成 Work。成员接收自定义 CR 要先安装相应 CRD，负责执行的 Operator 也要就绪。能复制一份 TrainingJob，与能读懂它的副本数、GPU 需求、依赖和健康条件，是两层能力。后者按需配置 Resource Interpreter，状态回传与聚合也要分别验证。绑定 API · 自定义解释器

Push、Pull 与已有平台怎么接

Push Pull
谁建立日常分发连接 中心执行控制器访问成员 API 成员侧 karmada-agent 主动访问 Karmada API
谁执行成员资源写入 中心持有成员访问凭证 Agent 用成员内身份写本地 API，并用独立身份与中心通信
谁承担日常运维 中心维护到各成员的路由、权限和凭证轮换 每个成员都要部署、监控和升级 Agent，验证出站 TLS 和集群身份隔离

数据面分布在不同 VPC 或供应商网络，只有出站通路时，我会先试 Pull。Agent 通过 List/Watch 获取期望状态，连接恢复后按当前状态重新协调。已有成熟 GPU 调度器时，由它负责选集群和资源预留，将唯一目标写成策略，让成员 Operator 执行业务；愿意把选址逻辑收进 Karmada 的平台，也可以扩展其调度器。两条路径都应指定一个选址结果的写入方。细粒度 GPU 装箱、同域 RDMA、租户配额和整组准入仍需显式实现。集群注册与通信方向

WireGuard、VPC 或专线提供网络可达性。Argo CD 可以从 Git 发布成员的 CNI、CSI、CRD 和 Operator。租户动态提交的 Job、开发机交给业务 API 和分发控制器管理。这样，同一个成员对象的同一组期望字段有明确的写入方，升级基础组件时也能单独回滚。WireGuard · Argo CD 架构

开发机没出现，值班人从哪里查

现有链路是「平台期望状态 → 自研 Agent → 成员 API → 业务 Operator」。如果保留原有平台 API，再接入 Karmada，前半段会增加适配控制器、Karmada 模板、策略、绑定和 Work。成功条件也变多了。用户收到的状态最好带上资源 UID、代次和最近一次成功的阶段，避免拿昨天的成功解释今天的更新。

观察到的最后一步 下一项检查 能缩小到的故障范围
平台已接单，Karmada 里没有模板 适配控制器的队列、模板名、身份权限及 API context 平台向 Karmada 写入失败
有模板，没有 Binding 选择器的命名空间、GVK、名称及依赖覆盖策略 模板尚未匹配或依赖未就绪
有 Binding，没有目标集群 spec.clusters、调度事件、成员健康、约束 可用候选为空或调度器积压
已选中 A，执行空间没有 Work Binding 事件、覆盖补丁、执行命名空间 清单生成或覆盖失败
有 Work，成员没有 CR Work 条件、执行控制器或 Agent 日志、目标 CRD、成员准入 授权、连接、版本或成员 API 拒绝写入
成员已有 CR，开发机仍用不了 成员 Operator 条件，Pod、PVC 和调度事件 业务协调、GPU、存储或镜像问题

Karmada 官方按 API、策略应用、调度、Binding 到 Work、Work 到成员资源分别提供 SLO 排障手册。可以把各段耗时分开，再从用户请求量起一条端到端指标。后一条要覆盖平台适配和业务启动，否则即使所有分发指标正常，用户也可能一直等不到可登录的开发机。官方 SLO 排障手册

需要为哪几项长期付账

运维对象 新增责任 在这个架构里何时发生
karmada-apiserver、etcd 接入和限流、证书、容量、备份、恢复演练和副本隔离 标准独立控制面持续承担
karmada-controller-manager、karmada-scheduler 队列积压、绑定或调度异常、升级和回退验证 每次策略或版本变更都可能触发
karmada-webhook 服务可用性、准入延迟、服务端证书和 CA 配置 API 看起来正常，准入仍可能失败
karmada-agent、跨集群身份 成员分批升级、断线重连、TLS 与最小 RBAC Pull 按成员增加 Agent，Push 集中管理成员凭证
Resource Interpreter 自定义 CR 的健康、副本和状态提取随业务版本演进 需要这些业务语义时承担
平台适配控制器 关联原对象与模板，处理重复事件、删除、回写冲突和升级顺序 保留原有业务控制面时承担

生产 HA 可以采用堆叠 etcd 或外置 etcd。官方对堆叠拓扑给出的下限是三个控制面节点，以便失去一个节点后仍有冗余。可以复用已有机器，但三个副本放在同一故障域，演练时仍会一起消失。我会把备份恢复后租户对象能否重新与成员对账，也放进验收范围。Karmada 高可用拓扑

能否让现有宿主 kube-apiserver 兼任 Karmada API？ 官方 FAQ 的回答是技术上可行，社区测试覆盖有限，常规部署优先独立 API。举例来说，在共享 API 上提交 Deployment 模板，本地 Kubernetes 控制器可能就地创建副本并写状态，Karmada 又会观察到这些变化。只分发自定义 CR 且宿主没有执行它的 Operator，可以避开这一个冲突；准入、监听范围、控制器版本、API 限流和共同故障域仍然要负责。Karmada 官方 FAQ

当整个 Karmada 控制面不可用 用户能观察到什么
已经运行的训练、开发机 成员 API、控制器、网络和存储独立可用时，现有 Pod 通常继续运行；依赖中心续租的业务还要看自身策略
新建、更新或删除 新意图无法经 Karmada 正常送达，成员暂时按最后收到的声明运行
查询运行状态 中心回传中断，缓存可能过期；成员本地可仍有最新状态
自动跨集群迁移 检测、选新集群、重新下发都依赖中心恢复

集群失联后，训练从哪里继续

对已启用相应故障转移策略的负载，Karmada 可以根据集群健康、驱逐条件和候选容量重新选址并下发。要让一份训练从第 8,000 步继续，训练框架还要先写出完整 checkpoint，目标站点要能读取并校验它，Operator 再以正确参数恢复优化器和训练进度。statePreservation 能从旧状态提取标识并传给替代实例，例如用 Job ID 定位 checkpoint；文件复制和恢复由存储与训练系统承担。实际可用行为要核对部署版本、功能开关和策略。集群故障转移与状态传递

我会单独演练一次“中心看不见 A，但 A 仍在训练”。此时启动 B，旧任务可能继续更新同一个 checkpoint。可以给每一轮执行分配递增的 fencing token，让存储写入端验证当前代次并拒绝旧写入；若写入端做不到，就要等旧实例被可靠隔离后再放行 B。单靠心跳超时或创建一个 Lease，无法阻止一个仍有写权限的旧进程。

轻量方案也有一份明确的契约。可以在现有中心 API 上创建每个集群专属的 Work，spec.manifests 装入 tenant-a/dev-001 的 DevMachine 声明，Agent 只监听自己的命名空间，用 Dynamic Client 写成员 API，再把执行代次和业务条件写入 Work/status。账要算全：删除与 Finalizer、离线重放、重连后的全量对账、权限隔离都需要长期维护。OCM 已经提供相近的实现。OCM ManifestWork

这是一份架构判断。集群规模、真实下发 QPS、当前 Agent 的故障记录和当班工时都还没有测量。做替换试验时，我会在同一成员、同一类业务上比较创建到可用的 P95、变更失败后能否自动收敛，以及断网重连后清空积压的时间。自研一侧怎样设计资源账本和成员准入，见配套文章。不使用 Karmada，怎样调度多集群 GPU 作业

clusterNames 限定候选集合。两个成员都满足调度条件时，Divided + Weighted 会把总共六个副本按 1∶2 分成两份。若改用 Duplicated，每个选中的成员都会收到六个副本。需要把应用集中在尽量少的集群时，可以考虑 Divided + Aggregated。静态权重表示期望的分配比例，集群容量和实际可用副本还要分别核查。v1.17 的静态权重分配不应用 spreadConstraints，因此不能把这两个字段叠在一起当作跨地域高可用保证。分发与副本策略 · 覆盖策略

覆盖在生成目标集群清单时生效。控制平面的模板仍声明 50m，member2 收到的清单则声明 100m。这里使用的 JSON Pointer 依赖容器在数组中的位置。模板加入 sidecar 或调整容器顺序后，应重新核对覆盖路径。涉及容量评估时，也应按成员收到的最终请求量核算。

从列表找到资源引用指向 karmada-nginx 的绑定，把实际名称填入 BINDING。调度完成后，第一条查询应列出 member1 2 和 member2 4，行顺序可能不同。

两行配置查询的预期值分别是 2 50m 和 4 100m。配置已经同步但 rollout 超时，就继续看成员 Deployment 和 Pod 事件。比如 API 准入允许了 Deployment，后续 Pod 仍可能卡在节点容量、拉取镜像或健康检查上。实验结束后，可从 Karmada 控制平面执行 kcp delete -f karmada-demo.yaml 清理，再到两个成员确认 Deployment 已删除。
