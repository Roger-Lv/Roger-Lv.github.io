一张 RDMA 网卡怎么区分不同的训练任务：从 QP/PD/MR 到 Rail 感知调度

Published2026-11-24|Updated2026-11-24|AI Infra
|Views:

多个训练任务共享同一张物理 RDMA 网卡，网卡凭什么不串包？

这是理解 RDMA 资源模型最好的入口。先把结论摆出来，四组概念各管一段，缺一层都不成立：

概念 解决什么问题
IP / GID / LID 数据发送到哪台机器、哪个网络端点
QP / QPN 数据属于哪个通信连接
CQ 通信操作完成后如何通知应用
PD / MR / lkey / rkey 哪些内存允许被访问、哪些不允许

RoCEv2 和 InfiniBand 在 QP、CQ、PD、MR 这些核心机制上基本一致，差别在底层网络寻址、报文封装、网络管理与隔离方式。

本文是 RDMA 系列的第五篇。前三篇讲承载 RDMA 的网络本身（技术手册、技术栈全解、全链路拆解），第四篇讲 RoCEv2 无损网络的三件套。这一篇往上一层：网卡内部有哪些资源、它们怎么隔离不同任务、NCCL 又是怎么用它们的。

一、六个核心对象

对象 全称 作用
QP Queue Pair 通信队列对
SQ Send Queue 存放发送操作
RQ Receive Queue 存放接收操作
CQ Completion Queue 存放操作完成结果
PD Protection Domain 内存访问保护域
MR Memory Region 注册给 RDMA 网卡使用的内存区域

围绕它们还有几个名词：

  • WR（Work Request）：应用提交给网卡的操作请求
  • WQE（Work Queue Element）：网卡工作队列中的请求描述符
  • CQE（Completion Queue Entry）：网卡产生的完成记录
  • CM（Connection Manager）：辅助建立 RDMA 连接的组件

与传统 TCP 网络的类比

普通 TCP 网络 RDMA 网络（以 RC 为例）
Socket QP
Socket 连接标识 端点地址 + QPN
TCP Sequence Number PSN
send / recv RDMA Work Request
I/O 完成通知 CQ / CQE
操作系统进程内存保护 PD + MR + 内存访问权限

两者不是完全一一对应，但这个类比有助于理解。

QP 与 CQ 的关系

QP 负责提交通信工作，CQ 负责接收完成结果。队列通常位于网卡可访问的内存中，网卡维护对应的硬件上下文。

假设 NCCL 想发送一段 4 MB 的梯度数据，大致流程是：

  1. NCCL 向 QP 的 SQ 提交一个 WR
  2. 用户态驱动将请求转换为 WQE，并通知网卡
  3. 网卡读取请求及对应数据，执行 RDMA 操作
  4. 对于需要完成通知的操作，网卡向 CQ 写入 CQE
  5. NCCL 轮询 CQ，判断操作是否成功

CQ 不是网络连接，也不是用来存放收到的梯度数据的——它只记录工作完成状态。

而且 QP 和 CQ 不是一对一。多个 QP 可以共用一个 CQ，应用通过 CQE 中的 qp_num 和 wr_id 区分完成的是哪个请求。

二、QPN 如何区分连接

假设 Node 1 上的 RDMA 网卡已经有四个 QP：

QPN 所属任务 对端 QPN 对端 IP 本地保护域
101 Job A 201 10.0.0.2 PD 10
102 Job B 202 10.0.0.2 PD 20
103 Job A 203 10.0.0.3 PD 10
104 Job C 301 10.0.0.4 PD 30

这是一张用于理解的逻辑表，并非网卡真实的硬件数据结构。实际上网卡并不知道 Job A、Job B 这些 Kubernetes 概念，它知道的是 QP、PD、地址和传输状态。

数据到达 Node 2 的网卡后，网卡根据目标 QPN 找到相应的 QP 上下文。此外 RC QP 有自己的 PSN、ACK、重传及其他传输状态，不同 QP 的报文顺序状态也是独立的。

一个容易误解的地方：RoCEv2 虽然使用 UDP 封装，但 RC 模式的 RDMA 通信仍然是可靠传输。可靠性由 RDMA 传输协议实现，而不是由外层 UDP 实现。

三、PD 与 MR 如何隔离内存

QPN 只解决了数据属于哪个连接，还不足以解决内存访问安全——还需要 PD 和 MR。

PD：Protection Domain

PD 可以理解为 RDMA 网卡中的本地内存访问权限分组。创建 QP 时把 QP 绑定到 PD，注册内存时也把 MR 绑定到 PD——接收方处理 RDMA Read/Write 时，必须检查目标内存区域与接收 QP 的 PD 是否匹配。

PD 是本地的保护域，两个通信节点上的 PD 编号不需要相同。它也不是 Kubernetes 给每个 Job 分配的全局租户 ID。

MR：Memory Region

Key 用途

rkey 远端 RDMA Read/Write 等操作访问该内存时使用

真实实现长什么样：看 Soft-RoCE

Linux 内核的 Soft-RoCE（RXE）在软件中实现 RoCE 协议，因此可以看到很多在物理网卡中由硬件和固件完成的操作。

内核源码 drivers/infiniband/sw/rxe/rxe_mr.c 中的 lookup_mr() 函数会检查：

  • 本地或远端 key 是否匹配
  • MR 与请求所使用的 PD 是否匹配
  • MR 的访问权限是否满足操作要求
  • MR 是否处于有效状态

而 rxe_resp.c 中，接收方处理远端操作时会使用当前 QP 的 PD 和报文中的 rkey 查找 MR，再检查内存地址范围。这就是真实的底层隔离逻辑。

当然，ConnectX 等物理网卡并不是在 CPU 上执行这段代码，而是由自己的硬件和固件实现相应语义。

两条路径：Slow Path 与 Fast Path

你可能还有另一个疑问：Job A 和 Job B 都打开了 /dev/infiniband/uverbs0，为什么 Job A 不能直接操作 Job B 创建的 QP？

因为这里还有一层 Linux 内核资源管理。ib_uverbs 根据文件描述符和用户态上下文跟踪资源对象，通过内核维护的对象句柄限制进程能够操作的资源。这也解释了为什么进程退出时，即使没有主动调用所有资源销毁函数，内核通常也能回收该上下文拥有的 RDMA 资源。

路径 操作 执行方式
Slow Path 创建 QP、CQ、PD，注册 MR 用户态与内核驱动交互
Fast Path 提交 WQE、收发数据、轮询 CQ 通常直接操作映射的队列及网卡寄存器

这个设计既实现资源管理和权限检查，又避免每次收发数据都经过内核协议栈。

Step 3：创建 QP

调用成功后，驱动和网卡为应用创建 QP 并返回分配好的 QPN。

QPN 不是由 AI 平台或 Job Controller 分配的，而是底层 RDMA 实现分配的。在相关 RDMA 设备的 QP 编号空间内，同时有效的普通 QP 不会使用相同 QPN。QPN 在不同设备之间可以重复，销毁后也可能被重新使用。

Step 4：交换连接信息

QP 创建完成时还不知道要和哪个远端 QP 通信，所以两端需要交换信息：

例如：

字段 Worker 0 Worker 1
QPN 101 201
初始 PSN 10000 20000
IP 对应 GID ::ffff:10.0.0.1 ::ffff:10.0.0.2
MR 地址 0x10000000 0x20000000
rkey 0xA001 0xB001

通常可以通过普通 TCP Socket 交换这些元数据。其中 QPN、PSN、地址信息用于配置连接；MR 地址和 rkey 用于后续的单边 RDMA 内存操作——后两者不一定在连接建立时交换，也可以按需在后续交换。

也就是说，RDMA 的控制面完全可以走 TCP，真正的大规模训练数据走 RDMA。 两者不冲突。

IB 不需要 IP 就能通信吗

可以。 InfiniBand 原生 RDMA 可以通过 LID、GID、QPN 等信息完成通信，不依赖 IP 协议栈。

但训练框架仍然经常需要 IP 网络，用于 rendezvous、连接信息交换、管理通信等。因此 IB 集群通常会使用普通以太网管理网络，或者 IPoIB。IPoIB 和原生 IB RDMA 是不同的通信方式，不要混在一起。

多租户隔离的四个层次

如果你要提供一个允许不互信租户使用的 AI 云平台，光靠 QP、PD、MR 还不够：

层次 解决的问题 实现机制
连接隔离 正常通信不会串包 QP、QPN、PSN
内存隔离 不能任意访问其他进程内存 PD、MR、rkey
租户网络隔离 未授权租户之间不能通信 VF、VLAN、VRF、P_Key 等
性能隔离 不能抢光别人的资源 QoS、带宽限制、RDMA cgroup
  • RoCEv2 走以太网隔离：通常需要结合 SR-IOV VF、VLAN、VRF、交换机 ACL、硬件防伪造策略等能力。
  • InfiniBand 走 P_Key 分区：Subnet Manager 管理 P_Key 分区成员关系，报文携带对应的 P_Key，网络设备根据分区成员关系检查。

⚠️ 两个必须警惕的点：

  1. RDMA 数据可能绕过宿主机普通网络协议栈，因此不能默认 Kubernetes NetworkPolicy 或 iptables 就能拦截所有 RDMA 流量。必须确认实际的数据路径和策略执行位置。
  2. rkey 不是密码学意义上的身份认证密钥，QPN 和 PSN 也不是安全凭证。 正常通信不串包，与抵御恶意租户攻击，是两个不同的问题。

另外，如果两个 Pod 共享一个允许访问多个 P_Key 的物理 HCA，仍需确保每个租户只能使用授权给它的分区——不能简单地在 Job 中指定一个 P_Key 就认为实现了完整隔离。

七、从训练启动到 QP 建立：四步走

7.1 成员发现（PyTorch / torchrun）

NCCL 不会主动扫描 Kubernetes 集群寻找 Worker，也不会扫描 RDMA 网络判断哪些网卡属于同一个训练任务。它是由上层训练框架告知参与者身份，然后在这些参与者之间建立通信拓扑。

整个过程有三个层次：

层次 负责者 确定什么
训练任务成员发现 PyTorch / torchrun 哪些进程属于同一个 Job、Rank 是多少、总共有多少 Rank
通信拓扑构建 NCCL 哪些 GPU 应该互相通信、用 Ring 还是 Tree、选哪些网卡和路径
RDMA 连接建立 Verbs 创建 QP、CQ，交换 LID/GID/QPN，建立实际数据传输连接

用一个具体例子走一遍：4 个 Worker、每个 Worker 2 张 GPU 和 2 张 RDMA 网卡，即 4 个 Pod、8 张 GPU、8 个训练 Rank（WORLD_SIZE = 8）。

注意 Worker Pod 和 Rank 不是同一个概念。在常见的一进程一卡模式下，一个 Worker Pod 里可能有 8 个 Python 训练进程，每个进程有一个全局 Rank。NCCL 主要在 Rank 粒度上组织集合通信，而不是 Kubernetes Pod 粒度。

7.3 Communicator 如何区分两个训练 Job

NCCL 有一个重要概念叫 Communicator（通信域）：

参数 含义
comm 当前进程的通信域对象
world_size 通信域包含多少 Rank
unique_id 通信域初始化标识
rank 当前进程在通信域中的编号

典型情况下，Rank 0 调用 ncclGetUniqueId(&id) 生成 ID，然后 PyTorch 通过 Store 把这个 ID 分发给其他参与训练的 Rank。所有 Rank 使用相同的 Unique ID 初始化 NCCL Communicator。

即使 Job A 和 Job B 都存在 Rank 0、Rank 1、Rank 2、Rank 3，它们也是不同通信域中的 Rank。 它们不会因为共用一张网卡就自动加入彼此的训练任务。

当然，这种通信域区分不是密码学意义上的租户安全隔离，平台仍需要提供网络访问控制。

九、LID / GID 标识的到底是什么

准确来说，LID 和 GID 标识的是 RDMA 网络端点，通常与 RDMA Port 相关联——而不是简单地标识一张物理网卡，也不是标识一个 Pod。

物理网卡、物理端口、虚拟设备、网络地址、通信连接，其实是五个不同的层次：

概念 标识粒度 示例
PCI Device PCIe 设备或功能 0000:81:00.0
RDMA Device / HCA RDMA 设备实例 mlx5_0
RDMA Port RDMA 设备的端口 mlx5_0/1
LID / GID 网络端点地址 0x0011、::ffff:10.0.0.11
QPN RDMA 通信队列 101、102

它们并不是一一对应的。 一张物理网卡可以有多个物理 Port，可以虚拟出多个 VF，一个 RDMA Port 也可以有多个 GID。

RoCEv2：GID 与 IP 的关系

假设物理机上有一张 ConnectX 网卡，通过 SR-IOV 创建两个 VF 分别交给两个训练 Pod：

设备 IP GID
PF / mlx5_0 10.0.0.10 ::ffff:10.0.0.10
VF 0 / mlx5_1 10.0.0.11 ::ffff:10.0.0.11
VF 1 / mlx5_2 10.0.0.12 ::ffff:10.0.0.12

在 RoCEv2 模式下，IPv4 地址通常以 IPv4-mapped IPv6 的形式表示为 GID。当 CNI 给 VF 对应的网络接口配置 IP 后，支持该接口的 RDMA 驱动通常会自动维护相应的 GID Table。

每条 GID Table 记录主要包含 GID Value、GID Type（RoCEv1 或 RoCEv2）、关联的 Network Device。因此同一个 IP 甚至可能在 GID Table 中出现两次，分别对应 RoCEv1、RoCEv2。

✅ 一个对平台设计的实用结论：在典型 SR-IOV RoCE 方案中，你的 AI 平台通常不需要额外实现 GID 分配器——配置好 VF 和 IP，驱动就会处理相应的 GID。

如果不是 SR-IOV，而是 Shared RDMA

情况就不一样了。假设两个 Pod 使用 hostNetwork 共享同一个 RDMA 设备，此时两个 Pod 可以拥有：

  • 相同的 HCA
  • 相同的 Port
  • 相同的 IP
  • 相同的 GID
  • 不同的 QP、CQ 和内存保护上下文

所以 GID 不一定能够区分训练任务，QPN 才是区分普通 RC 通信连接的关键标识之一。

InfiniBand 的 LID / GID

IB 与 RoCE 最大的不同是它有自己的网络寻址体系：

  • GUID：通常是一个 64 位的设备或端口标识
  • LID：由 Subnet Manager 分配，用于 IB 子网内的报文转发
  • GID：128 位地址，通常由 64 位子网前缀和 64 位接口标识组成

对于没有虚拟化的 IB 网卡，两个 Port 有各自的 LID 和 GID。此外 IB 的 LMC 机制允许一个 Port 拥有多个 LID。

开启 SR-IOV 后要区分具体的 IB 虚拟化模式：

IB 虚拟化方式 LID GID
物理 HCA 端口拥有 LID 端口拥有 GID 表
Shared Port PF、VF 可以共享 LID VF 有自己的虚拟 GID 表
支持独立 LID 的虚拟化模式 VF / 虚拟端口可以拥有独立 LID 可以拥有独立 GID

传统 IB Shared Port 架构下，不同 VF 共享物理端口的 LID，但拥有自己的虚拟 GID 表、P_Key 表和设备上下文。

两种网络的资源管理差异

配置项 RoCEv2 InfiniBand
VF 创建 SR-IOV SR-IOV
网络地址管理 IPAM SM、GUID 管理等
GID 产生 驱动根据关联接口 IP 等维护 IB 端口标识与子网配置
LID 分配 不用于 RoCE 转发 Subnet Manager
Pod 必须有 RDMA 网卡 IP 常见部署需要 原生 IB 通信不依赖 IP
QP 创建 应用运行时 应用运行时

十一、Rail：把连线照着通信模式安排

为什么要设计 Rail

假设有两台 GPU 服务器，每台 2 张 GPU、2 张 400 Gbps RDMA 网卡，网络采用 Rail-Optimized 架构。

同 Rail 通信：

跨 Rail 通信：

同 Rail 只经 1 台交换机、不占用 Spine 链路。Rail-Optimized 的核心设计目的，就是尽可能减少不必要的跨 Rail 流量，让不同 Rail 并行工作，降低流量之间的相互干扰。

跨 Rail 会发生什么

网络架构 跨 Rail 的结果
Rail-Only，Rail 完全独立 无法直接通过网络通信
Rail-Optimized，Rail 之间有限带宽互联 可以通信，但容易出现性能瓶颈
全互通、无阻塞网络 可以正常通信，性能影响可能较小

情况一：Rail 完全不互通。 两个 Rail 之间没有网络路径，NIC 0 无法直接向对端 NIC 1 发送 RDMA 数据。这时即使两个 Worker 的普通 Pod IP 能互通、NCCL 也可能通过 TCP 成功交换 QPN 和 GID，但实际 RDMA 数据无法到达对端。可能出现：

  • 路由或邻居解析失败
  • QP 初始化失败
  • RDMA 数据发送后收不到 ACK
  • RC QP 不断重试，最终超过重试次数
  • NCCL AllReduce 卡住或训练任务超时退出

甚至可能出现 QP 已经进入 RTS 状态，但实际上无法完成数据传输。 因为 QP 进入 RTS 不代表底层网络一定可达。

情况二：Rail 之间互通但带宽有限。 这是更典型的性能问题。例如 4 条各自需要 400 Gbps 的通信流同时经过一条 400 Gbps 的跨 Rail 链路：总需求 1600 Gbps，瓶颈容量 400 Gbps，每条流量平均只能获得原先四分之一的带宽。

更严重的是，AI 训练通常是同步通信——即使其他 Rank 的通信都很快，只要某条关键通信路径很慢，其他 Rank 就可能不得不等待。局部网络拥塞会扩大为整个训练任务的同步等待，这也是大模型训练对网络尾延迟特别敏感的原因。

跨 Rail 时 QP 会发生什么变化

你可能会认为跨 Rail 时交换机需要重新建立 QP。实际上不需要。

NCCL 在创建连接时就已确定发送端和接收端的 RDMA 端点。只要底层网络可达，数据包可以经过多台交换机到达远端 QP。交换机只负责网络转发，不会为你的训练任务创建新的 QP。

对象 跨 Rail 时是否改变
源 QPN / 目的 QPN 不变
目标 GID / LID 不变
PD / MR / rkey 不变
网络转发路径 可能更长
通信带宽和延迟 可能变差

所以跨 Rail 本质上是网络路径与资源竞争问题，不是通信连接隔离问题——它不会因为经过不同 Rail 就让两个训练任务的数据串在一起。

PXN：用节点内带宽换外部跨 Rail

PXN = PCI × NVLink，✅ 已核实（来源：NVIDIA 官方技术博客 Doubling all2all Performance with NCCL 2.12）：NCCL 2.12 引入，用于优化包括 All-to-All 在内的通信场景。

思路是：先在本机通过 NVLink 把数据转移到与目标端处于同一 Rail 的 GPU/网卡上，再发出。这样就能利用节点内的 NVLink/NVSwitch 带宽，减少外部网络的跨 Rail 流量。

官方博客另外提到，PXN 还能让网络层把多个消息聚合（multireceive），减少穿过二级 Spine 交换机的流量。

所以 GPU 0 的数据并不一定必须通过 NIC 0 发送。实际能否使用取决于硬件拓扑和通信库配置。

NCCL_CROSS_NIC 控制什么

参数 含义 适用场景
NCCL_CROSS_NIC=0 尽量要求同一 Ring/Tree 使用对应 NIC Rail-Optimized，跨 Rail 带宽有限
NCCL_CROSS_NIC=1 允许同一 Ring/Tree 使用不同 NIC 网络充分互通
NCCL_CROSS_NIC=2 优先对应 NIC，但允许性能更好的其他选择 默认值，通用场景

✅ 已核实（来源：NVIDIA 官方 Performance and Tuning 文档）：默认值确为 2，原文 “The default value is 2”。

官方文档特别指出，即使设置为 0，当不同节点上的 Communicator 使用了不同位置的 GPU 时，也仍然可能需要跨 NIC 通信。因此：

不是一个强制网络隔离开关，也不能保证任意 GPU 分配组合都能正常通信。

这对调度设计的影响

假设有两台 8 卡 GPU 服务器，每张 GPU 附近都有一张 RDMA 网卡，分别连接 Rail 0～7。现在用户申请两个 Worker、每个 Worker 使用 4 张 GPU：

  • Rail 对齐分配：Node 0 和 Node 1 都各分配 GPU 0～3（Rail 0～3）→ 两个 Worker 共同获得 4 个对齐的 Rail，具有良好的同 Rail 直接通信条件
  • 随机分配：可能一方拿 GPU 0～3、另一方拿 GPU 4～7（Rail 4～7）→ 跨 Rail 流量激增

收尾

四句话把所有知识串起来：

Rank 决定我是谁、和谁一起训练。
NCCL 通信拓扑决定我应该和谁交换数据。
LID / GID 决定数据应该到达哪个 RDMA 网络端点。
QPN 决定到达该端点后，由哪个通信队列处理数据。

而你的云平台要做的是保证这些训练进程能够发现彼此，并给它们提供正确、可达、隔离且性能合适的 RDMA 网络资源。剩下的连接创建工作，由 NCCL 在运行时完成。

网卡分配给 Pod，只是让 Pod 获得了使用 RDMA 的能力；真正的 RDMA 通信连接，是训练进程启动后，根据训练任务的通信拓扑动态创建出来的。

感知能力 解决的问题
RDMA-Aware 节点有没有 RDMA 资源
NUMA-Aware GPU 和网卡距离是否足够近
Rail-Aware 不同 Worker 的网卡能否高效地相互通信
Fabric-Aware 整个训练任务是否处于合适的高速网络域

第一版可以先实现 RDMA-Aware。如果后续要支持 GPU 服务器上的多租户共享和非整机分配，Rail-Aware 很可能就是下一步的重点。
