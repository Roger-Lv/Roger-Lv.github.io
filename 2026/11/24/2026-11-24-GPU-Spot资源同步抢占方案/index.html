GPU Spot 资源同步抢占方案：把异步驱逐升级为同步使用权交接

发表于2026-11-24|更新于2026-11-25|AI Infra
|浏览量:

Kubernetes 里 GPU 的分配状态和实际使用状态常常对不上：用户申请了开发环境却几天不跑任务、训练卡在 CPU 预处理阶段、实验做完没释放、夜间和周末大量开发容器闲置、训练结束后还留着 CUDA Context 和部分显存。

传统调度器只看申请量。只要资源已被 Pod 申请，哪怕 GPU 长期空转，其他任务也无法通过常规独占式调度拿到它。

Spot 机制就是把这部分闲置算力转成可抢占资源。但常规实现有个绕不开的问题——回收是异步的。

本文的方案与 Spot 资源实现深度解析：从虚拟设备到偷卡超卖的完整链路 讲的是同一类问题的两个阶段：那篇拆的是已落地系统的异步实现（自定义 runtime + ioctl 劫持 + 低功耗检测），这篇讲的是一套同步交接的设计方案——把「检测到 Owner 活跃」到「Spot 真正让出 GPU」之间的时间窗口，从事后补偿变成事前阻塞。

一、异步回收的问题出在哪

只靠 NVML 利用率检测 Owner 回归，时间线是这样的：

T1 到 T5 之间，Owner 可能已经发生显存 OOM、计算延迟或通信超时。 这就是被动式回收——平台在 Owner 已经受伤之后才开始补救。

根因是：NVML 是采样指标，不是资源准入控制点。 它可以告诉你「GPU 好像空着」，但它无法在 Owner 即将申请显存的那一刻拦一下。

方案的核心设计由此而来：GPU Reclaim Barrier（GPU 资源回收屏障）——Owner 恢复使用时，平台不是发一个驱逐事件就走，而是先阻塞 Owner 的新 GPU 请求，等 Spot 真正释放资源后，再放行进入真实 CUDA Driver。

SLA 边界要先说清

这个方案的目标不是让 Owner 完全无感知、零延迟恢复，而是：

  • 避免因 Spot 占用显存导致 Owner 竞争性 OOM
  • 避免 Owner 恢复后与 Spot 持续争抢算力
  • 把 Owner 回归的额外等待控制在可观测、可管理的范围内
  • 资源无法安全回收时明确报故障，而不是破坏资源隔离

⚠️ 严格同步保障依赖两个前提：GPU 请求能够被可靠拦截，且 Spot 的 GPU 使用权能够被有效撤销。对于不受平台管理、可绕过 Hook 的工作负载，不承诺上述强保障。这一点后面「安全边界」一节会展开。

二、Spot 资源模型

三种 GPU 类型

类型 说明 可抢占
Free GPU 尚未分配给任何租户 视分配策略而定
Owner GPU 已分配给正式租户 否
Spot GPU 从闲置 Owner GPU 派生的临时使用权 是

Spot GPU 不是新增的物理 GPU，而是基于现有物理 GPU 派生的逻辑资源使用权。

举个容易混淆的例子：一台节点 8 张物理 GPU 全部分配给正式租户，其中 3 张满足闲置复用条件——平台可以额外提供最多 3 个整卡型 Spot 使用权。但节点仍然只有 8 张物理 GPU，不能把它当成 11 张。

Kubernetes 资源表达

普通 GPU 继续用 nvidia.com/gpu，Spot 工作负载申请独立的扩展资源：

Spot Device Plugin 向 kubelet 注册逻辑设备 ID，并维护「逻辑设备 ↔ 物理 GPU UUID」的映射。

为什么必须用独立的资源类型：Kubernetes 原生扩展资源不支持直接超卖，Spot 资源只能通过独立逻辑资源表达，并由平台自行实现底层物理设备复用与使用权管理。

另一个关键约束：动态上报 Spot GPU 数量只能作为调度供给信息，不能作为实际资源使用权的最终依据。最终准入必须由节点侧 Lease Manager 确认。

四种复用模式与推进顺序

模式 资源状态 难度 建议
整卡闲置复用 Owner 无存活 CUDA Context 低 第一阶段
Context 保留复用 保留 Context 和部分显存，但无计算 中高 第二阶段
部分显存复用 Owner 使用部分显存 高 后续
部分算力复用 Owner 持续使用少量算力 高 后续
GPU 状态挂起复用 Owner GPU 状态迁移至主机内存 高 实验性

第一阶段优先做整卡闲置复用，避免一开始就引入 GPU 时间片共享和动态显存切分。

三、闲置资源怎么发现：NVML + eBPF

NVML：采样指标，不是证明

Agent 通过 NVML 采集节点 GPU 状态：

接口 用途
nvmlDeviceGetUtilizationRates 整卡 GPU 利用率
nvmlDeviceGetMemoryInfo 显存使用情况
nvmlDeviceGetProcessUtilization 进程级 GPU 利用率
nvmlDeviceGetProcessesUtilizationInfo 进程级利用率采样信息
nvmlDeviceGetComputeRunningProcesses_v3 GPU 计算进程与显存占用
nvmlDeviceGetUUID 物理 GPU 唯一标识

⚠️ NVML 是采样，不能严格证明某个时刻不存在待执行的 GPU 工作，部分进程级查询在 MIG 模式下还有限制。所以它的定位是发现候选闲置资源、辅助确认状态，而不是排他性资源分配的唯一依据。

eBPF：观测 CUDA 行为

在宿主机侧部署 eBPF Collector，通过 Uprobe/Uretprobe 监控实际加载的 CUDA Driver Library：

API 含义
cuInit CUDA Driver 初始化
cuDevicePrimaryCtxRetain 获取 GPU 主上下文
cuCtxCreate 创建 CUDA Context
cuMemAlloc_v2 / cuMemAllocAsync 显存申请
cuMemCreate GPU 物理内存分配
cuLaunchKernel / cuLaunchKernelEx Kernel 提交
cuGraphLaunch CUDA Graph 提交
cuMemcpyAsync 异步数据传输

记录字段包括 Timestamp、Host PID/TID、Process Start Time、Cgroup ID、CUDA API、API Return Code、GPU UUID。

需要处理：不同驱动版本的符号差异、容器内动态库映射、通过函数指针调用 CUDA API 的情况。

一个实现上的坑：Kernel 提交可能经过用户态命令队列，不保证每次都产生 ioctl 系统调用。所以不建议直接以 ioctl 作为 GPU 活跃状态的主要判据。而且普通 ioctl 也无法区分 GPU 计算请求与 nvidia-smi 这类管理查询。

进程归属识别链路

多租户场景必须区分 Owner 和 Spot 的行为：

两个细节：

  • 不能直接用容器内的 CUDA Device Index 当物理 GPU 标识——不同容器里的 cuda:0 可能映射到不同的物理 GPU。
  • PID 会复用，进程身份要结合启动时间或 pidfd 等机制识别。

闲置判定条件

建议初始参数（需按真实用户行为与集群负载调优）：

参数 建议初始值
NVML 采样周期 1 秒
Owner 利用率阈值 5%
持续闲置时间 300 秒
CUDA 活跃事件静默时间 300 秒
最小剩余显存比例 20%
回收后冷却时间 300 秒

整卡 Spot 模式还应额外要求 Owner 不存在未受管理的 CUDA Context 和显存占用。最终，候选 GPU 必须经过同步借出屏障、确认能安全交接使用权后，才能进入可分配状态。

四、Owner 回归的六级信号

把 Owner 的 CUDA API 调用按强度分级：

等级 典型行为 平台处理
L0 管理查询 nvidia-smi、nvmlInit 不触发回收
L1 初始化意图 cuInit 提高关注度
L2 Context 获取 cuCtxCreate、cuDevicePrimaryCtxRetain 触发准入检查
L3 资源申请 cuMemAlloc、cuMemCreate 同步触发回收
L4 工作提交 cuLaunchKernel、cuGraphLaunch、实际数据传输 同步触发回收
L5 实际计算 NVML 检测到 Owner GPU 活跃 紧急兜底回收

几个必须注意的反直觉点：

  • Context 创建是较早的使用意图，但不代表一定会执行计算。
  • Kernel Launch 是较强的计算需求信号，但可能已经晚于显存申请。
  • Owner 如果一直保留 CUDA Context，可能不再触发初始化或 Context 创建。
  • PyTorch 缓存分配器可能复用已有显存，不产生新的底层显存申请。
  • CUDA Graph 可能直接重复提交预构建的计算任务。

所以必须同时覆盖显存申请、Context 创建和 GPU 工作提交三条路径。

多信号融合：不做 AND

本方案不采用「CUDA API 调用 AND NVML 利用率升高」这种严格与条件。对于明确的 GPU 资源申请和计算提交请求，直接触发同步准入。

四种手段各司其职：

手段 职责
NVML 发现闲置资源
eBPF 感知 CUDA 行为、审计、异常检测
CUDA Hook 同步阻塞及触发抢占
Node Agent 完成实际资源回收

五、同步抢占怎么做：方案选型

方案 同步阻塞 覆盖能力 主要问题
eBPF Uprobe ❌ CUDA 行为观测 无法作为通用阻塞机制
ioctl 追踪 ❌ 部分驱动请求 语义弱、存在漏判
Seccomp User Notification 部分 系统调用级 无法覆盖所有 CUDA 提交路径
CUDA Hook ✅ 受管理的 CUDA API 存在兼容性与绕过问题
CUDA Checkpoint Lock ✅ 已存在的 CUDA 进程 进程级粒度、新进程问题
CUDA Proxy ✅ 经过代理的请求 实现复杂、兼容成本高
调度前置屏障 ✅ 平台创建的新任务 无法覆盖已有容器内部行为
内核驱动改造 理论支持 驱动级资源管理 开发维护成本高

优先采用 CUDA Hook + Shared Memory + Futex + GPU Lease。 对于平台新建的 Owner 训练任务，优先用调度前置屏障，在进程启动前完成资源回收。

调用路径

实现上可以借鉴 HAMi-core 的 CUDA API 劫持、显存限制与 Kernel 提交限流机制（参见 K8s GPU 复用与 HAMi 异构架构全解）。

区别在于：HAMi 做的是静态或动态配额控制，本方案做的是 Owner 与 Spot 之间的动态资源使用权交接。

同步抢占时序

关键点：Owner 的回归事件通过同步 Hook 直接触发回收，而不是依赖 eBPF 事件在用户态异步消费后再执行驱逐。eBPF 可以并行观测这个过程，用于审计、监控和覆盖率验证。

拦截范围

分类 代表接口
Context 管理 cuCtxCreate、cuDevicePrimaryCtxRetain
显存分配 cuMemAlloc_v2、cuMemAllocAsync、cuMemAllocManaged
虚拟显存管理 cuMemCreate、cuMemMap
内存池管理 cuMemAllocFromPoolAsync
计算提交 cuLaunchKernel、cuLaunchKernelEx
Graph 提交 cuGraphLaunch
数据操作 cuMemcpyAsync、cuMemsetAsync 及相关变体
动态入口获取 cuGetProcAddress、cudaGetDriverEntryPoint、dlsym

⚠️ 最后一行是重点：CUDA 提供 cuGetProcAddress 等接口动态获取 Driver API 函数指针，因此仅覆盖普通动态链接符号不足以保证全部调用被拦截。

另外必须区分「会增加或提交 GPU 工作的 API」与「用于释放资源、查询状态、等待已有工作完成的 API」——避免在回收过程中阻塞必要的清理调用，造成死锁。

Hook 实现骨架

对于正常持有 GPU 租约的进程，admission_enter 直接通过共享内存完成快速检查。对于当前 GPU 使用权属于 Spot 的 Owner：

  1. 登记 Owner 回归请求
  2. 通知 Node Agent
  3. 阻塞当前线程
  4. 等待 GPU 租约恢复
  5. 获得准入令牌后执行真实 CUDA API

实际实现需要处理 API 嵌套、重入、异常退出、多线程并发、Context 与设备映射，以及阻塞超时后的 CUDA 错误语义。

IPC 三件套

机制 用途
Unix Domain Socket 进程注册、首次请求、控制消息（控制面）
Shared Memory GPU 租约状态、版本号、快速准入（高频状态读取）
Futex 跨进程线程阻塞与唤醒（避免忙轮询）

共享内存中的租约控制数据应由 Agent 管理，普通租户不能任意修改。Futex 等待必须与原子状态检查结合，处理虚假唤醒、状态版本变化和丢失唤醒等并发问题。

Fast Path 与 Slow Path

Fast Path 不依赖 Kubernetes API Server，也不需要每次 CUDA 调用都做 RPC——这是控制高频 Kernel Launch 性能开销的关键。

六、GPU Lease 与并发一致性

租约模型

节点本地 Agent 是 GPU 实际使用权的权威管理者，Controller 负责集群级状态协调和持久化。

状态机

借出屏障（防 TOCTOU）

平台刚检测到 Owner 利用率为零、准备分配 Spot，此时 Owner 恰好开始新的 GPU 计算——这就是 TOCTOU 竞态。所以借出前必须：

  1. GPU Lease 切换至 LENDING
  2. 原子关闭 Owner 新 GPU 工作的准入入口
  3. 等待此前已获得准入的相关 API 完成提交
  4. 通过 Context 同步、应用协作或驱动支持的机制确认已有 GPU 工作完成
  5. 检查 Owner 保留显存及其他 GPU 资源
  6. 如果期间出现 Owner 新请求，取消借出
  7. 验证通过后，授予 Spot 新版本租约
  8. 开放 Spot GPU 准入入口

⚠️ API 返回不代表异步提交的 GPU 工作已经执行完毕。 所以仅统计 Hook 中的在途 API 数量是不够的，还需要独立的 GPU 工作排空机制。对于无法确认已有 GPU 工作是否完成的进程，应放弃本次借出。

回收屏障

  1. 原子将 GPU Lease 切换至 RECLAIMING
  2. 增加 Generation，使旧 Spot 租约失效
  3. 关闭普通 Spot GPU 请求的准入入口
  4. 禁止调度新的 Spot Pod
  5. 保持 Owner GPU 请求阻塞
  6. 撤销 Spot 使用权并执行终止或挂起
  7. 确认 Spot 进程和 GPU 资源状态
  8. 原子切换至 OWNER_ACTIVE
  9. 开放 Owner 准入入口并唤醒等待线程

如果选择优雅回收，可以为特定 Checkpoint 操作保留一个有明确截止时间的受控清理阶段，但 Owner 仍然保持阻塞。

准入检查的竞态

准入检查与在途调用登记必须构成原子协议：

不能仅依靠 Generation 数字本身实现资源隔离，因为已经取得许可的请求可能仍在执行。Lease Manager 切换使用权时，顺序必须是：先关闭新准入 → 再等待在途调用退出 → 最后完成 GPU 工作排空。

Agent 故障恢复

Node Agent 重启时：

  • 不直接信任 CRD 中的历史 Spot 状态
  • 不自动开放状态未知的 GPU 准入
  • 根据容器运行时、设备分配记录、NVML 和本地状态日志重建租约
  • 确认已有 Spot 资源安全释放后才恢复 Owner
  • 禁止 Agent 失联期间新增 Spot 分配

必要时引入独立的节点 Watchdog，处理 Agent 崩溃导致 Owner 长时间阻塞的问题。

七、快速回收与释放确认

三个回收等级

策略 行为 适用场景
Hard Reclaim 直接强制终止 Spot 对 Owner 延迟敏感
Graceful Reclaim 给 Spot 有限时间保存状态后退出 通用训练任务
Suspend Reclaim 保存 GPU 状态并挂起进程 支持 CUDA Checkpoint 的任务

初始实现建议以 Hard Reclaim 为基础，逐步增加有限时长的 Graceful Reclaim。

为什么回收路径要下沉到节点本地

不要只走这条链路：

涉及多个异步组件，回收时延容易受控制面负载和网络状态影响。

应该：

Controller 异步完成 Kubernetes 对象状态协调、事件记录和 Spot 任务重新调度。

节点本地终止操作应与 kubelet 生命周期协调，避免 Spot 容器在旧租约下自动重启并重新访问 GPU。对于 Job 类型的 Spot 负载，应结合 restartPolicy、任务控制器和启动准入检查避免旧任务被意外恢复。

各种停止方式的比较

方式 停止新增提交 释放显存 保留训练状态
SIGSTOP 暂停 CPU 提交线程 ❌ ✅
Cgroup Freezer 暂停容器进程 ❌ ✅
CUDA Lock 阻塞受支持的 CUDA API ❌ ✅
SIGKILL 终止目标进程 等待驱动清理 ❌
CUDA Checkpoint 挂起并保存 GPU 状态 ✅ ✅
应用 CKPT 后退出 ✅ 等待驱动清理 ✅

⚠️ SIGSTOP 或 Cgroup Freezer 无法直接释放 GPU 显存，也不代表已提交的 GPU 工作立即停止。因此不能单独作为资源回收的完成条件。

释放确认

Kubernetes Pod 对象被删除，不代表容器进程已退出，也不代表 GPU Context 已释放。

校验时要结合：容器运行时状态、Pod Cgroup 中的进程状态、GPU 计算进程及显存占用、驱动状态、资源归属记录、MPS 等共享模式的客户端状态。

资源状态不明确时应进入 QUARANTINED，禁止重新分配该 GPU，并保持准入保护。

NVML 不提供覆盖所有驱动资源的强一致性事务证明，因此释放确认必须建立在实际撤销执行能力之上，不能仅依据单次 NVML 查询。

八、NVIDIA CUDA Checkpoint 原生能力

官方接口

✅ 已核实（来源：NVIDIA CUDA Driver API 官方文档 CUDA Checkpointing 章节）：

官方状态模型是 RUNNING → LOCKED → CHECKPOINTED →（Restore）→ LOCKED →（Unlock）→ RUNNING。另有 cuCheckpointProcessGetState 与 cuCheckpointProcessGetRestoreThreadId。

三个官方文档里的实现细节（做方案评估时值得注意）：

  1. cuCheckpointProcessLock 支持可选的 timeoutMs，超时返回 CUDA_ERROR_NOT_READY，进程保持 RUNNING——这给「有限时长的优雅锁」提供了原生支持。
  2. cuCheckpointProcessRestore 要求先启用 persistence mode 或已调用 cuInit。
  3. 该能力目前仅 Linux 支持。

Owner 侧应用

利用驱动原生能力建立进程级屏障，有望减少自行实现部分阻塞逻辑的复杂度。

但 CUDA Lock 不直接提供完整的 Owner 回归通知机制，平台仍然需要 CUDA Hook、eBPF 或应用侧信号感知新请求。同时需要处理 Owner 新建进程、多 Context、多 GPU 等问题。

Spot 侧应用与它的限制

后续资源重新可用时再 Restore + Unlock + Resume。该方案有减少重新加载模型和优化器状态开销的潜力，但限制也很实在：

  • GPU 显存迁移消耗 PCIe 带宽和主机内存
  • Checkpoint 需要等待已提交的 GPU 工作完成，不保证在固定时间内完成
  • UVM、部分 CUDA IPC、分布式通信等场景存在兼容性限制
  • 不同驱动版本支持的能力有差异
  • 完整的跨节点进程恢复还涉及 CPU 状态、文件描述符、网络连接等资源

因此 CUDA Checkpoint 更适合作为后续实验性优化，而非第一阶段 Spot 容错的必要依赖。

MPS 场景要单独处理

如果未来采用 MPS 实现 GPU 共享，不能直接复用普通 CUDA 进程的强制终止逻辑，否则可能影响共享 MPS Server 中的其他客户端。MPS 提供了 terminate_client 等客户端终止机制，可通过 MPS Server 终止指定客户端的 CUDA Context。

第一阶段建议暂不支持 MPS 共享模式。

九、Spot 容错续训

Spot 任务随时可能被抢占，每次驱逐都从头训练会造成大量算力浪费。

Checkpoint 保存完成的三个层次

异步保存必须区分：

  • Staging Completion：训练状态已完成本地暂存
  • Upload/Save Completion：Checkpoint 写入流程已完成
  • Durable Completion：已满足底层存储持久化要求

较新的 PyTorch Distributed Checkpoint 接口提供了区分 staging 与保存完成的 Future。

⚠️ Sidecar 不应仅通过 inotify 检测文件关闭事件就判断整个分布式 Checkpoint 已保存完成。 建议由训练框架或 Coordinator 在全部 Rank 写入完成后生成 Manifest：

只有全部分片和元数据满足对应提交条件后，该 Checkpoint 才能被标记为有效。

三级存储

层级 选型 作用
L1 节点本地 NVMe 快速保存、同节点恢复
L2 P2P 分发及节点缓存 跨节点快速恢复
L3 JuiceFS 及持久化后端 持久化兜底

P2P 分发可以评估 Dragonfly（参见 具身智能训练存储与数据管线），但需要额外实现 Checkpoint 元数据管理、完整性校验、版本提交和恢复路由。P2P 缓存不能直接等同于可靠持久化。

抢占与 Checkpoint 解耦（重要）

不建议在 Owner 回归时才触发一次完整的分布式 Checkpoint，并等全部数据上传完再回收 GPU。 大模型训练的保存过程包含 GPU→CPU 复制、多 Rank 同步、本地磁盘写入、P2P 传播、远端持久化——这些会显著延长 Owner 的等待时间。

正确做法是 周期性异步 Checkpoint + 有限时长的抢占保存窗口 + 后台数据传播：

  1. 向 Spot 发送回收通知
  2. 如果已有完成暂存的 Checkpoint，可在独立于训练 Pod 生命周期的节点缓存或后台进程中继续持久化
  3. 如果正在保存且能在预算时间内完成，允许有限等待
  4. 超过预算立即回收 GPU
  5. 后续从最近已提交的有效 Checkpoint 恢复

Checkpoint Sidecar 与训练 Pod 同时被删除时，其后台任务也可能终止，因此需要由节点级组件承接尚未完成的数据持久化工作。

分布式训练要以 Job 为单位协调

十、安全边界：必须说清楚的事

CUDA Hook 不是安全边界

基于 LD_PRELOAD 的 CUDA Hook 属于用户态拦截机制，不能天然作为不可绕过的多租户安全边界。潜在绕过路径：

  • 应用未加载平台 Hook Library
  • 应用使用未覆盖的 Driver API 入口
  • 应用通过函数指针绕过普通符号拦截
  • 应用使用不兼容的 CUDA Driver Library
  • 进程已持有 GPU Device FD 或 MMIO 映射
  • 用户具备修改容器运行环境的权限

因此必须明确区分「受管理的协作式资源复用」与「针对不可信租户的强制资源隔离」。第一阶段仅支持经过平台准入和兼容性验证的工作负载。

多层保护

层级 保护方式
Kubernetes Admission 限制可参与 Spot 的工作负载
Container Runtime 注入受管理的 CUDA Hook
Device Access 限制未授权的设备访问
Cgroup 标识租户并辅助进程终止
GPU Lease 控制资源使用权
eBPF 监控异常 CUDA 或设备访问
Node Agent 撤销租约并确认资源释放

⚠️ Linux Cgroup v2 的设备控制机制可通过 BPF 管理设备文件访问权限，但设备访问控制并不能直接撤销已经建立的 GPU 文件描述符、Context 或用户态映射，所以不能单独依赖它完成存量进程的 GPU 抢占。严格不可信租户隔离需要进一步评估驱动级机制、CUDA Proxy、硬件虚拟化等方案。

第一阶段应排除的场景

  • 特权容器
  • 未受管理的宿主机 GPU 进程
  • 不支持 Hook 的 CUDA 应用
  • 延迟敏感型在线推理服务
  • 无法安全终止的训练任务
  • GPU Direct RDMA、MPS 等未经验证的特殊模式
  • GPU 健康状态异常
  • 对 GPU 使用权存在归属争议的设备

IPC 安全

UDS 服务端应验证调用方进程身份及所属 Cgroup，不能信任客户端自行上报的 Pod UID、Owner 身份或 GPU UUID。Agent 的租约共享内存应采取最小权限设计。

跨租户的 Checkpoint 缓存及 P2P 分发也需要独立的数据权限校验，防止不同租户之间读取训练状态、模型参数或数据。

十一、可观测性与验收

Owner 回归时延的分解

分别是：回归信号识别、租约撤销、可选优雅退出、Spot 进程终止、驱动资源清理、资源释放确认、Owner 唤醒。

采用同步 CUDA Hook 后可以显著降低对 NVML 轮询周期的依赖，但整体回收时延仍受 GPU 在途工作、驱动状态、显存规模和进程终止行为影响。

回收策略分级

策略 示例目标 说明
强制抢占 1 秒 不等待应用层 CKPT
快速抢占 5 秒 允许有限清理
优雅抢占 30 秒 允许尝试保存训练状态
GPU 状态挂起 动态 取决于显存规模和传输能力

上述时间是设计预算或 POC 目标，不是未经测试即可承诺的硬性回收时延。

显存余量预留

安全余量按 GPU 型号、驱动开销及实际训练负载配置。显存预留只能降低风险，不能替代同步准入屏障。

十二、分阶段实施与建议先做的三个 POC

五个阶段

阶段 目标 关键产出
Phase 1 Spot 资源感知与基础调度 NVML Collector、归属识别、闲置判定、Spot Device Plugin、基础调度插件、单卡 Spot 任务
Phase 2 eBPF 回归感知 CUDA API Uprobe、Owner/Spot 事件区分、Context 与 Kernel Launch 识别、误判漏判测试
Phase 3 同步资源准入 CUDA Hook Library、UDS 协议、Shared Memory + Futex、Lease Manager、借出/回收双屏障、并发竞态测试
Phase 4 容错续训 PyTorch DCP 接入、Checkpoint Sidecar/Controller、三级存储、P2P 分发、任务重新调度
Phase 5 高级复用 Context 保留复用、部分显存复用、多卡跨节点、CUDA Checkpoint、状态挂起恢复、活跃时间预测

Phase 1 只验证资源发现和逻辑资源管理，不宣称已具备透明的 Owner 同步抢占保障。 同步抢占能力在 Phase 3 完成、且经过兼容性验证后才成立。

建议先做的三个 POC

如果准备落地，不要先投入大量时间开发 Controller 和调度插件——先在单台 GPU 节点验证三件事：

POC 1 · CUDA 同步拦截
验证 PyTorch、FSDP、CUDA Graph 的关键 CUDA 调用能否被透明拦截，并通过 Futex 实现可靠的阻塞与恢复。

POC 2 · GPU 使用权安全交接
让 Spot 占用大量显存，再启动 Owner 训练，验证同步回收能否避免竞争性 OOM，同时测量完整回收时延。

POC 3 · 抢占后的有效计算保留
验证 FSDP 分布式 Checkpoint、强制抢占、跨节点数据恢复、重新训练之间的完整闭环。

这三个 POC 跑通，方案的核心技术可行性就基本验证了。相比之下，CRD、Controller、Device Plugin 和 Scheduler Plugin 都有相对成熟的工程实现范式。

最值得深入的方向

GPU 资源的同步使用权交接机制（Synchronous GPU Ownership Handover） ——它不只是一个 Spot 调度功能，还涉及 CUDA Driver、Linux 进程同步、GPU 资源管理、并发一致性以及分布式训练容错，是整个方案中技术深度最高的部分。

核心链路回顾

方案的核心不是简单地提高 GPU 利用率，而是在保障正式租户资源使用优先级的前提下，实现 GPU 资源的动态复用。五组机制各解决一个问题：

机制 解决什么
NVML 闲置资源发现
eBPF CUDA 行为观测
CUDA Hook 同步准入
GPU Lease 资源使用权一致性
Node Agent 快速资源回收
Checkpoint 系统 抢占后的计算进度恢复
