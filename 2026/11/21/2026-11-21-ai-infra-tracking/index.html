AI Infra 技术追踪｜2026-11-21

发表于2026-11-21|更新于2026-11-21|AI Infra
|浏览量:

首期回看：截至 11 月 21 日 09:00（UTC+8）的过去七天。本文核对了发布说明、论文及项目代码；下文的实验数字来自作者，验证建议尚未实跑。

一句话结论：优先用 MultiKueue 的稳定版补丁验证集群下线是否会重复运行作业；SPICE 和 BidKV 值得做对照实验，但前者不能证明跨站容灾，后者不能把显存压力下的首 token 收益外推到所有流量。

进展 解决的是哪一层 建议
MultiKueue v0.20.7 调度控制面：从派发名单移除集群时，已准入的作业会不会被重复派发 已使用 MultiKueue 时优先验收
SPICE 训练通信：允许改变同步协议时，低带宽会怎样影响达到目标 loss 的时间 研究验证，不改生产拓扑
BidKV 推理引擎：KV 空间不够时，先抢占哪个请求 先重放流量，再决定是否试点

1. MultiKueue：停止向旧集群派新活，不应重跑已经接下的活

11 月 19 日，稳定补丁。 以前从 MultiKueueConfig 移除 worker A，已经在 A 准入的 Workload 可能被重新派发到 B，而 A 上的远端对象没有被删除，同一训练任务便可能跑两份。v0.20.7 与 v0.19.14 修正了这一配置变更路径：已准入的作业继续在 A 跑到结束；A 不再是该配置下新作业的派发候选。v0.20.7 · v0.19.14 · 实现 PR

关键是区分停止新派发与断开管理连接。保留 A 的 MultiKueueCluster 对象和可用连接，以便管理集群继续跟踪状态。这不是 A 失联、删除对象或实际节点丢失时的恢复保证，也不提供任意故障下的 exactly-once。这里的收益是避免双跑和重复写结果；代价是旧集群必须继续可达，直到已有作业排空。发布材料没有给出生产规模或耗时基准。

怎么验： 用管理集群和两个隔离 worker，先让短训练在 A 准入并写带唯一 run ID 的 heartbeat，再仅修改配置移除 A，提交第二个作业。验收：第一份作业只在 A 启动、跑完且管理端记录完成，第二份走 B；同时看两侧 Job UID 和训练进程日志，不只看 Workload 状态。把撤销凭据、网络失联、销毁 worker 留给另一组测试，不与配置移除混为一谈。

2. SPICE：低带宽下少发参数，多联系几个副本

11 月 17 日预印本，训练协议研究。 同步 DDP 需要按训练步完成全局梯度聚合。SPICE 让副本先做本地优化，再与每轮轮换的少量 peer 交换选中的参数坐标及其修正后数值；未发送的位移保留在误差反馈中，以后还能参与选择。它用更小的消息覆盖更多邻居；带截止时间的变体在截止时只聚合已完整到达的贡献。相对 DDP，这改了优化及同步语义，不是把同一个 AllReduce 换条网线。代价是坐标筛选与编码、误差缓存，以及不同步时对收敛的额外验证。论文 §3、§4.4 与附录 B · 提交日期

  • 等时间，图 5： 134M 模型，单机 8 张 RTX A6000，Linux 在每副本的总发送、总接收方向分别限速至 1 Gbps，DDP 走 NCCL sockets。SPICE 每条消息选 3.125% 的坐标、联系 4 个 peer，在同样时间里多处理了 token，验证 loss 比 DDP 低 6%（相对值）。不是“等 token 低 6%”，也不是“快 6%”。论文另一组等 token 实验中，8 副本、2.70B token 的验证 loss 约为 DDP 3.17、SPICE 3.19；它和计时实验的设置不同，不能当成图 5 的严格消融。
  • 临时链路变慢，图 6： 同机模拟三个逻辑网络域，将其中两个域之间受影响的每个有向 worker 对限到 100 Mbps，持续五分钟。常规 SPICE 保留自身健康阶段约三分之二的吞吐，带截止时间时约 86%。归一化分母是各方法各自的健康阶段吞吐，不是跨方法的绝对比值。进程和控制连接仍在线，未验证真 WAN、硬分区、掉节点或 checkpoint 恢复。

怎么验： 在同一负载上比较 DDP、稠密 gossip（GASLoC）和 SPICE，同时报告等 token 的 loss、等时长的 loss、到指定 loss 的时间和 GPU 小时数。额外记线上的字节数、CPU staging、通信等待 p95；把带宽、RTT、抖动分开改。对同步训练，仍优先把 worker 组放在单站内；真正的跨站重启要单独验证完整训练状态和数据游标恢复。

3. BidKV：KV 不够时，按回收收益和恢复代价选请求

11 月 18 日 SC26 报告，作者实验与可读代码；不是 vLLM 稳定版功能上线。 KV cache 不足时，驱逐一个正在运行的请求会腾出块，但它回到调度队列后可能需要重算。BidKV 给候选请求估算能释放的容量和中断代价，用「可释放容量 ÷ 估计代价」排序，再复用引擎原生的回收路径。它改变的是选谁，不新建显存层，也不压缩 KV。估计误差、打分开销和长请求反复被抢占是值得测的代价。SC26 作者报告 · 作者代码

数据边界： 作者用 RTX A6000、Llama-3.1-8B-Instruct、ShareGPT 负载；对比原生 vLLM 策略，报告 p95 TTFT 降低超过 90%，300 ms 首 token SLO 达标率在所报告负载点提高 14.8 个百分点。作者的公开实现将该 SLO 结果标在 3.8 请求/秒。另一个 SGLang 结果对照其原生 LRU，不能和 vLLM 数字相加。数字来自显存压力测试，不代表正常流量、其他 KV 容量或生产规模的收益；较早发表的配套文章已有数据，这周的新动向是 SC26 报告。作者实现与实验说明 · 配套公开论文

怎么验： 固定引擎版本、模型、KV block 上限、请求长度分布和到达时间，仅替换抢占选择器。先做低压力控制组，再做中高压力与突发组；同时记录 TTFT p95、inter-token latency p95、每秒满足 SLO 的请求数、重算 token 和按请求长度分桶的重复抢占率。若 TTFT 变好但长请求反复被踢、decode 尾延迟恶化，不能只按单项指标上线。引擎抢占可用实际 exporter 上的 vllm:num_preemptions_total 验证，避免拿等待队列当事件计数。vLLM V1 指标
